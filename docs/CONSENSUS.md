# Hashstash consensus format

The complete genesis configuration fixes the chain identity and must match the database. [The specification](SPECIFICATION.md) describes economic transitions.

## Canonical encoding

`codec::encode` uses bincode 1 variable-width little-endian encoding. Struct fields appear in declaration order without names; tuples concatenate their elements. Unsigned integer types wider than u8 use the shortest representation below. Enum discriminants are zero-based u32 values encoded by the same rule. Vector, sequence and string lengths use the u64 form. A u8 remains one literal byte, booleans and Option discriminants occupy one byte, and fixed arrays/tuples carry no length prefix.

| Unsigned value | Encoding |
| --- | --- |
| 0 through 250 | One byte containing the value |
| 251 through 65,535 | 251 followed by two little-endian bytes |
| 65,536 through 2^32 − 1 | 252 followed by four little-endian bytes |
| 2^32 through 2^64 − 1 | 253 followed by eight little-endian bytes |
| 2^64 through 2^128 − 1, for a u128 field only | 254 followed by sixteen little-endian bytes |

Marker 255, a marker wider than the destination type, truncated values and nonminimal encodings are invalid. Decoding enforces record limits and rejects trailing bytes or any encoding that differs from its canonical re-encoding. Collection lengths remain bounded by their record and field limits; compact encoding does not relax those bounds.

Public amounts use `types::amount`: decimal strings in JSON and a compact byte-count followed by minimal unsigned little-endian magnitude bytes in binary records. Zero is encoded as an empty byte vector (`00`); a nonempty magnitude ending in a zero byte is invalid. Decoding is bounded by the containing record or request bytes, and subsequent validation applies the configured monetary and share ranges. Decimal strings contain digits only, with no leading zero except `"0"`. Hashes and public keys are fixed 32-byte arrays. State commitment tuples use num-bigint 0.4's sequence of little-endian u32 limbs for unwrapped BigUint values: the limb count and each limb use compact unsigned encoding. This differs from the annotated public-record amount adapter and is part of the specified commitment schema.

One displayed hash is 1,000 raw hash atoms; one displayed stash is 1,000 share atoms. CLI/RPC amounts remain raw integers. Monetary display names do not alter issuance or integer curve arithmetic. Physical mining work uses EH and EH/s. Marked Stash value uses marginal price; a full-redemption quote follows the curve and can be smaller.

## Genesis configuration

The chain ID is `tagged_hash("Hashstash/chain", codec::encode(&config))`. Every Config field participates in declaration order, including the explicit test_work fixture flag. Config and Settings reject unknown JSON fields. The encoded configuration fixes the chain identity. Transaction signatures commit to the chain ID and to an anchor block from that chain; their bodies do not repeat the chain ID. All participants must use the same configuration, transaction/state formats and validation rules. The chain ID binds configuration bytes; it does not attest which software is running. Amount-only clearing, exact leading-price comparison and chain-bound transaction signatures require matching implementations. Start a fresh network with a distinct network name and empty database when changing these rules; existing databases and signed transactions cannot be reinterpreted under a new format.

Config fields are: network, test_work, genesis_time, initial_bits, limit_bits, daa_half_life, timestamp_window, future_seconds, max_signatures, max_height, money_bits, share_bits, max_integer_bits, quote_scale, share_scale, auction_timeout, initial. The source types define each width and amount annotation. The test_work flag must be false in production. An explicit test-fixtures build can accept true for disposable tests; it changes issuance to one expected hash per atom and therefore changes the chain identity. Production builds reject true.

Settings fields are block_bytes, minimum_fee_rate, interval, lead, rest, decision_blocks, max_price_change_bps, miner_fee_percent, pass_margin_bps, in that order. The first seven are u64; interval, lead and rest use seconds, decision_blocks counts blocks, and max_price_change_bps uses basis points. Config's auction_timeout also uses seconds. Both percentages are Option<u64> and must be present. MinerFeePercent is a whole percentage from 0 through 100; PassMarginBps is an unsigned basis-point margin. Config.share_scale is a positive, fixed genesis amount defining the initial raw stash per raw hash. It is not governable.

The three maintained presets use a 15-second target, 900-second ASERT half-life, 11-header median window and 120-second future allowance. Those are preset choices. Genesis validation requires a positive half-life and timestamp-window size; future allowance uses its u32 representation. The operator must choose genesis-only values sensibly, because the chain cannot change them. Validating each block loads up to timestamp_window ancestors. A max_signatures of zero permits only empty blocks, and a very large value lets a full block exceed peer and Stratum work limits ([network controls](NETWORK-HARDENING.md)). The governed half-life also bounds the target interval governance can choose. Timestamp rules and target encoding still apply. The target limit is immutable genesis configuration. The economic clock advances by parent_settings.interval for each block. Auction and rest deadlines preserve their nominal duration when the interval changes; decisions retain a frozen number of blocks. These are scheduled seconds, not header timestamps or wall-clock deadlines; the chain must advance for economic time to pass.

## Transactions and parameters

A signed transaction contains its body followed by exactly 64 BIP340 signature bytes, with no signature-length prefix. Body order is sender[32], nonce:u64, fee:Amount, anchor[32], expiry_blocks:u64, operation, data:Vec<u8>. The nonce and lifetime use compact unsigned encoding. The body fee is the exact total charged when included. The BIP340 signing message is tagged_hash("Hashstash/chain-bound-transaction", chain_id || codec::encode(body)), where chain_id is the 32 raw bytes of the accepting network's chain ID. It binds the network and every body field, including the anchor. The chain ID is signed but never transmitted: block validation, block template selection and mempool admission (local submission, broadcast and peer relay) all verify against the node's own chain ID, so a signature made for another network, or a body anchored on another network but signed for this one, is rejected. The anchor commits to chain history and the receiving node verifies its ancestry. Chain ID also remains in configuration, state commitments, addresses and peer messages, but not in transaction bodies. Transaction IDs are SHA256d of the complete signed record. The anchor must be an ancestor of the including block’s parent, including that parent or genesis. With anchor height A and positive lifetime N, inclusion is valid exactly when A < height <= A + N. The sum uses checked u64 addition; the including block must independently satisfy the network’s height bound. Unknown anchors, references from another branch, zero lifetimes and overflow are invalid. Retries retain the original anchor and lifetime. Removing the anchor in a reorganization invalidates the transaction; a reorganization that preserves it does not. Two forks retaining the same anchor can both accept the transaction while its lifetime and account state permit. The anchor does not select between descendants of a shared block. Conditional Deposit and Redeem orders also sign a decision ID. That ID depends on the opening block's parent and the winning proposal, not on the opening block's contents (see Accounts, reserve and governance). A same-parent sibling of the opening block therefore opens the same decision, and such an order survives that replacement whenever its anchor does.

The anchor-only body layout and chain-bound signature domain are incompatible with earlier transaction bytes and signatures, including the network-independent "Hashstash/anchor-only-transaction" domain; old signed records must not be reinterpreted. A transfer of 1 hash (1,000 atoms), a one-atom fee, a one-byte nonce, a two-block lifetime and empty data is 169 bytes including its signature. Unsigned wallet exports carry separate network context for address formatting; a signer compares it with the network it selected itself and signs for that selection, so a mislabelled export cannot make a signature take effect on another network. The context cannot prove ancestry to an offline signer.

The operation is a direct six-variant enum followed by a length-prefixed data byte vector, including a zero length for empty data. Transaction data has no consensus text format; all bytes count toward the block-byte and fee-weight limits. Chat interprets readable UTF-8, and [Mail](MAIL.md) defines an encrypted application envelope.

| Tag | Operation | Payload order |
| --- | --- | --- |
| 0 | TransferExact | recipient, exact amount |
| 1 | Deposit | amount, optional decision, optional outcome |
| 2 | Redeem | shares, optional decision, optional outcome |
| 3 | Propose | round, description hash, proposal, support |
| 4 | Support | round, proposal ID, amount |
| 5 | Refund | round, proposal ID |

Unknown operation tags are rejected. Round numbers use compact u64 encoding. Outcome tags are Pass=0 and Fail=1. Proposal tags are Grant=0 (payments), Parameter=1 (parameter, old:u64, new:u64). Grant payments are a compact nonzero count followed by pairs of recipient[32] and amount:Amount, sorted by public-key bytes with no duplicate keys. Each key must be valid and each amount positive. The combined amount must fit the configured monetary range; there is no separately encoded total. Decoding is bounded by the actual transaction/record bytes; a hostile count cannot preallocate an oversized list. In JSON the grant is `{"Grant":{"payments":[{"recipient":[...],"amount":"..."}]}}`. Decision hashes and outcome options must either both be present or both absent. Human-readable records reject unknown fields.

Parameter tags are BlockBytes=0, Interval=1, Lead=2, Rest=3, DecisionBlocks=4, MinerFeePercent=5, PassMarginBps=6, MinimumFeeRate=7, MaxPriceChangeBps=8. A proposal's old value must equal the frozen value and its new value must differ. Genesis settings use the representability rules in the first column. Governance changes also need the second column:

| Parameter | Allowed genesis value | Additional rule for a governed `new` |
| --- | --- | --- |
| BlockBytes | From 4,096 through 67,108,864 (64 MiB) weight. The floor holds the heaviest data-free Parameter Propose (339 bytes: every compact u64 at 9 bytes, 512-bit fee and support amounts), its 1,024 record weight and a new mining account's 1,024; the ceiling keeps every valid block within the peer frame, the HTTP response limit, the Explorer's stored-record bound and an SQLite row | `old / 2 <= new <= 2 * old` |
| MinimumFeeRate | Any u64 raw hash atoms per 1,024 weight, including zero | `1 <= new <= max(2 * old, 1)` and `new <= max(initial.minimum_fee_rate, 1) * 2^16` |
| Lead | Any u64 scheduled seconds, including zero | `new <= (auction_timeout - interval) / 2`, saturating at zero |
| Rest | Any u64 scheduled seconds, including zero | `new <= 2^22` |
| Interval | Positive u64 scheduled seconds | `new <= daa_half_life`, `old / 2 <= new <= 2 * old` and `new >= max(1, initial.interval / 4)`; if `new > old`, also `lead <= (auction_timeout - new) / 2` and `decision_blocks * new <= 2^22` |
| DecisionBlocks | Positive u64 block count | `new >= 3` and `new * interval <= 2^22` |
| MaxPriceChangeBps | Any u64 basis-point value; default 1,000 (10%) | `0 < new <= 9,999` |
| MinerFeePercent | A whole percentage from 0 through 100 | None |
| PassMarginBps | Any u64 basis-point value, including zero | None beyond the reachability rule |

Every governed change, whatever its parameter, must also leave `pass_margin_bps < (ceil(decision_blocks / 2) - 1) * max_price_change_bps` (saturating multiplication) in the changed settings. That keeps a later PASS majority arithmetically reachable: its earliest required observation follows `ceil(N/2) - 1` traded blocks, each bounded by the price-change limit. The governed rules exist because a passed value can only be reverted by another decision. Without them, one decision could end governance (fewer than three decision blocks, zero price movement, an unreachable margin, or a capacity too small for any Propose beside a new miner account), stall a phase indefinitely (a huge lead, rest or decision, including one reached by lengthening the interval after a long lead or decision), starve the difficulty schedule (an interval far above the ASERT half-life), price every transaction out (a huge fee rate, also reached by compounding doublings), make permanent account and record state free (a zero fee rate), let one holder empty a world and suppress PASS leads (a price bound of 10,000 basis points or more permits full redemption), or jump to blocks no node can store or relay. Capacity and interval move at most by a factor of two per decision, and the interval stays at or above a quarter of its genesis value, which bounds chain growth, orphan risk and per-block state churn.

Every change supplies an exact `new` integer within these rules. All values fit u64. The node requires a 64-bit target. Genesis values other than block capacity are representability checks, not suggested operating values; `init` and `run` warn about unsafe ones without rejecting them ([specification](SPECIFICATION.md)). A one-block genesis decision resolves on the first subsequent block, before a conditional trade can affect its result.

The effective auction timeout is `max(auction_timeout, lead + interval)`, with checked addition. The scheduled clock and every deadline use checked u64 arithmetic. A Propose transaction is checked at the including block's clock. The projected decision/rest activation boundary is checked whenever the proposal would lead or open its decision, and failure cancels it rather than invalidating the Propose. Activation checks the value again. Rounding a phase duration up to a block boundary must also fit. A value that fits u64 can therefore still be invalid at a particular clock. The product of the decision block count and frozen interval, the end height and projected deadlines must fit. A governed change must also stay representable through every remaining height: at each check, `clock + interval * (max_height - height) + effective_timeout + decision_blocks * interval + rest + 2 * interval` must fit u64 under the changed settings, computed exactly. The check uses the clock and height of the block that performs it: the including block for Propose, and the projected activation block (opening height plus decision blocks plus `ceil(rest / interval)`) when the proposal would lead or open, at activation and in state validation. Along an unchanged schedule each block adds one interval to the clock and removes one remaining height, so the sum is constant. Later phase deadlines therefore cannot overflow before the height limit. A genesis whose own sum already exceeds u64, because its clock range ends before its height limit, may still make a change whose sum does not exceed the sum under its current settings. As defence in depth, a rest deadline that would overflow saturates at 2^64 − 1: governance waits rather than every candidate block failing. Changes activate after the rest period under the frozen settings of their decision; the activating block still uses its parent's interval, and its child uses the new one. Existing signed anchors and lifetimes are never rewritten.

Auction leadership is evaluated once per block after its transactions. The incumbent keeps a tie with the highest bid; otherwise the ranking's last key leads, which is the highest bid and, among equal bids, the smallest proposal ID. A proposal that could not open its decision in that block is cancelled with `refund_height = height + 1` and skipped. Examples are an unfundable grant, an unrepresentable schedule or end height, and a parameter value invalid at its projected activation. It therefore never becomes leader or restarts another proposal's lead. When a strictly higher bid replaces an active leader, the old leader and its `lead_since` are appended to `displaced` (removing any earlier entry for it), and `lead_since` becomes the block's clock. A leader can be cancelled later, for example a grant made unfundable by sales. When the leader is cancelled, entries for cancelled proposals are dropped and the last remaining entry is the incumbent for the tie rule. If that proposal becomes leader it is removed from `displaced` and resumes its recorded `lead_since`; any other new leader starts at the block's clock. The leader opens its decision when `clock - lead_since >= lead` or `clock - opened >= effective_timeout`, provided it can open. Otherwise, at the timeout the round times out. If a mature leader is cancelled, `replacement_height = height + 1` and no leader is chosen until the next block. Rest completion is processed after auctions in the same block.

Transfers credit the signed exact amount. Recipient creation increases the required minimum fee, which the exact signed fee must cover. Proposal explanations are transaction data; the UI verifies their SHA256 against the signed description hash.

## Fees, capacity and issuance

Transaction weight is its signed byte length plus 1,024 for a new TransferExact recipient, or 1,024 per payout in a grant proposal. Grant payout weight is fixed, whether or not those accounts already exist. Every Propose adds `fees::RECORD_WEIGHT` = 1,024 for its proposal and first support record, and a Support adds it when `supports` holds no record under `support_key(round, proposal, sender)` before the transaction. Proposal and support records are never pruned, so they prepay their state like accounts. The fee quote reports this charge as `record_fee`, the rate times one 1,024-weight unit, or zero. The minimum fee is ceil(weight * minimum_fee_rate / 1024). The exact signed body.fee must meet this minimum and is charged in full. A transfer recipient created by a preceding transaction can reduce the required minimum and weight but does not reduce the signed payment. The presets start the minimum rate at one atom per 1,024 weight. A successful MinimumFeeRate proposal can lower the rate to any positive value in one decision, or raise it to at most twice the old rate (from zero, to one) and at most 2^16 times the genesis rate (2^16 from a zero genesis rate). Only genesis can choose a zero rate, which requires no minimum fee. Empty or full blocks do not change it. An optional extra is only an input to the quote builder; the signed record contains one exact fee, not a separate extra or cap.

The grant proposal prepays bounded settlement work. This transaction fee is not refunded if the proposal loses, expires or becomes ineligible, or if recipients obtain accounts before settlement. It is distinct from refundable auction support. Its miner share goes to the miner that includes the proposal, under the ordinary fee split; settlement does not deduct another fee from any grant amount.

For each transaction, miner_fee = floor(actual_fee * active_miner_fee_percent / 100); waiting revenue receives the remainder. The initial split is 50/50. The whole paid fee is split, including any extra. This transfers existing hashes; it does not create issuance.

BlockBytes bounds both measured body bytes and transaction weight, including prepaid grant payout weight. A new mining recipient contributes 1,024 weight without any deduction from its protocol payment. Mandatory grant settlement is exempt from this closing block's weight limit because its work was charged with the proposal. Its recipient count was bounded by the proposal’s byte and weight capacity when included. Ordinary payment-account creation and miner-account creation retain their capacity checks. During governance, one logical payment-account creation counts once. Presets start with 16 KiB of body/weight capacity. There is no separate recipient-count or transaction-size setting: a transaction may use the block’s remaining byte and weight capacity, including its signature, data and execution weight. Block framing and any mining-account creation also need capacity. Governance can double or halve BlockBytes per decision, within 4,096 through 64 MiB; independent signature-count limits still apply. Transport and API admission limits are separate service constraints.

For each block, physical expected work is W = floor(2^256 / (target + 1)). Production issuance uses Q = 10^15 expected hashes per atom. The block issues floor(W / Q) atoms; any smaller fraction is discarded. When W is only a few multiples of Q, as on private chains calibrated for low hashrate, this discards a large share of work-implied issuance (a third at W = 1.5Q) and makes reward per hash a sawtooth that favours W just above a multiple of Q, which header timestamps can nudge. Calibrate W far above Q. Total issued atoms are the sum of these independently rounded block rewards. A block below one petahash issues zero atoms. Losing blocks receive no reward. Fork choice still compares exact accumulated physical expected work, without monetary rounding.

## Accounts, reserve and governance

State uses persistent authenticated maps: a Patricia trie over hashed keys, with canonical roots independent of insertion order and shared immutable subtrees, plus an uncommitted index in key order (see [state commitments](#state-commitments)). Account updates copy changed paths rather than cloning all accounts. Depth does not depend on chosen keys: no entry lies under more than 256 branches, and pushing a key L levels below its natural depth of about log2(n) costs about 2^L hash evaluations. Account field order is ordinary:Amount, shares:Amount, nonce:u64, epoch:u64. Each outcome's cash is its ordinary field; there is no extra conditional balance field. Public-key bytes are the map key, not an extra account field.

The account `epoch` is internal bookkeeping for governance context. Each decision increments `last_epoch`; account reads normalize the returned tag to that decision's number, or zero outside a decision. Stored records retain the context used when written. Changing this tag does not change a balance, mint funds or perform the PASS/FAIL split: the two account-tree roots hold those alternatives. The field participates in the account commitment and its stored value cannot exceed `last_epoch`. It is not a Unix timestamp.

A deposit d into an empty reserve sets reserve = curve_mass = d and creates d * Config.share_scale stash for its sender. Ordinary trades then use the current dynamic ratio. Revenue adds min(revenue, curve_mass - reserve) to reserve without changing curve mass or stash; excess waits. All stash belongs to accounts. Config.quote_scale must be at least Config.share_scale so the initial nonempty curve has a nonzero integer price quote. An empty world quotes zero, and a block in which either governance world is empty adds no PASS lead; its next deposit opens at the configured exchange rate.

A governance decision starts with two roots referencing the same account state. PASS and FAIL each expose full balances automatically. Selected Stash trades affect that world's cash and shares; ordinary payments and fees debit both worlds. Therefore shared payment availability is the minimum of the two cash balances. Nonces and account keys remain coordinated. Alternative balances must not be summed.

Grant eligibility requires positive, representable payments whose total is at most waiting revenue plus `floor(reserve / 2)`. One grant can therefore at most halve either outcome's reserve ratio, and a live Stash reserve always retains at least one raw hash atom. At activation, PASS escrows that total from waiting revenue first and reserve second, keeping mass and stash unchanged. FAIL moves the same reserve amount into its own waiting revenue without escrow, so both worlds open with equal reserve, mass and supply. Only then does the winning support become waiting revenue in both worlds, so it never funds its own grant. Neither world replenishes its reserve from revenue while the decision is active; the selected world replenishes in its resolution block. Each subsequent block compares exact completed-parent marginal prices P = M_pass/S_pass and F = M_fail/S_fail. When both worlds hold Stash it adds one leading block when M_pass*S_fail*10000 > M_fail*S_pass*(10000+m), using the frozen margin m. If either world holds no Stash, the block adds no lead. Display quote rounding and quote_scale do not affect this comparison. Equality adds none. After decision_blocks observations, PASS requires leading_blocks > decision_blocks/2; a tie fails. Resolution selects the winning root and atomically pays every listed amount once if PASS wins. No recipient is paid before resolution or partially paid by a failed transition. No account-wide settlement rewrite occurs. Losing tree nodes remain reachable while retained checkpoints need them.

Amount-only Deposit and Redeem operations are reserved from opening balances and cleared together once per world. The signed fee is paid even on a zero fill. Unfilled inputs are returned. Exact rounded closing marginal prices respect MaxPriceChangeBps. No order identifier or transaction position selects a rounding beneficiary. [Batch clearing](SPECIFICATION.md#amount-only-block-clearing) defines price determination, proportional allocation, dust handling, the per-world limit of 1,024 curve evaluations and the remaining miner inclusion power.

Decision fields are id, epoch, round, proposal_id, proposal, started (scheduled clock), started_height, blocks, leading_blocks. The last three are u64. The proposal field is a copy of the winning action, which is committed once, in the actions map under proposal_id; the state root's phase commitment therefore omits it (see State commitments). The opening height plus blocks is the resolution height; the observation occurs before that block’s transactions. The decision ID is tagged_hash("Hashstash/decision", encode((chain_id, round, proposal_id, started_height, parent_hash))). Here parent_hash is the block hash of the opening block's parent. Anyone who knows that parent and the maturing leader can compute the ID before the opening block exists, and same-parent siblings share it.

A proposal ID is tagged_hash("Hashstash/proposal", encode((chain_id, round, proposer, description, proposal))), where proposer is the sender of the registering Propose. Proposal record fields are round, proposer, description, support, refund_height. Registration also writes the proposal (its action) once into the actions map under the same ID; nothing updates it later. Support and cancellation rewrite only the record, so their hashing work does not depend on how many payments a grant lists. A sender can register a given ID once; an identical Propose from another sender registers a separate proposal, so copying a pending Propose cannot invalidate it or replace its attached data.

## State commitments

World root is tagged_hash("Hashstash/world", encode((accounts.root(), reserve, shares, revenue, grant_escrow, curve_mass, account_cash, account_shares))). Each dynamic curve field is committed.

The state root is tagged_hash("Hashstash/state", encode((A,B))). A contains chain_id, height, clock, issued, settings, frozen, world.root(), optional alternative.root(), phase commitment. Clock is cumulative scheduled seconds. The phase commitment encodes the phase with its own tags and fields, except that a Governance decision omits its proposal field: id, epoch, round, proposal_id, started, started_height, blocks, leading_blocks. B contains proposal/action/support/round/ranking roots, auction_escrow, last_round, last_epoch. Field and tuple ordering is consensus-critical.

Map domains are Hashstash/TriePath, Hashstash/TrieLeaf, Hashstash/TrieBranch and Hashstash/TrieEmpty. Protocol roots commit to authenticated map roots rather than their in-memory representation. All changes, including fees and protocol payments, must reproduce the declared state root.

Each map is committed as a binary Patricia trie over hashed keys. A key's path is the 256-bit tagged_hash("Hashstash/TriePath", key), read most significant bit of its first byte first. The empty map's root is tagged_hash("Hashstash/TrieEmpty", ""). An entry's leaf is tagged_hash("Hashstash/TrieLeaf", encode((key, value))), where key is a length-prefixed byte vector; a map with one entry has that leaf as its root. Otherwise the root is a branch at the first bit b in which the entries' paths differ: tagged_hash("Hashstash/TrieBranch", b || left || right), where b is one byte (0 to 255), left is the root of the entries whose path has a zero at bit b and right that of the others, each computed the same way. The trie of a key set is unique, so roots do not depend on insertion order, removals or snapshot restoration.

### Design note: key-independent state depth

The previous commitment, a treap whose priorities were public hashes of the keys, let anyone who chose keys (account public keys, proposal IDs, support keys) build one arbitrarily deep, permanent path, and every update on it copied and rehashed one node per level. The trie removes that dependence at the commitment itself rather than capping or pricing depth, which would have let an attacker block a key range or still left paths unbounded:

- Each branch tests a later path bit than its parent, so no entry lies under more than 256 branches whatever the keys.
- Paths are hashes, so n honest keys sit about log2(n) branches deep. Placing a key L levels deeper than that needs a path that shares about L more leading bits with an existing one, which costs about 2^L hash evaluations. Practical depth is therefore about log2(n) plus the logarithm of the attacker's hash budget: under 100 levels against 2^64 work.
- Hashed paths have no useful order, but consensus needs key order: the highest `ranking` key selects the auction leader, snapshots list entries by key, and audits and the RPC proposal index iterate in key order. Each map therefore also keeps an uncommitted index of the same entries ordered by key bytes. It is a weight-balanced search tree, so its height is logarithmic in the number of entries for any keys and insertion order. Its shape depends on history and may differ between nodes, but no result depends on that shape: lookups, ordered iteration and the greatest key are functions of the entries alone. The index is not hashed.
- Entries, both structures and their nodes are immutable and reference counted. Cloning a map is constant time; an update copies one trie path (at most 257 nodes, one hash each) and one index path, and shares stored values with earlier versions. The snapshot encoding is unchanged: entries in strictly increasing key order, from which a node rebuilds both structures in one pass.

## Mining wire format

The Bitcoin-style header is 80 bytes: version:u32 at offset 0, previous digest[32] at 4, Merkle root[32] at 36, timestamp:u32 at 68, bits:u32 at 72, nonce:u32 at 76. Integers are little endian; digest bytes are raw. Fixed version bits are 0x20000005, with rolling mask 0x1fffe000. Outside that mask the version must match exactly.

The sole Merkle leaf is a Bitcoin-serialized system coinbase. It has transaction version 1, one zero-prevout input (index and sequence 0xffffffff), a minimally encoded height plus PUSH8 and eight extranonce bytes, one zero-value output, and locktime 0. The height is a Bitcoin script-number push, as `CScript() << height` builds it: OP_0 (0x00) for 0, OP_1..OP_16 (0x51..0x60) for 1..16, and otherwise a length byte followed by the minimal little-endian magnitude, with a 0x00 byte appended when its top bit is set. For example 17 is 01 11, 128 is 02 80 00 and 32768 is 03 00 80 00; a length-prefixed push such as 01 05 is not valid for heights 1..16. Its output script is OP_RETURN, PUSH68, ASCII HST!, miner key[32], commitment[32]. The commitment is tagged_hash("Hashstash/block-commitment", encode((transactions,state_root))). There is no optional proof field or padding. Coinbase transaction counts and script lengths use canonical CompactSize.

The header Merkle root is SHA256d of this coinbase, so Stratum supplies an empty Merkle branch. The complete ordered signed transaction vector is bound inside the commitment. Verifying that commitment needs the full vector; it does not provide short transaction-inclusion proofs.

The governed body measurement is state_root[32], CompactSize record count, and each record's CompactSize length plus complete bytes. Records are the coinbase followed by user transactions. The 80-byte header is excluded. Binary block record field order is header, height:u64, miner[32], state_root[32], extranonce[8], transactions. The extranonce is exactly eight bytes without a length prefix. The binary record's Header integers use the compact serializer; proof of work always hashes the separately constructed fixed 80-byte header specified above. Validators reconstruct all redundant commitments. Bitcoin CompactSize framing remains distinct from the compact integer encoding of consensus records.

## Timestamps, difficulty and forks

Proof of work compares the little-endian SHA256d header digest with a canonical positive target no easier than genesis limit_bits. Each branch derives cumulative scheduled seconds S_h = S_(h-1) + parent_settings.interval. Its first mined block supplies the anchor scheduled seconds S_1. The anchor timestamp T_1 is max(block_1.timestamp, block_2.timestamp - parent_settings.interval), fixed by the branch's second block; the first block's entry uses its own timestamp. For a child of a non-genesis parent, error = (parent.timestamp - T_1) - (parent.expected_seconds - S_1). Ideal target is initial_target * 2^(error/daa_half_life), using the fixed-point integer ASERT approximation, compact rounding and target limit. The first two blocks use initial_bits, and the third block's error is at most zero: time before mining began is excluded even when the first block's timestamp is backdated toward genesis. A miner producing both of the first two blocks can still backdate them; `init --hashrate` bounds the resulting easing by setting limit_bits to 256 times the calibrated initial target. An interval change modifies future schedule increments without resetting the anchor. Competing branches retain their own first-block anchors; reopening reconstructs these from validated history.

Timestamp must exceed median past time and must not exceed local now + future_seconds. Median uses available ancestors including the parent, capped by timestamp_window, sorted at index length/2. Future blocks remain retryable. Because the header timestamp is u32, no block can follow once median past time equals u32::MAX (2106-02-07 06:28:15 UTC); templates then fail with "timestamp exhausted". This is the protocol's lifetime limit. Time checks reduce but do not eliminate timestamp manipulation. Header time affects ASERT, while governance phases advance by the target interval, independently of the candidate timestamp. Transaction expiry is measured in blocks after its signed anchor; timestamp samples and confirmations retain their count units.

The greatest-work valid branch becomes active; equal-work arrivals retain the current tip. Local side-branch admission may hold a far-behind branch's headers until they prove more work than the tip before its blocks are validated ([network controls](NETWORK-HARDENING.md)); that delays, but does not change, the greatest-work choice. Reorganization replaces all affected state, issuance, fees, funding and decisions together. Accepted block bodies and checkpoints allow reconstruction; governance resolution gives no finality. SQLite commits block/tip changes atomically, and the node publishes tip and state together. Mempool recovery revalidates anchors, lifetimes, nonces, funds and decision bindings. Chain validation checks ancestry during admission, block validation, template construction and historical replay. The pure economic execution helper checks transaction structure and state transitions; callers must supply chain validation for ancestry and proof of work.

## Bounds and genesis

Genesis is a deterministic unmined height-zero anchor with zero cumulative work and issuance, empty accounts, reserve and revenue, eight zero extranonce bytes and no transactions. It commits the full configuration and an initial Rest state ending at initial.rest scheduled seconds, or opens auction round zero immediately when initial.rest is zero. Proposal rounds begin through normal transitions. Its zero miner is not a payable account. Mining validation starts at height 1.

Maximum configured height is positive and at most i64::MAX, matching the database height representation. Nonces, phase clocks and deadlines use checked u64 values. Config validates amount ranges, share ranges, bounded curve arithmetic, lifetime issuance and price-comparison capacity. Canonical records are bounded by their actual encoded bytes, configured field ranges and the including block’s byte/weight capacity. BlockBytes is at most 64 MiB, so every valid block fits the peer frame's u32 length, the HTTP response limit for its hexadecimal record, the Explorer's stored-record bound and SQLite's 1e9-byte row limit. A node whose SQLite build cannot hold a 65 MiB row refuses to open its chain database instead of rejecting a valid block its peers accept. Other peer frames and API responses keep their own service limits. These bounds constrain representability and work; they do not guarantee economic outcomes or constant validation latency.

Fields, enum tags, hash domains, rounding and coinbase construction are consensus rules. See [validation](VALIDATION.md) for tested scope, and [network controls](NETWORK-HARDENING.md) for limits that are node policy rather than consensus.

Peer transport framing is separate from consensus records. Binary peer messages carry canonical transaction and block bytes. Their chain identity and record domains must match this protocol.
