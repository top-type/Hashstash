# Solo mining

Hashstash exposes optional Stratum V1 for SHA256d ASICs. Mining configuration belongs to the node operator. Wallet selection and the public UI cannot change the payout identity or start software mining. A Stratum username is only a worker label: every accepted block pays the node's configured public key or address. Pool share accounting and multi-user payouts are not implemented.

```sh
hashstash run --config network.json --data chain.sqlite --miner '<address>' --rpc 127.0.0.1:18480 --p2p 0.0.0.0:18481 --stratum 0.0.0.0:18482 --stratum-share-difficulty 65536 --stratum-advertise example.net:18482 --stratum-password-file mining-password
```

`--stratum-advertise` takes a bare reachable `HOST:PORT`; the interface adds the `stratum+tcp://` scheme, and startup rejects a value containing one.

`--stratum-password-file PATH` requires its password at authorization. The file holds one printable ASCII token of at most 256 characters; trailing line endings are ignored and an empty file is refused. It is mandatory when Stratum binds a non-loopback address, including `0.0.0.0`; otherwise anyone reaching the listener could authorize and hold its worker slots. Restrict file access and never put credentials into a public endpoint. `--no-stratum` runs a validating/relaying node without a mining listener. Keep private RPC loopback-only. The public browser page exposes mining status under Explorer → Network, without administrative controls. Public-web responses keep the password requirement and worker statistics, but omit the Stratum bind address and loopback flag. They keep the connect URL only when it was given with `--stratum-advertise`. A connect URL derived from a specific bind address would publish that interface, so public responses report it as `null`. The private listener still shows it.

For a fresh network, `init --preset slow --hashrate 100T` calibrates initial work to estimated hashrate. It also sets the easiest permitted target to 256 times the calibrated one, so a stall or a backdated start cannot make blocks practically free; difficulty then cannot follow a hashrate collapse of more than 256-fold. Each block issues only whole atoms of one petahash of expected work, so 100 TH/s at 15-second blocks (about 1.5 PH per block) discards a third of work-implied issuance. Reward per hash then jumps at each whole petahash, a weak incentive to nudge timestamps toward work just above a multiple. About 7 PH/s or more at 15 seconds keeps the loss below 1%. The resulting configuration fixes a new chain identity; do not edit the genesis of a running chain. ASIC work on an extremely easy development target can overwhelm a small node. The three presets alone do not establish production safety: uncalibrated, their easiest target needs about two hashes per block. `init` therefore requires `--hashrate` for the slow preset (or an explicit `--uncalibrated`), `init` warns about any genesis whose easiest target needs fewer than 2^32 expected hashes per block, and `run` refuses a non-loopback `--p2p`, as in the example above, or `--peer-discovery` on such a network unless `--allow-easy-target` is given. Because calibration eases the limit 256-fold, that takes at least 2^40 expected hashes per block: `--hashrate 73.4G` or more at 15-second blocks. The development `mine` RPC, which CPU-mines through the node, runs only on such development networks while no untrusted peer can reach the node (or on fixture ones) unless the node was started with `--dev-rpc`; ASIC mining always uses Stratum.

## Reporting shares and block rewards

Share difficulty is a reporting threshold, not block difficulty or a payout contract. The assigned reporting target is capped at the network difficulty so valid blocks can be reported. Each job retains its own assigned difficulty. `mining.suggest_difficulty` respects the configured reporting floor before that cap. The node measures each connection's valid reporting shares at its current difficulty in samples of at least 16 share intervals. A sample that has spanned 30 seconds and averages more than two shares per second multiplies the reporting difficulty for new jobs by the largest power of two that keeps the rate at or above one per second, so random clustering of shares does not raise a miner near that rate. A stream faster than eight shares per second, the per-session request rate, is raised without waiting for 30 seconds: its rate is measured over at least the two seconds that 16 intervals take at the session rate, and it is raised by at most eight times at once. Shares that arrive together, from a proxy that batches them or a connection that stalled, therefore raise difficulty at most eightfold, and only a stream that keeps arriving faster is raised again. Difficulty raised above the floor, or above what the miner last negotiated with BIP310 minimum difficulty or `mining.suggest_difficulty`, halves again for new jobs while the connection's valid shares average fewer than one per two seconds (half the target rate) over at least two minutes, so a miner raised by such a batch returns to its own difficulty. Shares a fast miner sends past the session rate in the meantime get a rate-limit error instead of a disconnect, and a block among them is still submitted. A miner that keeps ignoring the new difficulty is disconnected once its overrun allowance is spent. BIP310 minimum-difficulty requests are accepted only if compatible with the easiest representable network target; otherwise they return false.

Only canonical blocks earn issuance. Each block contributes floor(2^256/(target+1)) physical expected hashes. The block issues one atom (0.001 hash) per whole petahash of expected work and discards any smaller fraction. A low-work block can therefore issue zero atoms. Losing-parent jobs are rejected; losing blocks cannot later earn rewards. Transaction fees transfer existing hashes: the miner receives the governed percentage of each entire actual paid fee and revenue receives the remainder.

Accepted/rejected shares, workers and estimated hashrate are local statistics and reset on process restart. A found block may be removed by reorganization. Worker labels and counters do not authenticate hardware or geographical location. Short hashrate estimates are noisy.

## Time and wire format

Timestamp ASERT uses a default 15-second interval. Governance may set a positive whole-second interval of at most the ASERT half-life. A longer interval must also keep the current auction lead and decision length within their governed limits, and the scheduled clock and deadlines must stay representable. The presets fix a 900-second half-life, 11-header median and 120-second future allowance. Each timestamp must exceed its parent median and remain within the future allowance. ASERT starts from each branch's first mined blocks, so an unmined genesis can wait without creating a difficulty catch-up period. The anchor is the later of block 1's timestamp and block 2's timestamp less one interval, so a backdated first block alone does not create one either. The first two blocks use the initial target. Later target changes preserve the accumulated branch schedule. Auction lead and rest use scheduled seconds, advancing by the parent's target interval per block. Decisions last a fixed number of blocks and count which completed parent prices lead. Revenue replenishment has no time schedule. Changing the interval preserves auction and rest durations in scheduled seconds; decision length, transaction lifetimes and confirmation counts remain block-based. Header timestamps do not determine these phases.

The 80-byte header has fixed version 0x20000005 and rolling mask 0x1fffe000. The sole coinbase leaf contains HST!, the payout key and a commitment to ordered transactions plus resulting state. Stratum sends an empty Merkle branch. Four-byte server extranonce and four-byte worker extranonce fill the eight-byte input slot. Nonce, valid nTime, extranonce and negotiated version bits may be rolled without recomputing the account transition. The [consensus format](CONSENSUS.md) gives exact encodings.

Supported methods are mining.configure, mining.subscribe, mining.authorize, mining.submit, mining.extranonce.subscribe and mining.suggest_difficulty. New tips replace active work immediately. Pending transaction changes refresh the shared cached template, which the node builds outside its state lock, one build per parent. After a change on the same parent, the previous template, still a valid block, is served until as long as its build took has passed since it finished; connections then receive the rebuilt one. A connection receives at most one same-parent refresh every two seconds, and changes that arrive while its refresh is scheduled are folded into that refresh, with periodic refresh as fallback. A new tip's template is built at once: a build still running for the old tip neither delays it nor holds a mining worker, and stops at its next step. While new tips keep overtaking a request's builds, as during catch-up, the request is served an empty template for the current tip after three of them, and the connection receives the full template at its next refresh. Each connection retains its eight most recent active-tip jobs. A same-parent refresh retires only the oldest job and does not set `clean_jobs`, so transaction churn alone retires a job no sooner than 16 seconds after it was issued. Duplicate headers across job IDs are rejected.

BIP310 negotiation fixes the exact version mask for six-field submissions. For proxies that never request version rolling, submissions may contain an optional sixth version-bits field within the fixed `1fffe000` mask. An explicit failed request disables this fallback. All submitted bits enter the reconstructed header and its proof-of-work check; bits outside the applicable mask are rejected.

Connections, validation workers, traffic, parsing, jobs and duplicate tracking are bounded. Authorization must finish within 10 seconds; letting it lapse closes the connection. Connections awaiting authorization use separate slots, so they cannot occupy the 64 authorized worker slots. The time each waits is charged to its address however it closes, and addresses that recently authorized keep reserved slots, so the operator's miners can reconnect while other sources crowd the general slots. Those addresses are saved beside the chain database and kept across restarts, and `--stratum-trusted ADDRESS[/LENGTH]` names further addresses or prefixes that always qualify. Outside local networks (loopback, private, CGNAT, link-local and unique-local) such a prefix must be at least /16 for IPv4 or /32 for IPv6, because a broader one would treat much of the internet as the operator's miners; `--stratum-trusted-broad` names a broader prefix deliberately. Valid non-block shares are acknowledged without full block execution. A solved block always reaches validation on its own validators, never behind mining workers or template builds: busy parsers and validators delay it rather than discard it, budgets and rate limits are enforced after submission, and an address cooldown caused by another connection does not end an authorized worker's requests. A valid block that loses a race with a competing block on the same parent is reported as a stale job and is not counted as found. See [network controls](NETWORK-HARDENING.md).

Anyone holding the mining password can authorize, so the 64 authorized worker slots are shared out rather than first come, first served. Workers from sources outside the `--stratum-trusted` prefixes hold at most 16 from one IPv4 /24 or IPv6 /48 (an address on a local network is its own group), and when the operator trusts any prefix, at most 48 slots in all: the other 16 stay free for trusted prefixes, which may use every slot and have no group limit. An authorized solo worker may wait for a block without submitting a reporting share. When the slots a newly authorized worker may use are full, it replaces the competing worker that has gone longest without a valid share, once that is at least five minutes since that worker's last valid share or block, accepted or refused for a rate limit, or its authorization, and the replaced connection closes: a source outside the trusted prefixes replaces only such a worker from outside them (from its own group when that group is full), and a trusted source replaces one from outside them first and an idle trusted worker only when no other is idle. Otherwise the newcomer is told that worker capacity is reached. A worker from outside the trusted prefixes does not start a fresh five minutes while its group already has workers that have sent no valid share: it counts as idle from the earliest authorization among them, including those that closed or were replaced, until an hour after the last of them left. Reconnecting, or replacing its own idle workers, therefore never keeps a group's slots: five minutes after the group's first such worker authorized, a newcomer from another network can replace any of them. Miners that report shares are never replaced. A leaked password still lets its holder take slots that are free or idle; holding them without work takes another /24 or /48 for every 16 slots every five minutes, each unused for the hour before. Only `--stratum-trusted` guarantees slots: once it names a prefix, 16 are reserved for trusted prefixes, and other sources never take them. Rotate a leaked password with the node's password file and a restart. A trusted worker, once authorized, also stops counting toward its address's 16 connections and its /24's 64, and its lines pay only its own session limits, so a rental marketplace that opens one connection per rig from one proxy address can connect more than 16 rigs when its addresses are trusted. Other authorized workers share their address's and /24's request, byte and work budgets with every connection from there; when other sources have exhausted them, the worker's shares are refused with a rate error and its blocks are still submitted, but its connection stays open. A forwarder that makes every miner arrive from one address, such as a loopback port forward, puts them all in one group and one budget unless that address is trusted; give rentals the node's own address instead.

One connection may authorize up to 64 worker names, each with the password, as proxies do for the miners behind them, and keeps one worker slot; statistics are reported under its first name. A share under any authorized name is accepted, and proof of work is checked before the name, so a solved block is submitted whatever name it carries. Each node starts its four-byte extranonce counter at a random value, so two nodes that pay one key and serve the same template, or one node before and after a restart, do not give their first miners identical work. Still, give each node its own payout key.

## Verification

`python scripts/test_stratum_wire.py` starts a disposable loopback node, independently constructs HST! coinbases and headers, submits reporting shares and blocks, and checks commitment, fees, canonical issuance, timestamp changes, losing-parent rejection and restart persistence. This is a software wire check, not evidence of every ASIC's compatibility. Run `cargo test --locked --test stratum_shares --test mining_adversarial` for bounded-session and competing-work tests. See [validation](VALIDATION.md) for completed results.
