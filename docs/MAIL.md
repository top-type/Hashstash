# Recipient-hidden encrypted mail

Mail is a browser application over signed transaction data. Any valid transaction carrying a mail envelope in its signed `data` bytes can carry an encrypted message, independently of its public action. A payment may carry private instructions to its payee, and a Stash trade, proposal or other action may carry mail for any chosen key. The standalone Mail composer uses a positive `TransferExact` **to itself**, returning one raw atom to the sender and paying the ordinary network fee. That convenience sends no coins to the message recipient. There is no new consensus operation or account field.

## Discovery

Every Mail client reads the same bounded, chronological `explorer_mail` stream. Mail discovery requests contain no account address or recipient filter. This does not make all wallet traffic anonymous: ordinary account and snapshot queries still identify selected wallet keys to the connected node. Nearly every envelope belongs to someone else, so the browser first attempts authenticated decryption locally under the feed’s stated sender, nonce and network; an unwrap that fails costs no signature check. Only an envelope that opens is then verified, before it is displayed or checkpointed: the browser verifies the canonical signed transaction and its BIP340 signature, checks the transaction ID, and binds the feed’s sender, nonce, ciphertext and public operation to those signed bytes. The signed anchor is part of the verified record; canonical inclusion and anchor ancestry are checked by the connected node, not established by unsigned feed context. A row without its signed record, or an opened envelope whose signature or details do not match, stops the page without advancing the saved cursor. Wrong-key decryption failures are ordinary and silent. A feed that alters an envelope’s stated sender, nonce or ciphertext makes it fail to open and so can hide that message, as it can by leaving the row out; it cannot attribute a message to a key that did not sign it. Watch-only accounts cannot discover incoming messages; they can prepare outgoing ciphertext for offline signing. The cold signer verifies the public transaction action, fee and ciphertext but cannot inspect the hidden message or intended recipient.

Scanning runs only while Mail is open with a local signing wallet. It uses bounded pages and rests for a quarter second after every 100 candidate envelopes, then continues on its own; Pause scan stops it and Continue scan resumes it. A long history or a burst of envelope spam therefore costs scan time, not repeated clicks. Clear saved mail scan removes the current account’s checkpoint and cached ciphertext. Each browser stores an atomic checkpoint and the signed public transaction bytes of successfully opened messages for each chain and account; plaintext and keys are never written to the Mail cache. Restoring the cache rechecks each transaction signature and derives sender, nonce and ciphertext from the signed record before decryption. Unsigned cache checkpoints are not reused. The saved canonical anchor is checked with the connected node before restoration. The cache holds at most 256 messages and 2 MiB. Anyone can send an address that many messages, so a full cache does not stop the checkpoint: the newest messages that fit are saved, the older ones (and any single carrier transaction too large to cache) are left out and counted, and the checkpoint still advances. A later visit shows the saved messages and reports how many earlier ones are not kept in this browser; Clear saved mail scan and a rescan from the beginning show them again. If browser storage itself is exhausted or unavailable, the last complete checkpoint is retained and the UI explains that later progress exists only for this visit. Local cache metadata reveals which ciphertext the local account opened, and a recorded start the block at which the wallet was created, to anyone with access to browser storage. A canonical anchor check protects continuation across chain changes. When the node reports the height above which the anchor's blocks were replaced, the browser drops only messages above that height and continues from it; an unknown or deeply replaced anchor restarts discovery from genesis. Either way messages from the replaced history are removed. Wallet, node-session and network changes cancel work and clear visible plaintext and drafts.

When this browser creates a wallet it records the tip it was created at, and that account’s first scan starts in the next block: nobody can have sent mail to a key that did not exist yet. The recorded block anchors the start and is checked with the node like a saved checkpoint, so a reorganization below it rewinds the scan to the fork. Mail settings can also set the first block to scan, for example for an imported key whose history is known (the current tip anchors that choice), and offer an explicit scan from genesis. Each start is stored per chain and account beside the checkpoint; Clear saved mail scan returns to it rather than to genesis. No creation height is guessed for imported or existing wallets: without a recorded or chosen start, the first scan begins at genesis. A start whose anchor the node does not know is dropped and discovery restarts from genesis. No discovered-message fetch, automatic read receipt, remote image or plaintext RPC is used.

## Privacy boundary

Recipient, subject and body are encrypted. There is no public message-recipient identifier or recipient-derived filter tag. Every supported envelope has the same byte length, hiding text length within this format. The publishing account, public transaction action (including any payment recipient and amount), fees, inclusion timing, network activity and fact that this is mail remain observable. The encrypted recipient is independent of the public payment recipient; choosing the same person for both can reveal that relationship. Replies, other payments or behavior can reveal relationships. Fees charge for chain use but do not guarantee spam prevention.

Ciphertext is permanent. Static account-key compromise exposes historical sent and received mail: this format **does not provide forward secrecy**. A compromised browser or wallet-serving site can expose keys/plaintext. Global scanning does not conceal a visitor's IP address or remove trust in RPC completeness. Local signature verification proves that the publishing key signed the transaction; it does not independently prove block inclusion, confirmation counts or the node’s reported canonical history. This application protocol uses established primitives but has not received an independent security audit. It makes no sender-anonymity claim.

## Envelope and encryption

The current format is `hashstash.mail/2\n` followed by compact canonical JSON with fields in this exact order:

```json
{"ephemeral_key":"<32-byte hex>","iv":"<12-byte hex>","ciphertext":"<1168-byte hex>","recipient_iv":"<12-byte hex>","recipient_key":"<48-byte hex>","sender_iv":"<12-byte hex>","sender_key":"<48-byte hex>"}
```

The recipient_key and sender_key fields are encrypted content-key wraps, not account public keys. All hex is lowercase. Duplicate/unknown/reordered fields, noncanonical JSON, invalid curve points and wrong lengths are rejected. Every supported envelope is exactly 2,793 bytes, within the 3,072-byte parser limit and ordinary transaction limit. Chat excludes mail envelopes.

The pinned Noble secp256k1 implementation handles curve operations; Web Crypto supplies HKDF-SHA256 and AES-256-GCM. ECDH normalizes private scalars to the even-Y representative of their BIP340 x-only key and lifts peer keys to even-Y points. The shared secret is the resulting point's 32-byte x coordinate.

Each message generates a fresh ephemeral scalar, random 32-byte content key and three random 12-byte GCM nonces. Canonical encrypted JSON is ordered recipient, subject, body. A two-byte big-endian JSON byte length precedes the JSON, with zero padding to exactly 1,152 bytes. AES-GCM adds a 128-bit authentication tag, producing 1,168 ciphertext bytes.

Subject is 1-96 UTF-8 bytes and body 1-768. Both need non-whitespace content. Newline/tab are accepted; malformed Unicode and other controls are rejected. JSON escaping must also fit the padded bound. The inbox renders decrypted text as plain text and shows explicit bidi embeddings, overrides and isolates (U+202A–U+202E, U+2066–U+2069) as visible `\u202e`-style escapes, so a subject or body cannot display in a different order from its encrypted bytes.

Common authenticated data concatenates UTF-8 `Hashstash/Mail/v2\0`, chain ID, sender public key, eight-byte little-endian transaction nonce and ephemeral public key. All public keys and the chain ID occupy 32 bytes. The intended recipient is absent. Browser nonces use canonical unsigned-64-bit decimal strings; nonce changes invalidate prepared ciphertext and fee quotes.

Each role (recipient or sender) derives ECDH with its public key and the ephemeral scalar. HKDF uses the chain ID as salt and `Hashstash/Mail/v2/<role>\0`, common authenticated data and the role's candidate public key as info. A decrypting client derives its candidate from its own key without a lookup. The resulting AES key wraps the content key using authenticated data equal to common data followed by `/<role>`. The sender wrap enables sent-mail recovery, including the encrypted recipient.

Decryption authenticates both wrap and content before validating canonical JSON, length, zero padding and the encrypted recipient. Readable UTF-8 never establishes delivery. The outer transaction signature authenticates the publisher and binds operation, fees, nonce, anchor block, lifetime and ciphertext. Different chain/sender/nonce invalidates decryption; ordinary account nonces prevent transaction replay.

## Discovery API

`explorer_mail` accepts limit (at most 50) and optional paired after/anchor. The after value is an ascending height:position cursor; anchor is the canonical block hash from the prior scan. Results contain confirmed messages, next_cursor, scan_cursor and chain/tip/readiness/indexed-height context. At the end scan_cursor advances through the indexed height, including empty blocks. Pending mail is not indexed for discovery. Address filters are rejected.

The derived index rebuilds from every canonical transaction whose data decodes as a supported envelope. Reorganizations remove detached entries. Records contain `raw` (the complete canonical signed transaction in hexadecimal), sender, signed ciphertext context, `kind` and the unwrapped public `operation`, with no mail-recipient field. A derived-index schema change rebuilds older rows from canonical history so every result includes the signed record; it does not change consensus or the mail envelope. Applications can read a payment's amount and destination from `operation.TransferExact` and reconcile it with `explorer_transaction {"txid":"..."}`, which includes full ciphertext and confirmed/orphaned/pending status. Indexing is derived metadata: consensus still validates the transaction action and signature, and mail clients authenticate the encrypted contents locally.

## Verification

Browser crypto tests and an independent Node/OpenSSL implementation cover sender/recipient/self delivery, x-only scalar representatives, wrong keys, authenticated malformed padding, tampering, context binding and fixed lengths. UI tests cover global pagination, cancellation, account/reorg isolation, local directory resolution, ciphertext-only standalone mail and encrypted attachments on other transaction forms. Sender-verification tests use real signed records. Rows without a signed record are rejected before decryption; an opened envelope with an altered signature, a forged sender, a wrong transaction ID or a mismatched operation is rejected before display or checkpoint advancement; altered sender, nonce or ciphertext metadata and a wrong feed network context make an envelope fail to open; and an envelope that does not open is never signature-checked. Start tests cover the start recorded at wallet creation, a chosen first block, a genesis rescan and an unknown start anchor. Cache tests cover account isolation, atomic checkpoints, storage bounds, obsolete unsigned checkpoints and restoration failures. Large-grant mail tests preserve complete signed records across bounded pages. A disposable localhost wire scenario uses published fixture keys to sign, confirm, globally discover and decrypt a real transaction.

## Transaction attachments

Payment, Stash, proposal, support and refund forms offer public text or an encrypted message. Encrypted attachments use a full recipient address and never look that recipient up on RPC. Payment recipient and mail recipient are independent. During proposals, an encrypted message replaces the public description and its ciphertext is committed by the proposal description hash; the proposed action stays public. The transaction signature binds its public action and the complete ciphertext.
