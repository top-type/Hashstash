# Node operation

The node requires a 64-bit target. Genesis identifies the chain. A database must use its exact genesis configuration; changing that configuration creates a different identity, affecting addresses, application caches and chain-scoped faucet ledgers. A database also records the storage format of the release that wrote it (`hashstash-storage-043` since 0.43.0). The same genesis file gives 0.42.0 and 0.43.0 the same chain ID, but their blocks are incompatible, so a database holding blocks written by 0.42.0 or earlier is refused at startup with an error naming that release; start this release with a new `--data` path. Launching a new network is described in the [launch runbook](LAUNCH.md).

Source builds place executables in `target/release`; packaged releases place them in `bin`. The PowerShell launchers prefer the source build when present. Examples using `bin` assume the packaged layout.

```sh
hashstash init --config network.json --preset slow --hashrate 100T
hashstash keygen --out miner.key
hashstash run --config network.json --data chain.sqlite --miner PUBLIC_KEY --rpc 127.0.0.1:18480 --p2p 0.0.0.0:18481 --stratum 0.0.0.0:18482 --stratum-password-file mining-password --peer-discovery --seed SEED_HOST:18481 --advertise-peer YOUR_PUBLIC_IP:18481
```

`init` records this computer's clock as `genesis_time` and prints it in UTC. Block 1 must be later than genesis, so a fast clock delays the first block on every correctly clocked node; check the clock or pass `--genesis-time UNIX_SECONDS`. `init` warns about a genesis time beyond the network's future-time allowance.

`--hashrate` is the expected aggregate SHA256d hashrate of the network's miners. It calibrates the initial target and sets the easiest permitted target 256 times easier than that (see [mining](MINING.md)). The presets alone keep a development limit of about two hashes per block, at which a stalled or backdated chain makes blocks, side-branch admission, header presync and every other proof-of-work-gated defence practically free. With `--preset slow`, the preset for shared networks, `init` therefore refuses to run without `--hashrate` unless `--uncalibrated` keeps that limit, and `init` warns about any genesis whose easiest target needs fewer than 2^32 expected hashes per block. A calibrated limit is 1/256 of the calibrated work, so it clears that bound only from 2^40 hashes per block: at 15-second blocks, `--hashrate 73.4G` or more. A smaller calibrated network is still flagged, and the warning names that minimum. `run` refuses to accept untrusted peers on such a network, through a non-loopback `--p2p` or `--peer-discovery`, before opening the database; `--allow-easy-target` runs it anyway, with a warning. Loopback nodes with configured `--peer` endpoints, and fixture (`test_work`) networks, which need a test build, are unaffected. `run --preflight` makes every check `run` makes before opening the database and then exits without opening it or binding a listener; the [Linux installer's](../deploy/linux/README.md) `--check` uses it.

The Stratum password file must contain one printable ASCII token of at most 256 characters, as the Linux launcher requires; `run` refuses an empty or malformed file, and refuses a non-loopback Stratum listener without one before opening the database. `run` warns when `--public-web` binds a non-loopback address, because that listener serves plain HTTP.

The node needs only the public mining key. Keep any private backup inaccessible to untrusted users. `--no-stratum` disables the mining listener without disabling validation or relay. Mining payout and listener/password/reporting settings are operator configuration, not wallet controls. See [mining](MINING.md) and [Linux deployment](../deploy/linux/README.md).

`--wallet-key PATH` and `--watch-key ADDRESS` are mutually exclusive opt-in server-wallet modes for private operator tooling. Without them the server wallet database starts empty. `--wallet-passphrase-file PATH` names an owner-only file whose passphrase encrypts that database's hot keys; once a start has used it, the database opens only with it (see [node wallet passphrase](WALLETS.md#node-wallet-passphrase)). Browser wallets are independent and sign locally. The separate cold signer requires no node connection to review/sign exported transactions. See [wallets](WALLETS.md).

## API boundaries

Private JSON-RPC is POST `/rpc`, envelope `{jsonrpc:"2.0",id,method,params}`. RPC must bind loopback. Public-web mode exposes an allowlist of reads and signed-transaction submission without server-wallet management, secret material, software mining, configuration changes or arbitrary private methods. Serve browser wallets through HTTPS or localhost. Bind `--public-web` to loopback behind a reverse proxy with per-client limits, such as the [Linux template](../deploy/linux/README.md#public-wallet-website). The listener serves at most 32 sessions, and one client address may hold 6 of them and an eighth or less of the request, byte and work budgets, as more visitors are active. Behind a loopback proxy the node tells visitors apart only by an `X-Real-IP` header that the proxy must overwrite, and all proxied visitors still share one admission budget, a quarter of which only wallet balance, quote, preparation and broadcast calls may spend. The request line and headers must arrive within 5 seconds, and HTTP framing errors and expired deadlines cool down the remote client or named visitor.

JSON amounts are canonical nonnegative decimal integer strings; hashes and keys use documented hex strings or 32-byte arrays. RPC currency values are raw atoms. The UI converts 1,000 atoms to one hash and 1,000 share atoms to one stash.

Read methods include status, config, snapshot, account, governance, proposals, support, quote, stash_quote, fee_quote, grant_quote, mining, getblock, blockreceipt, peers and peerstatus. `blockreceipt` returns the canonical block hash at a height and whether that block holds up to 64 named transaction IDs, without the block itself; the [faucet](FAUCET.md) uses it. `getblock` takes `hash` or `height` (the tip when neither is given) and `format`. The default `json` returns the block's fields as JSON, one value per byte, and refuses a block too large for the JSON page budgets (32 MiB of text or 2,000,000 values, about 2 MB of block), since that tree costs tens of bytes of node memory per block byte. `format: "hex"` returns `hash`, `height` and `raw`, the canonical block record in hexadecimal, which the response limit admits for every valid block; `submitblock` accepts that same object, or `{raw}`, as well as the JSON block. Explorer has separately paginated public methods documented [here](EXPLORER.md). Snapshot binds related reads to one published tip/state. Quotes are estimates under their stated state. A Stash order signs its input amount, fee, context, anchor block hash and lifetime in blocks. `stash_quote` returns `input_requested`, `input_filled`, `input_unfilled`, `output` and the resulting holding estimate, with `indicative: true`, `partial_fill_possible: true` and `execution: "block_batch"`. Inputs use hashes for deposits and stash atoms for redemption; output uses the other asset. Other orders in the block can change the fill. Both `quote` and `stash_quote` require an explicit `Pass` or `Fail` outcome during an active decision; outside a decision, omit the outcome. The governance response reports its scheduled clock with `time_unit: "seconds"` and decision progress separately with `progress.time_unit: "blocks"`. At a decision's last tip (`height - started_height + 1 == blocks`) the next block resolves the decision before any of its transactions, so no conditional trade can be included: `progress.trading_closed` is `true`, and `quote`, `stash_quote`, `fee_quote` and `preparetransaction` refuse a conditional Deposit or Redeem with a "conditional trading is closed" error instead of offering it. Operations common to both outcomes are still prepared. On a curved Stash (reserve below curve mass) a `quote` deposit cannot exceed the world's total account cash, since no larger order can execute. `account` also returns `pending_nonce`, the next nonce after the account's pending transactions, as a decimal string. A snapshot with `key` embeds that account read, so `account.pending_nonce` is the nonce `preparetransaction` requires, computed over the whole mempool. It also returns `sender_mempool`, that sender's own pending rows (at most 128, in the snapshot's summary format), so the sender's transactions stay visible when the global `mempool` page of 128 rows is full. Snapshots without `key` include neither. During a grant decision, `governance` also returns `decision_grant` with the grant's `payment_count` and `payment_total`. `support` returns `status`: `converted_to_revenue` for the backers of a round's winner (never refundable), `refundable`, `locked` (not yet refundable) or `none` (no unclaimed support).

`proposals` and `mempool` accept `offset` and `limit` (up to 128); response byte and JSON-value budgets may end a page sooner. Advance the offset by the number of rows returned until an empty page. Without `round`, `proposals` lists every proposal in ID order. With `round`, it lists that round's leader, decision or winner first, then the others by support (highest first) and ID, so cheaply funded proposals cannot hide better-backed ones from the first page. Support changes from block to block, so page one round listing against a single tip: pass the first page's `tip` (from `status` or the snapshot) with every page. A page requested for an earlier tip is refused; restart from offset 0. A node keeps proposals indexed by round from tip to tip: a round that can no longer change is shared between tips, and a new block re-ranks only the auction round with the proposals it registered, so neither a page nor a wallet's snapshot poll walks all history. Only the first read after startup, a reorganization, or more than 16,384 registrations across tips that nobody read builds the index from every proposal. An unfiltered page finds its offset by subtree size in the state's own key-ordered index, so it reads and pays for only its rows, at any offset. Snapshot `proposals` is the first such page for the current round (the round that just ended during Rest, never all history) and `proposals_total` counts that round's proposals. A record too large for an empty page, such as a governed grant with tens of thousands of payments, is returned as a summary with `truncated: true`, its `payment_count` and its first 256 payments instead of failing the page; the explorer serves the complete record. The snapshot is a bounded wallet summary. A grant with more than 256 payments appears that way in its `proposals` and pending `mempool` rows, and the decision grant appears so in `governance.phase`, with `governance.decision_grant.truncated` set. A wallet poll therefore stays small however large a grant is. `governance`, `proposals` and `mempool` return the complete records. Snapshots include pending transaction metadata and operations, without arbitrary data or signatures. For complete large pending transactions, request `mempool` with `format: "hex"`; each row contains `txid` and the full signed `raw` record. Default JSON mode preserves the ordinary transaction fields when they fit the bounded JSON page.

Private development methods can mine or submit candidate blocks. Use those only on explicitly selected disposable fixtures. Every local process can reach the private listener, so `mine` (and `hashstash mine`) runs only on a development network: fixture issuance (`test_work`), or a proof-of-work limit easier than 2^32 expected hashes per block, such as the presets' uncalibrated one, on a node that untrusted peers cannot reach. Elsewhere it is refused unless the node was started with `--dev-rpc`, including on an easy network that `--allow-easy-target` exposes through a non-loopback `--p2p` or `--peer-discovery`, where outside hashrate can raise difficulty far above the limit. It runs on its own single worker, never on the two mutation workers that transaction submission, `getblock`, `blockreceipt` and the faucet use, and each mined block also pays one work unit per 4,096 requested attempts. Public signed transactions carry their sender, nonce, exact fee, anchor block hash, lifetime and operation/data; the node verifies them before mempool admission. Wallet mutation endpoints require their local session token and exact wallet revision. They have a reserved worker of their own and also take a free mutation worker, so RPC traffic cannot hold off the operator's sends. `GET /api/session` lists server wallets only with that token in `X-Hashstash-Token` (see [wallets](WALLETS.md#optional-node-wallet-tools)).

## Peers

Peers exchange length-framed binary synchronization batches containing chain identity, block locators, canonical block records and canonical signed transactions. Each batch is limited to 128 locator hashes, 32 blocks and 256 loose transactions, with separate byte limits. RPC and Stratum remain JSON interfaces. See [network controls](NETWORK-HARDENING.md#binary-peer-transport) for framing and allocation limits.

Configured peers must use the same binary transport, peer protocol generation and chain identity. Every peer message starts with the generation marker `HSP2P043` (`HSP2A043` for authenticated handshakes); a peer of another release is refused at its first message, and the `peers` RPC names it, for example as Hashstash 0.42.0 or earlier. Transport keys are separate service identities.

### Joining a public network

Use the same consensus implementation as the network's operators, and obtain their exact genesis configuration and a reachable seed. Matching configuration alone does not establish compatible validation rules. Do not create a new genesis to join an existing chain. Start with `--peer-discovery --seed HOST:PORT`; repeat `--seed` for independent bootstrap sources. There are no universal or hardcoded test-network seeds. DNS seeds resolve to numeric endpoints; discovered addresses are always numeric. `--peer IP:PORT` can also provide an explicitly configured bootstrap endpoint.

Discovery uses signed transport sessions. If `--peer-key-file` is absent, the node creates a dedicated, owner-only `chain.peer-key.json` beside `chain.sqlite` (a chain database not named `NAME.sqlite`, such as `net.db`, uses `net.db-peer-key.json`; see [wallet storage](WALLETS.md#optional-node-wallet-tools)), without overwriting an existing identity. It writes the identity to a temporary file and links it into place, or renames it there on a filesystem without hard links, so an interrupted first start cannot leave a partial identity; an empty file left by an earlier interrupted start is replaced. It never uses a wallet, faucet or mining secret. `run` refuses a peer identity equal to its `--wallet-key` or `--watch-key` account or to any saved server wallet account, and the private wallet tools refuse to import or watch that key while the node runs. A successful seed synchronization is followed by address exchange. The node checks learned endpoints by synchronizing with them before relaying them, remembers reachable peers in `chain.peers-CHAIN_ID.json`, retries with backoff, and continues through those peers if the initial seed disappears. Restarting with the same database reloads that chain's peer book even without a seed argument. Losing all saved peers still requires a reachable bootstrap source.

To accept inbound joins, bind `--p2p 0.0.0.0:18481`, open/forward that TCP port, and set `--advertise-peer YOUR_PUBLIC_IP:18481`. Use `[IPv6]:PORT` for IPv6 endpoints. No NAT traversal or automatic public-IP lookup is performed. An outbound-only node can still discover, validate and relay by polling its peers, but it does not advertise an unreachable listener. The public protocol rejects private/reserved gossip; isolated LAN/test fixtures must explicitly select `--allow-private-peer-discovery` (alias `--allow-private-peers`). Never enable that option on a public seed.

Discovery limits the book to 256 endpoints, each exchange to 32, each source network to 32 candidates, and each destination network to 16 candidates. Source/destination groups are IPv4 /16 or IPv6 /32. At most two outgoing sessions run concurrently, spread across destination groups in public mode. These controls reduce address poisoning and concentration; they do not prove operator independence or eliminate Sybil/eclipse attacks. Use several independent seeds and pinned known peers where available.

### Fixed pinned networks

For closed authenticated transport, create a separate identity with `peer-keygen`, validate with `peer-keycheck`, supply `--peer-key-file`, and pin each `--peer` endpoint with `--peer-pin IP:PORT=PUBLIC_KEY`. Omit `--peer-discovery`. All configured endpoints must have pins in this mode, and discovery is disabled. Wrong key/chain/challenge, changed frames or sequence errors fail closed; there is no downgrade retry.

Open discovery can retain known pins: add `--peer-discovery` alongside the dedicated key and pins. Those endpoint pins are still enforced; an incoming source IP with configured pins must prove one of its pinned keys. Unknown addresses may prove a new transport identity and join. `peer-keycheck --peer-discovery` validates this policy with zero or more pins. Public-key possession is not a trusted real-world identity, and all received blocks/transactions still undergo ordinary validation. Nodes without either authenticated mode retain legacy compact-binary synchronization for explicit peers. Transport signatures provide integrity, not confidentiality.

## Mining and transactions

Stratum V1 serves an HST! coinbase as the sole Merkle leaf of a Bitcoin-format 80-byte header. External miners supply nonce/extranonce/version rolling and valid timestamps. Current jobs retain their reporting target. Non-block shares are statistics; only accepted canonical work creates hashes. Losing-parent work is rejected. Process counters reset on restart and a found block can later be reorganized out.

The mempool holds the next-block selection, at most 4096 transactions, plus a backlog of at most 256 earlier entries that lost only to block capacity, within one block's bytes, whatever the selection's size. Backlog entries compete again for later blocks until included, outbid at the same nonce, or expired. A new transaction that cannot win a place in the next block is refused; there is no separate count limit, so a better fee rate displaces the weakest entry. While an account's earlier transaction waits in the backlog, its next nonce (the one preparation returns) or a same-nonce rebid of a waiting transaction may wait behind it within the same bounds; it ranks no higher than the earlier transactions it waits for, and past its first waiting transaction one account's chain holds at most half of the backlog. If better bids fill the backlog, the refusal says that an earlier transaction from the sender is still waiting. A replacement at the same nonce must raise the signed fee rate by at least an eighth and by the minimum fee rate, and must also earn the miner at least as much per weight unit. A transaction whose fee is below the least minimum it could need in the next block, whose sender's opening balance cannot cover its inputs and fee, or whose earlier nonce is not pending, is refused without a selection. Once a selection refuses a transaction as invalid, another broadcast or relayed transaction at the same sender nonce is refused too until the pool or the tip changes, unless it raises the fee rate as a replacement must; the operator's private submissions are exempt. Selection accepts at most 8192 candidates, verifies each unique candidate once and never re-verifies a pooled entry, applies operations atomically with bounded retries, and prioritizes fee rate subject to nonce/state dependencies. A trade's fill never decides whether a transaction is valid, so admission does not clear batch trades; clearing runs when a block template is built, outside the node's state lock, and when a block is validated. A pending transaction is not guaranteed inclusion. The declared exact fee is paid in full and must meet the governed weight-based minimum. All of it is split by the governed miner percentage. Block usage does not change the minimum rate.

## Persistence and resources

Each accepted block and selected tip update is committed transactionally in SQLite. A commit that fails, as on a full disk, changes nothing: the tip stays where it is, and `status` and `peerstatus` report `storage.degraded` with `failed_commits`, `failing_since` (Unix time) and `last_error` until a block is stored again. Once eight block commits in a row have failed over at least a minute, the node exits with status 74 for a supervised restart rather than running on a frozen tip whose miners' blocks are lost; free space before it restarts. The node also saves a state checkpoint: the full state 31 blocks below the tip, every 1,024 heights once the active chain is 1,055 blocks long, and again at every clean stop once it is 32 long, so a stop and start validates only about 31 blocks at any height. The state must pass the full state audit before it is saved (a periodic save audits on its own thread, off the node lock, and writes at a later block); a state that fails is not saved, and the older checkpoints stay. The node keeps the newest two and up to two older ones, about one per doubling of depth in intervals of 1,024 heights. On Unix, a save needs free disk space of twice the largest saved state plus 512 MiB. A failed save is logged and reported as `storage.checkpoint_error`; the write-ahead log is truncated, and periodic saves wait 1,024 heights before trying again, doubling with each further failure up to 16,384. A start uses the newest checkpoint that the same executable saved on the saved active chain, after checking it: its state root must equal the root its block commits to and the full state audit must pass (the root omits a decision's copy of its winning action, which the audit compares with the committed one), its ancestors' persisted index entries must link up and agree with their headers, and the blocks above it must lead back to the saved tip. The node then validates only the stored blocks above the checkpoint; stored losing branches forking below it keep their checked index entries and are not executed. A checkpoint start decodes one copy of the state, so it needs about the memory the running node holds: during a decision the PASS outcome's account records are saved only where they differ from the FAIL outcome's, and restored sharing the rest rather than as a second copy. Any failed check, a different executable (after an upgrade, whose rules may differ), or no checkpoint at all, means the full start: every saved body is validated and the derived indexes are rebuilt in bounded batches, after which a new checkpoint is saved. Losing-branch blocks that the persisted index already shows to have fallen out of competition are not validated: they are deleted if the rebuilt index reproduces the persisted tip's entry, and validated after all otherwise. Startup then truncates the write-ahead log. A stale saved tip is replaced by the replayed best tip. Losing-branch blocks that no longer validate move to the `rejected_blocks` table with a log line; a failure in the saved tip's own history still stops startup. Losing-branch blocks that have fallen out of competition are deleted, also with a log line; peers can supply them again if their branch revives. Writing a checkpoint every 1,024 blocks holds the node lock while it encodes the state and writes it to SQLite, right after the block that triggers it is stored and before that tip is published: block handling, transaction admission and template refreshes wait, and miners keep working on the previous tip meanwhile. The pause grows with the state, to seconds for one of hundreds of MB. Current tip publication includes block and state together. Reorganizations restore accounts, reserve shape, revenue, grants, fees and governance as one state; no decision is irreversible.

Retained blocks and live account/proposal state grow. Proposal and round records are never pruned, and support records persist until refunded. Like new accounts and grant payouts, every proposal and every new support record therefore carries 1,024 extra weight, which bounds their growth by block capacity and prices it like account creation. The node has bounded hot caches: 128 recent historical states, active-chain checkpoint states (every block within 32 of the tip, then two per doubling of depth), 256 header/work entries and an 8 MiB SQLite page cache; deep traversal uses disk-backed temporary storage. A block that cannot become the tip is stored only if its branch is competitive when it arrives, within side-branch budgets of blocks and bytes refilled by active-chain growth and kept across restarts, and, on Unix, while at least 512 MiB of disk space is free; otherwise only its header is held in memory, so a heavier branch can still be presynced and then adopted if it needs at most 65,536 headers past the stored fork point before it claims more work than the tip; after a longer partition the node needs a manual resynchronization ([specification](SPECIFICATION.md#12-records-storage-and-networking)). After a start from a checkpoint only genesis is retained below it, so a losing branch forking below the checkpoint is likewise held as headers until it claims more work than the tip; it is then validated and adopted. Adopting it rebuilds its fork point's state in budgeted steps during which the node stays on its current tip: from an older saved checkpoint at or below the fork point when one passes its checks and the fork point lies more than 1,024 heights above the nearest retained state, otherwise from genesis, about the fork point's height in blocks rather than its depth. That replay retains states on its way like a full replay, so once the branch is adopted, reconstructing a state on the new active chain costs about its depth again. Admitted losing-branch blocks are retained until they fall out of competition, when startup prunes them; a full start replays those the persisted index does not show to have fallen out of competition, a start from a checkpoint replays only those forking above it. These limits do not bound every allocation or total restart time: the whole account state is held in memory, and a checkpoint start decodes it from one saved copy. The active chain is never pruned. Back up a stopped database or use SQLite's backup facilities; never edit tables manually.

RPC, peers and Stratum have separate admission, byte/work budgets and worker pools. HTTP reads, peer connections and handshakes time out after 15 seconds. Peer synchronization reads allow additional time for validated block capacity; each outbound synchronization attempt allows five times that read allowance overall, and each inbound peer session twice it. Stratum authorization must finish within 10 seconds, and a non-loopback Stratum listener requires a password; authenticated idle miners may wait for work. Requests and decoded structures have explicit size/depth/value limits. Future-dated candidates, unknown parents, deferred history and declined side blocks are retryable, and a declined side block's header keeps the peer synchronization going rather than counting as a peer failure. Repeated permanently invalid full bodies have a bounded short-lived cache. See [network controls](NETWORK-HARDENING.md) for limits and remaining risks.

Current settings expose nine governance parameters: BlockBytes, Interval, Lead, Rest, DecisionBlocks, MinerFeePercent, PassMarginBps, MinimumFeeRate and MaxPriceChangeBps. Each proposal sets an exact new value. DecisionBlocks is a positive block count; Interval is positive scheduled seconds, while Lead and Rest allow zero. BlockBytes is from 4,096 weight (the heaviest data-free proposal, its record and a new mining account) through 64 MiB. MinerFeePercent is 0–100. PassMarginBps and MaxPriceChangeBps are unsigned basis-point values. The initial price-change limit is 1,000 bps (10%); zero prevents quote movement and values at or above 10,000 permit the full downside range. MinimumFeeRate starts at one raw atom per 1,024 weight and allows zero. Integer values, future clocks and block boundaries must remain representable. Governed changes have extra limits so one decision cannot make the next impossible: Interval at most the ASERT half-life, at least a quarter of its genesis value and within half or twice the old value (and an increase must keep the Lead and DecisionBlocks limits), BlockBytes within half or twice the old value, Lead at most half of the auction timeout less one interval, Rest at most 2^22 seconds, DecisionBlocks at least 3 and at most 2^22 seconds long, MaxPriceChangeBps from 1 through 9,999, a positive MinimumFeeRate of at most a doubling and at most 2^16 times the genesis rate, and a reachable PASS margin. [Consensus](CONSENSUS.md) specifies the arithmetic and byte format.

All order inputs and fees come from block-opening balances. Same-block incoming funds cannot finance them. Each world clears its included Stash orders together at one execution price, with proportional fills on the constrained side and unused input returned. Orders do not persist after inclusion. RPC and CLI trade preparation default to two-block expiry; all other operations also default to two blocks. Explicit expiry overrides are supported.
