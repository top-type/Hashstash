# Node operation

The node requires a 64-bit target. Genesis identifies the chain. A database must use its exact genesis configuration; changing that configuration creates a different identity, affecting addresses, application caches and chain-scoped faucet ledgers.

Source builds place executables in `target/release`; packaged releases place them in `bin`. The PowerShell launchers prefer the source build when present. Examples using `bin` assume the packaged layout.

```sh
hashstash init --config network.json --preset slow
hashstash keygen --out miner.key
hashstash run --config network.json --data chain.sqlite --miner PUBLIC_KEY --rpc 127.0.0.1:18480 --p2p 0.0.0.0:18481 --stratum 0.0.0.0:18482 --stratum-password-file mining-password --peer-discovery --seed SEED_HOST:18481 --advertise-peer YOUR_PUBLIC_IP:18481
```

`init` records this computer's clock as `genesis_time` and prints it in UTC. Block 1 must be later than genesis, so a fast clock delays the first block on every correctly clocked node; check the clock or pass `--genesis-time UNIX_SECONDS`. `init` warns about a genesis time beyond the network's future-time allowance.

The Stratum password file must contain one printable ASCII token of at most 256 characters, as the Linux launcher requires; `run` refuses an empty or malformed file, and refuses a non-loopback Stratum listener without one before opening the database. `run` warns when `--public-web` binds a non-loopback address, because that listener serves plain HTTP.

The node needs only the public mining key. Keep any private backup inaccessible to untrusted users. `--no-stratum` disables the mining listener without disabling validation or relay. Mining payout and listener/password/reporting settings are operator configuration, not wallet controls. See [mining](MINING.md) and [Linux deployment](../deploy/linux/README.md).

`--wallet-key PATH` and `--watch-key ADDRESS` are mutually exclusive opt-in server-wallet modes for private operator tooling. Without them the server wallet database starts empty. Browser wallets are independent and sign locally. The separate cold signer requires no node connection to review/sign exported transactions. See [wallets](WALLETS.md).

## API boundaries

Private JSON-RPC is POST `/rpc`, envelope `{jsonrpc:"2.0",id,method,params}`. RPC must bind loopback. Public-web mode exposes an allowlist of reads and signed-transaction submission without server-wallet management, secret material, software mining, configuration changes or arbitrary private methods. Serve browser wallets through HTTPS or localhost. Bind `--public-web` to loopback behind a reverse proxy with per-client limits, such as the [Linux template](../deploy/linux/README.md#public-wallet-website): the listener serves at most eight sessions, and proxied visitors share one admission budget. A directly exposed listener lets one host hold every session.

JSON amounts are canonical nonnegative decimal integer strings; hashes and keys use documented hex strings or 32-byte arrays. RPC currency values are raw atoms. The UI converts 1,000 atoms to one hash and 1,000 share atoms to one stash.

Read methods include status, config, snapshot, account, governance, proposals, support, quote, stash_quote, fee_quote, grant_quote, mining, getblock, peers and peerstatus. Explorer has separately paginated public methods documented [here](EXPLORER.md). Snapshot binds related reads to one published tip/state. Quotes are estimates under their stated state. A Stash order signs its input amount, fee, context, anchor block hash and lifetime in blocks. `stash_quote` returns `input_requested`, `input_filled`, `input_unfilled`, `output` and the resulting holding estimate, with `indicative: true`, `partial_fill_possible: true` and `execution: "block_batch"`. Inputs use hashes for deposits and stash atoms for redemption; output uses the other asset. Other orders in the block can change the fill. Both `quote` and `stash_quote` require an explicit `Pass` or `Fail` outcome during an active decision; outside a decision, omit the outcome. The governance response reports its scheduled clock with `time_unit: "seconds"` and decision progress separately with `progress.time_unit: "blocks"`. On a curved Stash (reserve below curve mass) a `quote` deposit cannot exceed the world's total account cash, since no larger order can execute. `account` also returns `pending_nonce`, the next nonce after the account's pending transactions, as a decimal string like the snapshot's `pending_nonce`. During a grant decision, `governance` also returns `decision_grant` with the grant's `payment_count` and `payment_total`. `support` returns `status`: `converted_to_revenue` for the backers of a round's winner (never refundable), `refundable`, `locked` (not yet refundable) or `none` (no unclaimed support).

`proposals` and `mempool` accept `offset` and `limit` (up to 128); response byte and JSON-value budgets may end a page sooner. Advance the offset by the number of rows returned until an empty page. Without `round`, `proposals` lists every proposal in ID order. With `round`, it lists that round's leader, decision or winner first, then the others by support (highest first) and ID, so cheaply funded proposals cannot hide better-backed ones from the first page. Support changes from block to block, so page one round listing against a single tip: pass the first page's `tip` (from `status` or the snapshot) with every page. A page requested for an earlier tip is refused; restart from offset 0. A node indexes proposals by round once per tip, so a page never scans all history. Snapshot `proposals` is the first such page for the current round (the round that just ended during Rest, never all history) and `proposals_total` counts that round's proposals. A record too large for an empty page, such as a governed grant with tens of thousands of payments, is returned as a summary with `truncated: true`, its `payment_count` and its first 256 payments instead of failing the page; the explorer serves the complete record. The snapshot is a bounded wallet summary. A grant with more than 256 payments appears that way in its `proposals` and pending `mempool` rows, and the decision grant appears so in `governance.phase`, with `governance.decision_grant.truncated` set. A wallet poll therefore stays small however large a grant is. `governance`, `proposals` and `mempool` return the complete records. Snapshots include pending transaction metadata and operations, without arbitrary data or signatures. For complete large pending transactions, request `mempool` with `format: "hex"`; each row contains `txid` and the full signed `raw` record. Default JSON mode preserves the ordinary transaction fields when they fit the bounded JSON page.

Private development methods can mine or submit candidate blocks. Use those only on explicitly selected disposable fixtures. Public signed transactions carry their sender, nonce, exact fee, anchor block hash, lifetime and operation/data; the node verifies them before mempool admission. Wallet mutation endpoints require their local session token and exact wallet revision.

## Peers

Peers exchange length-framed binary synchronization batches containing chain identity, block locators, canonical block records and canonical signed transactions. Each batch is limited to 128 locator hashes, 32 blocks and 256 loose transactions, with separate byte limits. RPC and Stratum remain JSON interfaces. See [network controls](NETWORK-HARDENING.md#binary-peer-transport) for framing and allocation limits.

Configured peers must use the same binary transport and chain identity. Transport keys are separate service identities.

### Joining a public network

Use the same consensus implementation as the network's operators, and obtain their exact genesis configuration and a reachable seed. Matching configuration alone does not establish compatible validation rules. Do not create a new genesis to join an existing chain. Start with `--peer-discovery --seed HOST:PORT`; repeat `--seed` for independent bootstrap sources. There are no universal or hardcoded test-network seeds. DNS seeds resolve to numeric endpoints; discovered addresses are always numeric. `--peer IP:PORT` can also provide an explicitly configured bootstrap endpoint.

Discovery uses signed transport sessions. If `--peer-key-file` is absent, the node creates a dedicated `chain.peer-key.json` beside `chain.sqlite`, without overwriting an existing identity. It writes the identity to a temporary file and links it into place, so an interrupted first start cannot leave a partial identity; an empty file left by an earlier interrupted start is replaced. It never uses a wallet, faucet or mining secret, and `run` refuses a peer identity equal to its `--wallet-key` or `--watch-key` account. A successful seed synchronization is followed by address exchange. The node checks learned endpoints by synchronizing with them before relaying them, remembers reachable peers in `chain.peers-CHAIN_ID.json`, retries with backoff, and continues through those peers if the initial seed disappears. Restarting with the same database reloads that chain's peer book even without a seed argument. Losing all saved peers still requires a reachable bootstrap source.

To accept inbound joins, bind `--p2p 0.0.0.0:18481`, open/forward that TCP port, and set `--advertise-peer YOUR_PUBLIC_IP:18481`. Use `[IPv6]:PORT` for IPv6 endpoints. No NAT traversal or automatic public-IP lookup is performed. An outbound-only node can still discover, validate and relay by polling its peers, but it does not advertise an unreachable listener. The public protocol rejects private/reserved gossip; isolated LAN/test fixtures must explicitly select `--allow-private-peer-discovery` (alias `--allow-private-peers`). Never enable that option on a public seed.

Discovery limits the book to 256 endpoints, each exchange to 32, each source network to 32 candidates, and each destination network to 16 candidates. Source/destination groups are IPv4 /16 or IPv6 /32. At most two outgoing sessions run concurrently, spread across destination groups in public mode. These controls reduce address poisoning and concentration; they do not prove operator independence or eliminate Sybil/eclipse attacks. Use several independent seeds and pinned known peers where available.

### Fixed pinned networks

For closed authenticated transport, create a separate identity with `peer-keygen`, validate with `peer-keycheck`, supply `--peer-key-file`, and pin each `--peer` endpoint with `--peer-pin IP:PORT=PUBLIC_KEY`. Omit `--peer-discovery`. All configured endpoints must have pins in this mode, and discovery is disabled. Wrong key/chain/challenge, changed frames or sequence errors fail closed; there is no downgrade retry.

Open discovery can retain known pins: add `--peer-discovery` alongside the dedicated key and pins. Those endpoint pins are still enforced; an incoming source IP with configured pins must prove one of its pinned keys. Unknown addresses may prove a new transport identity and join. `peer-keycheck --peer-discovery` validates this policy with zero or more pins. Public-key possession is not a trusted real-world identity, and all received blocks/transactions still undergo ordinary validation. Nodes without either authenticated mode retain legacy compact-binary synchronization for explicit peers. Transport signatures provide integrity, not confidentiality.

## Mining and transactions

Stratum V1 serves an HST! coinbase as the sole Merkle leaf of a Bitcoin-format 80-byte header. External miners supply nonce/extranonce/version rolling and valid timestamps. Current jobs retain their reporting target. Non-block shares are statistics; only accepted canonical work creates hashes. Losing-parent work is rejected. Process counters reset on restart and a found block can later be reorganized out.

The mempool holds the next-block selection, at most 4096 transactions, plus a backlog of at most 256 earlier entries that lost only to block capacity, within one block's bytes, whatever the selection's size. Backlog entries compete again for later blocks until included, outbid at the same nonce, or expired. A new transaction that cannot win a place in the next block is refused; there is no separate count limit, so a better fee rate displaces the weakest entry. While an account's earlier transaction waits in the backlog, its next nonce (the one preparation returns) or a same-nonce rebid of a waiting transaction may wait behind it within the same bounds; if better bids fill the backlog, the refusal says that an earlier transaction from the sender is still waiting. A transaction whose fee is below the least minimum it could need in the next block, whose sender's opening balance cannot cover its inputs and fee, or whose earlier nonce is not pending, is refused without a selection. Selection accepts at most 8192 candidates, verifies each unique candidate once and never re-verifies a pooled entry, applies operations atomically with bounded retries, and prioritizes fee rate subject to nonce/state dependencies. A pending transaction is not guaranteed inclusion. The declared exact fee is paid in full and must meet the governed weight-based minimum. All of it is split by the governed miner percentage. Block usage does not change the minimum rate.

## Persistence and resources

Each accepted block and selected tip update is committed transactionally in SQLite. Startup validates saved bodies and rebuilds derived indexes in bounded batches, then truncates the write-ahead log. A stale saved tip is replaced by the replayed best tip. Losing-branch blocks that no longer validate move to the `rejected_blocks` table with a log line; a failure in the saved tip's own history still stops startup. Losing-branch blocks that have fallen out of competition are deleted, also with a log line; peers can supply them again if their branch revives. Current tip publication includes block and state together. Reorganizations restore accounts, reserve shape, revenue, grants, fees and governance as one state; no decision is irreversible.

Retained blocks and live account/proposal state grow. Proposal, support and round records are never pruned. Like new accounts and grant payouts, every proposal and every new support record therefore carries 1,024 extra weight, which bounds their growth by block capacity and prices it like account creation. The node has bounded hot caches: 128 recent historical states, active-chain checkpoint states (every block within 32 of the tip, then two per doubling of depth), 256 header/work entries and an 8 MiB SQLite page cache; deep traversal uses disk-backed temporary storage. A block that cannot become the tip is stored only if its branch is competitive when it arrives, within a side-branch budget refilled by active-chain growth; otherwise only its header is held in memory, so a heavier branch can still be presynced and then adopted. Admitted losing-branch blocks are retained and replayed on restart until they fall out of competition, when startup prunes them. These limits do not bound every allocation or total restart time. The active chain is never pruned. Back up a stopped database or use SQLite's backup facilities; never edit tables manually.

RPC, peers and Stratum have separate admission, byte/work budgets and worker pools. HTTP reads, peer connections and handshakes time out after 15 seconds. Peer synchronization reads allow additional time for validated block capacity; each outbound synchronization attempt allows five times that read allowance overall, and each inbound peer session twice it. Stratum authorization must finish within 10 seconds, and a non-loopback Stratum listener requires a password; authenticated idle miners may wait for work. Requests and decoded structures have explicit size/depth/value limits. Future-dated candidates, unknown parents, deferred history and declined side blocks are retryable, and a declined side block's header keeps the peer synchronization going rather than counting as a peer failure. Repeated permanently invalid full bodies have a bounded short-lived cache. See [network controls](NETWORK-HARDENING.md) for limits and remaining risks.

Current settings expose nine governance parameters: BlockBytes, Interval, Lead, Rest, DecisionBlocks, MinerFeePercent, PassMarginBps, MinimumFeeRate and MaxPriceChangeBps. Each proposal sets an exact new value. DecisionBlocks is a positive block count; Interval is positive scheduled seconds, while Lead and Rest allow zero. BlockBytes must cover 1,024 weight and fit the host allocation representation. MinerFeePercent is 0–100. PassMarginBps and MaxPriceChangeBps are unsigned basis-point values. The initial price-change limit is 1,000 bps (10%); zero prevents quote movement and values at or above 10,000 permit the full downside range. MinimumFeeRate starts at one raw atom per 1,024 weight and allows zero. Integer values, future clocks and block boundaries must remain representable. Governed changes have extra limits so one decision cannot make the next impossible: Interval at most the ASERT half-life (and an increase must keep the Lead and DecisionBlocks limits), Lead at most half of the auction timeout less one interval, Rest at most 2^22 seconds, DecisionBlocks at least 3 and at most 2^22 seconds long, a positive MaxPriceChangeBps, at most a doubling of MinimumFeeRate, and a reachable PASS margin. [Consensus](CONSENSUS.md) specifies the arithmetic and byte format.

All order inputs and fees come from block-opening balances. Same-block incoming funds cannot finance them. Each world clears its included Stash orders together at one execution price, with proportional fills on the constrained side and unused input returned. Orders do not persist after inclusion. RPC and CLI trade preparation default to two-block expiry; all other operations also default to two blocks. Explicit expiry overrides are supported.
