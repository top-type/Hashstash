# Changelog

## 0.43.0

The release for the launch network. It covers every change since 0.42.0 (commit `cfaaeb8`): the audit fixes (findings F001 to F180), the review follow-ups (R01 to R42) and the release preparation. The [launch runbook](docs/LAUNCH.md) turns the required actions below into steps.

**0.43.0 is incompatible with 0.42.0 in consensus, signatures, peer protocol and storage.** Its blocks commit to a different state encoding (every state root changes, genesis included), its transaction signatures bind the chain ID, and its peers and databases carry new format markers. A 0.42.0 chain cannot be continued or upgraded in place, and the two releases cannot share a network. Breaking changes are marked **Breaking** below.

### Required operator actions

1. **Every node runs 0.43.0; there is no mixed network.** A 0.42.0 node and a 0.43.0 node refuse each other at the first message. The refusing node records an error naming the other release (see [Peer protocol](#peer-protocol-and-synchronization)).
2. **Create a fresh genesis with 0.43.0** (`hashstash init --config network.json --preset slow --hashrate RATE`) and distribute that one file unchanged, with its SHA256 and chain ID, to every operator. Do not reuse a 0.42.0 `network.json`: the same file would give the new chain the old chain's ID, and so its addresses and wallet storage, while its blocks are incompatible. `--preset slow` now refuses to run without `--hashrate` (or an explicit `--uncalibrated`).
3. **Start every node on a new, empty database** (`--data` path, or an empty `/var/lib/hashstash`). 0.43.0 refuses a database holding 0.42.0 blocks with an error that names that release; keep old data only for the old release.
4. **Fund accounts again on the new chain.** Keys remain valid, but balances do not carry over, and every transaction signed or exported by 0.42.0 is invalid under the chain-bound signature domain. Prepare and sign transactions again with 0.43.0 tools. `hashstash sign` now needs `--config` or `--chain-id`; the cold signer needs the new network selected (Explorer → Network → Identity → Export network).
5. **Reinstall the Linux service from this source snapshot.** The installer pins version 0.43.0 and the binary's full SHA256 and refuses to replace an existing installation. Review the new `node.env` fields `ALLOW_EASY_TARGET`, `STRATUM_TRUSTED` and `STRATUM_TRUSTED_BROAD` and the changed nginx template (nginx 1.15.7 or later). A `STRATUM_TRUSTED` prefix outside local networks must be at least /16 for IPv4 or /32 for IPv6.
6. **Give every non-loopback Stratum listener a password file.** `run` refuses to start one without it.
7. **Update tools that use the private RPC session token.** `GET /api/session` no longer returns it; read the owner-only `<data>.session-token` file written at each start (for example `chain.session-token` beside `chain.sqlite`). Tools that called `fee_quote` or `transfer_quote` without `sender` must now name it: neither defaults to the selected server wallet any more.
8. **Handle HTTP 429 and 503 with `Retry-After`** in any client, monitor or proxy of the node's HTTP listeners. Admission refusals are now answered instead of dropping the connection.
9. **Use a new faucet ledger** for the new network, and review the faucet's new `subnet_daily_claims` setting.

### Consensus

All of the following are **Breaking**: a 0.42.0 node rejects 0.43.0 blocks and the reverse.

- **State commitment (R04).** Every authenticated state map is committed as a binary Patricia trie over `tagged_hash("Hashstash/TriePath", key)`, with `TrieLeaf`, `TrieBranch` and `TrieEmpty` tags, instead of a treap whose depth users could grind. Depth is at most 256 for any keys. Every state root changes, genesis included. Independent vectors in `tests/commitment_encoding.rs` pin whole state roots and phase commitments ([consensus format](docs/CONSENSUS.md#state-commitments)).
- **Proposal actions and phase commitment.** A proposal's action is stored once in a write-once `actions` map committed after the proposals root; `ProposalRecord` keeps round, proposer, description, support and refund height. The phase is committed without the decision's copy of its proposal.
- **Chain-bound signatures.** The signing message is `tagged_hash("Hashstash/chain-bound-transaction", chain_id || encode(body))`. The chain ID is still not part of the transaction bytes; each node verifies against its own chain ID, so a signature takes effect on one network only.
- **Proposal IDs bind the proposer (F075):** `tagged_hash("Hashstash/proposal", encode((chain_id, round, proposer, description, proposal)))`, with a committed `proposer` field. A copied pending Propose from another sender registers a separate proposal.
- **Decision ID (F179, F108)** hashes `(chain_id, round, proposal_id, height, parent_hash)`, so same-parent siblings share it.
- **Symmetric PASS and FAIL opening (F010).** FAIL sets the grant's reserve shortfall aside as waiting revenue, so both outcomes open on identical curves; neither world replenishes during a decision, and the selected world refills in its resolution block. A grant draws all waiting revenue but at most half of the reserve. The winning bid becomes revenue only after the grant is reserved.
- **Empty worlds (F014).** A block in which either world holds no Stash adds no PASS lead.
- **Auctions (F016).** A proposal that cannot open its decision is cancelled when it reaches the top instead of taking the lead. When a leader is cancelled, the most recently displaced active proposal resumes its recorded lead start. At the auction timeout an eligible leader opens its decision even before its lead matures.
- **Record weight (F046).** Every Propose, and a Support that creates the sender's support record for a proposal, adds 1,024 execution weight. Fee quotes report it as `record_fee`.
- **Governed-parameter bounds (F012, F015, F028, R01, R05).** BlockBytes is from 4,096 through 64 MiB at genesis and under governance. Governed changes, not genesis, must also keep: BlockBytes and Interval within half or twice the old value; Interval at most the ASERT half-life and at least a quarter of its genesis value; Lead at most half of the auction timeout less one interval; Rest at most 2^22 seconds; DecisionBlocks at least 3 and at most 2^22 seconds long; MaxPriceChangeBps from 1 through 9,999; a positive MinimumFeeRate of at most a doubling per decision and 2^16 times the genesis rate; a PASS margin reachable within the decision; and a schedule representable through the whole remaining height range. An overflowing Rest deadline saturates instead of invalidating blocks.
- **Flat-curve execution (F005).** Each order on a flat curve receives its rounded-down output at the exact price and pays the least input for it; the rest is refunded. When inexact sales alone break the price bound on a flat world, the budget search falls back to the sale side, then to both sides. A world refilled to flat stays tradeable.
- **Bounded batch clearing (F006, F047).** Clearing spends at most 1,024 curve evaluations per world, with a deterministic conservative fallback, logarithm precision sized to the inputs (4b+128 bits, at most 2,048) and a specified root search.
- **ASERT anchor (F029).** The first-block anchor is bounded below by the second block's timestamp less one interval.
- **Common credits (F158, F160)** require identical account existence and nonce in both worlds, and broken invariants in execution return errors instead of panicking.

The coinbase height push, the canonical codec and the pinned `bincode`, `serde` and `num-bigint` encodings are unchanged and now pinned by vectors.

### Peer protocol and synchronization

- **Breaking: peer protocol generation marker.** Every peer payload starts with `HSP2P043` instead of `HSP2PBIN`, and the authenticated handshake with `HSP2A043` instead of `HSP2PAUT`; the marker is part of the signed handshake transcript. The suffix names the release that introduced the rules a node enforces. For the same genesis file, 0.42.0 and 0.43.0 compute the same chain ID and share the framing, so without the marker they exchanged addresses and records that failed validation on the other side ("no common ancestor", "early eof"). Now a node refuses another generation's first frame or greeting before decoding it, closes, and records "peer runs Hashstash 0.42.0 or earlier (peer protocol HSP2PBIN)" in the `peers` RPC. A 0.42.0 node refuses this release's frames as an invalid format, which the 0.43.0 side reports as a peer that closed the connection on a header request, a locator request or the authentication handshake, naming 0.42.0 as a possible cause. `tests/node_transport.rs` checks both directions.
- **Headers-first synchronization (R09), transport version 2.** Outbound sessions open with up to four header requests (tag 4) answered by at most 2,000 consecutive 80-byte headers (tag 5). A node counts a branch's claimed work from its headers before holding any, so a heavier branch is followed whatever its blocks' size, and whatever its distance within the 65,536-header bound; held headers are bounded at 65,536 and admitted ones persisted in a `held_headers` table. A branch that needs more headers than that past the node's stored fork point before it claims more work than the tip is not followed (see [Accepted limitations](#accepted-limitations)). Peers that close two consecutive sessions on a header request are synchronized by blocks only for ten minutes (`version1_peers` in `peerstatus`).
- **Side branches.** Declined side blocks are presynced as headers (at most 32,768) instead of refused for good. Side-branch storage draws on a budget refilled by active-chain growth; replay of side blocks is bounded before it runs and executed off the node lock. Stale losing branches are pruned at startup.
- **Admission and slots.** Peer record admission follows the greatest validated capacity plus 1 KiB instead of a 32 MiB floor; a connection's first message is bounded to a locator request; buffered frame memory is reserved as bytes arrive and shared node-wide. Inbound peers have 16 general slots with group caps and reserved slots for configured, pinned and verified peers; a newcomer can evict an unprotected session. Admission is charged per address and per prefix (IPv4 /24, IPv6 /48, 6to4's embedded /24).
- **Inbound slot fairness (L002, L007, L014, L057, L058).** No inbound session is evicted within 15 seconds of its admission, so sources that keep reconnecting cannot displace honest sessions before they finish; while every unprotected session is that young a newcomer is refused instead. A network group at its two-session cap no longer refuses its other members: while general slots are free, a member whose address holds none of the group's sessions takes one beyond the cap, and once they are full, sessions beyond a cap are the first a newcomer takes over, while a member takes over the group's session that delivered something new least recently. Neither one address nor a few that keep reconnecting or sending transactions can lock their /16 or IPv6 /32 out of a node any more. Recently verified peers take over each other's reserved slots after that grace period. Operator privileges (reserved slots, no group cap or eviction, the frame memory share) go to the exact configured or pinned address only, no longer to its whole IPv6 /64, and such an address's inbound connections are no longer refused through its /24 or /48 aggregate's cooldown or connection cap.
- **Discovery.** Address-book replacement instead of refusal, two learned endpoints per IP, configured peers not gossiped, anchors tried first after a restart, atomic saves.
- **Discovery scheduling (L001, L039).** A synchronization counts as a success only when one of the peer's blocks became the tip, when it delivered headers or new blocks of a heavier branch this node holds but has not adopted yet, or when the turn completed within one read allowance without anything new; a slow turn that delivered nothing is a failure. A synchronization that has neither advanced the tip nor that heavier branch within two read allowances is cut off, whatever transactions it delivered. Discovery runs three outbound sessions: one slot is reserved for the operator's chosen peers (configured peers, numeric seeds and DNS seed results that answered their last contact), each synchronized every 15 seconds and no other entry ever takes it, so slow-walking or transaction-sending entries no longer delay them; the synchronizing slot re-dials a peer that just advanced the tip or a heavier branch at once, then peers that advanced the tip within the hour, ahead of the rotation through other verified peers; the exploring slot probes unknown entries. Anchors are the last two peers that advanced the tip, not any that answered. Failures beyond six back off up to an hour, but only while other entries answer meanwhile, so a node whose own connectivity was lost retries every peer at least once a minute and reconnects soon after it returns; configured peers, numeric seeds and DNS seed results are always retried at least once a minute. DNS seed results skip the learned quotas, but one seed holds at most 16 of them, they never displace verified peers or anchors in a full book, and one that never answered is dropped after three failures until the seed's next lookup returns it; seeds are resolved again every minute instead of every ten while no peer has answered for ten minutes. A learned address that finds its IP full displaces an unverified entry there from a source holding more of the IP's entries, so several sources gossiping bogus ports cannot keep an honest node's real endpoint out, and one that finds its group full displaces one only from a source that would still hold more; an inbound peer's own announcement displaces any unverified entry. Never-answered learned entries expire after a day; unknown entries in a healthy group are probed every ten minutes.
- **Replies are paid for before they are built (L010).** A header reply pays its work, one unit per header, before any header is read; a budget that cannot pay for it closes the session unbuilt and without a cooldown. The reply reads the header index 250 headers at a time and releases the node lock in between. A synchronization reply or push pays for each block and loose transaction as it is added and ends at the first one the budget refuses. Previously both were built in full under the node lock and refused afterwards without any cost to the requester. A requester whose locator shows it is only catching up on the responder's chain receives one header instead of 2,000 it would discard (L069).
- **Sessions survive local outcomes (L020, L043).** A header reply that raced another download, or whose processing fails, ends the header requests but no longer the session: the block exchange still runs. A reply or push whose replay this node defers is still answered with the push or the acknowledgement, so a deep reorganization no longer makes either side treat the other as failed. A peer that closes between two messages, or a budget refusal already penalized, no longer starts a malformed-frame cooldown. `node::sync_peer` returns a `SyncOutcome` (header rounds, header error, blocks received, whether replay deferred).
- **Held header bounds (L018, L019, L070).** An admitted header chain is extended only from its best header: a header leaving it lower down, from a reply, a header download or a pushed block, is held without admission until it claims more work than every admitted chain, and counts the 2,048-header extension bound on from the admitted header it leaves, so a detour through a header held without admission no longer starts that count again. Header downloads are ranked by the work of the headers they counted instead of their number, so headers at the network limit (256 times easier than a calibrated initial target) cannot cheaply outrank a real branch. Once 64 downloads run, or four from one network group, a new download takes the place of the one that counted the least work only if it counted at least as much itself; otherwise it is dropped and that session's header requests end. Replies of already stored headers count no work, so downloads made of them displace only each other, never one that counted work. A database error while following headers releases the download's pinned headers.
- **Peer capacity accounting (L040, L046, L054).** Once two largest frames exceed the peer baseline, a peer address's byte burst and refill rate cover two of them, one session's reply and push. The read deadline for a peer message follows the largest frame instead of the capacity alone, matching what its sender allows itself to write (at the launch capacity about 18 instead of 15 seconds, and the overall session limits scale with it); an inbound connection's handshake and first request keep the allowance of the largest request (15 seconds at launch). Frames being decoded are accounted against a reserve of one largest frame per decoding worker within the frame memory budget. A push or a reply without a declared allowance no longer sends a block after a download cursor beyond the recipient's validated capacity, and a reply to a header session is decoded within the allowance its request declared.

### Signing and keys

- **Breaking:** chain-bound transaction signatures (above). Every signer binds its selected network: the CLI, node wallet, faucet, browser wallet and cold signer. `hashstash sign` requires `--config` or `--chain-id` and refuses an export prepared for another network.
- **Passphrase keys.** New `hashstash-passphrase-v2`: scrypt (N = 2^17, r = 8, p = 1) salted with the chain ID, at least 16 printable ASCII characters. The unsalted v1 scheme is restore-only behind an explicit acknowledgement.
- **Encrypted keys at rest (R13).** Browser wallets can seal saved keys under a passphrase (`hashstash-browser-lock-v1`: PBKDF2-HMAC-SHA256, 600,000 iterations, AES-256-GCM), with an idle lock and timed clipboard clearing. `run --wallet-passphrase-file PATH` encrypts the node wallet's hot keys (`hashstash-node-wallet-lock-v1`, ChaCha20-Poly1305); an encrypted store opens only with the passphrase, and 0.42.0 refuses it.
- **Cold signer.** Random key generation with a one-time backup, reviews only for an operator-selected network, warnings and confirmation for lifetimes above 1,000 blocks, review limits (`--max-review-bytes`, `--max-review-payments`), a session token delivered only in the launch URL's fragment, an idle lock (`--idle-lock-seconds`, default five minutes), at most 16 connections, and core dumps disabled. Without the token, `GET /api/session` reports only the format, limits and lock state (`unlocked`, `idle_locked`), never the open account's key or address or the selected network; a tool that read those there must send the token to the new `POST /api/status`. A generated key's one-time backup is built in a wiped buffer of its exact size. `Start-ColdWallet.ps1` opens the token address only once every listener on its port belongs to the signer process it started (`Get-NetTCPConnection`), and otherwise stops with an error naming the other process.
- **Secret files.** Wallet stores, key files, peer identities, faucet keys and session tokens are owner-only on every platform. On Windows a new secret file is created with a protected access list granting only the node's account, so no other account can open it even briefly (a handle opened before a later restriction kept its access); an existing one gets that whole list, which also removes entries granted explicitly to other accounts. An existing secret file that another account owns is refused (take ownership of it or move it aside), and the list is read back; on an NTFS volume anything but an owner-only list is an error. The node also creates the wallet database's rollback journal, and creates it again whenever SQLite deletes one (after playing back a write that a crash interrupted, or beside a database without pages), so SQLite never creates it with the folder's inherited list. Key files that other accounts can read are refused by the faucet, the peer identity reader and `--wallet-passphrase-file`. Spending key files given to `sign`, `send`, `transfer`, `public-key`, `address --key` or `run --wallet-key` must be regular files of at most 4,096 bytes, and the command warns when other accounts can read them.

### Storage

- **Breaking: storage format marker.** The chain database records `hashstash-storage-043` in its metadata. A database holding 0.42.0 blocks (same configuration row, no marker) is refused at startup by name instead of failing replay with "unknown parent"; an empty one takes the marker. 0.42.0 refuses a 0.43.0 database because its blocks do not validate there.
- **State checkpoints (R08).** The node saves the state 31 blocks below the tip every 1,024 heights once the chain is 1,055 blocks long, and at every clean stop once it is 32 long, so a stop and start validates about 31 blocks at any height (S002). It starts from the newest one that its own executable saved after verifying its root, audit, index entries and descendants. Any doubt, or a different binary, means a full replay ("Ignoring state checkpoints saved by another build"). A crash replays at most about 1,055 blocks.
- **Checkpoint hygiene (L049, L086, L089).** A state is audited before it is saved (a periodic save on its own thread, off the node lock); one that fails is not saved and the older checkpoints stay. The node keeps the newest two checkpoints and older ones about one per doubling of depth, the oldest at least a third of the way down to genesis (at most 16 in all, about 12 at a million heights), and a reorganization below the restored checkpoint rebuilds its fork point from the newest older one that passes its checks instead of from genesis, however deep the split. A save needs free disk space of twice the largest saved state plus 512 MiB; after a failure the WAL is truncated and periodic saves back off from 1,024 to at most 16,384 heights instead of retrying on every block. Failures are reported as `storage.checkpoint_error`.
- **Full disks and failed commits (L048).** The private `status` and `peerstatus` report `storage` (`degraded`, `failed_commits`, `failing_since`, `last_error`, `checkpoint_error`); public web `status` and `snapshot` show only `storage.degraded`. A failed block commit changes nothing; after eight in a row over at least a minute the node exits with status 74 for a supervised restart instead of running on a frozen tip whose miners' blocks are lost. Only a submission whose own commit failed can trigger the exit: a block refused for another reason after the disk was freed no longer restarts the node. Stratum and the development `mine` call keep issuing work while commits fail, so blocks found in that window (at most until the exit) are lost: refusing work would stop the failures that lead to the exit and leave a node without peers degraded until restarted by hand.
- **Side-branch storage (L047).** Besides 4,096 blocks, side blocks draw on a byte budget of 64 MiB (or four block capacities) refilled by one block capacity per active height, so they are admitted no faster than the active chain grows. Both budgets are stored and survive restarts, which no longer grant a new burst. Side blocks are declined, their headers held, while less than 512 MiB of disk is free. Every 64 new active heights the running node also deletes the stored side blocks that fell out of competition (as startup does), with the presync headers after them unless a header download pins them, so side storage stays bounded instead of growing until a restart: blocks carrying 1/64 of the next block's work last about 128 heights, about 2 MiB at 16 KiB blocks beyond the 64 MiB burst, where they previously added up to about 377 MB per day.
- **Startup.** The derived index rebuild commits in batches of 4,096 blocks and the WAL is truncated afterwards; invalid losing-branch blocks move to `rejected_blocks`; the SQLite build must be able to store the largest valid block. A full start deletes losing branches judged stale children first, so an interrupted start can no longer leave a stored block without its parent, which made every later start fail; such a block, left by an earlier interrupted start, moves to `rejected_blocks` ("parent block absent") instead (L013).
- **Deferred reorganization replays (L008, L017).** Rebuilding the fork point of a block that would become the tip, or of an admitted held chain, keeps its progress in records that side-block replays can neither take over nor flush from the recent-state cache, and the newest stored states of admitted held chains stay outside that cache until adopted, so relayed side blocks can no longer keep a minority node from reorganizing. Finding earlier progress reads at most one index entry per cached state instead of one per height.
- **File names.** Files beside a chain database are named from its full file name. `NAME.sqlite` keeps `NAME.wallets.sqlite`, `NAME.explorer.sqlite`, `NAME.peer-key.json`, `NAME.session-token`, `NAME.peers-CHAIN_ID.json` and the new `NAME.stratum-trusted.json`; any other name `F` uses `F-wallets.sqlite` and so on.
- **Explorer index** schema bumped (rebuilt at first start); transaction data is stored in its own table; reorganization recovery uses chain checkpoints; the worker is supervised and retries. A startup step that fails after the index database opens (detaching rows, indexing genesis, a catch-up block) is logged and retried by the worker instead of leaving Explorer, Mail and Chat unavailable until a restart (L030). Its write-ahead log is truncated to zero at startup, after each reorganization and every 64 blocks, which SQLite's own checkpoints cannot do while readers overlap; detached rows and their transaction data are deleted once 5,760 blocks below the tip, where they were kept forever; an encrypted-mail record no longer stores its data twice more, as `raw` and `data_hex`, which responses restore unchanged from the data row; and [its disk use](docs/EXPLORER.md) is documented: several times the chain's bytes, with hexadecimal keys and no switch to turn the index off as known limitations (L059). A Support whose record an earlier Propose or Support in the same block wrote is indexed without record weight, as consensus charges it, so its `minimum_fee` and the block's `minimum_fees`/`extra_fees` are no longer overstated (L078).
- **Dependencies.** `rusqlite` 0.39 with bundled SQLite 3.51.3 (CVE-2025-29087, CVE-2025-6965).

### Node, RPC and HTTP

- **429 and 503 refusals.** Admission refusals (cooldowns, exhausted request, byte or work budgets, connection quotas) are answered with HTTP 429 and `Retry-After`; busy shared capacity with 503 and `Retry-After: 1`; a charge that can never fit with 400. Accept-time answers are limited to one per `Retry-After` window per address. The CLI, web UI and faucet report the message and the wait.
- **Bent-curve clearing cost (S001).** A curve evaluation's logarithm series runs on 64-bit limbs, with one product and one division pass per term (the upper bound's chain derived from the lower one) and reciprocals for the small term divisors. Every bound, and so every clearing result, is unchanged: `tests/clearing_cost.rs` pins a digest of 931 clearings, including exhausted work limits and the widest 2048-bit search, made by the previous code. Clearing is about twice as fast at every magnitude; ordinary batches on a bent curve at launch magnitudes take well under a millisecond per world. The soak's 30 to 170 ms per clearing was measured on 0.42.0, whose logarithms always used 2048 bits. With the soak harness fixed (see [Validation](#validation)), three 20-minute soaks ran side by side on one loaded host, each with two nodes, chaos, seven or eight decisions and grants drawn from reserve. On this release, trades cleared on 342 bent-curve tips (reserve-to-mass ratios with denominators up to 21 bits); `broadcasttransaction` p99 was 52 ms and the genesis `getblock` probe p99 35 to 45 ms. 0.42.0 under the same load: 405 ms and 400 to 440 ms, with `getblock` p99 1.3 s during decisions. Alone on a quiet host, a 15-minute soak of this release passed all 21,610 checks over six decisions and 281 bent-curve tips, with `broadcasttransaction` p99 2 ms (at most 3 ms) and `getblock` p99 under 2 ms.
- **Lock scheduling (R02, R03, R07).** Newcomer selections share a node-wide lock-time budget (relays and the operator 200 ms/s, public broadcasts 50 ms/s); relayed newcomers queue; blocks are executed off the node lock; batch trades are cleared only when a template is built, outside the lock.
- **Block submission (L021, L090).** A copy or child of a block being validated goes on as soon as that block is stored, ahead of the transaction admission its storing starts, instead of waiting for that admission too. That admission runs on a thread of its own, so `submitblock` and a Stratum finder (its `mining.submit` reply and its new-tip job) no longer wait up to about 1.25 s for relay admission; the development `mine` method still returns after it. Reorg replay runs one historical block per node-lock hold, for a block that would become the tip as for a side block, instead of up to eight, so one hold never executes more than one historical block however costly; the 64 replayed blocks per submission are unchanged.
- **Mempool.** No hard count gate: selection ranks by miner fee per weight unit, then signed fee per weight unit, then transaction ID, with a backlog of 256 entries that lost only to capacity; spends from accounts that a pending transfer creates wait for the funding; a validity refusal holds that sender nonce for relayed and broadcast copies until the pool or tip changes.
- **Mempool admission hardening (L009, L012, L050 to L053, L088).** A backlog entry ranks no higher than its sender's earlier pending nonces and is kept only after them, so high bids chained behind a low one no longer push other senders' entries out and are then dropped as stranded; a sender's backlog entries are kept only while its opening balance covers them together with its selected ones, so a chain no longer holds more than its sender can pay for, and its chain past its first backlog entry keeps at most half of the backlog's entries and bytes. A same-nonce replacement must also outrank what it replaces by fee, so a minimal raise that earns the miner no more is refused at once instead of losing to the old transaction on its ID. The first of a sender's candidates whose selection attempts ran out after it failed gets one last attempt once nothing else is ready (one per sender), so a Support for a lower-ranked pending Propose is no longer dropped as invalid. A left-out Support or payment that may have failed only because another sender's left-out Propose or payment would have created its proposal or new recipient account stays undecided instead of being refused as invalid. Spends awaiting funding count a queued transfer only in nonce order after its sender's pending and earlier queued transactions, and only if the opening balance covers it together with them; holds whose funding is gone are dropped at the next admission, and a spend refused for want of holding room is refused only until the pool changes. Each relaying source, and public broadcasts together, hold at most a quarter of the holding bytes; relays together leave public broadcasts a quarter, and the operator's submissions and reorg recovery another quarter that no relay or public visitor can take; refused recovery holds are logged. A resent transaction refused for validity holds its sender nonce back only for other resent transactions, so variants refused for validity cost at most two selections per sender nonce and pool revision. While the selection's bytes, or its weight as its execution counted it, leave no room for a newcomer, one that does not outrank its weakest entry is refused without a selection, as for a count-full selection; so a block filled by account-creating payments no longer costs a selection per low bid. A public `broadcasttransaction` checks its reserved lock-time budget again when its turn for the admission lock comes and is answered 429 with `Retry-After` if it is spent.
- **RPC.** New `blockreceipt`; `account.pending_nonce`; keyed snapshots carry `sender_mempool`; `proposals` pages by round with a tip pin; `support` reports a status; fee quotes report `record_fee` and a `scheduled_change` due within the lifetime; large grants are summarized in snapshots; reads are priced by the work they do. Conditional trades are refused at a decision's last tip ("conditional trading is closed").
- **Quotes.** `fee_quote` and `transfer_quote` require `sender` on the private listener as on the public one; the fallback to the selected server wallet told any local process, without the session token, that account and its spendable balance (L024). Quotes and `preparetransaction` refuse a transaction whose weight (bytes plus 1,024 per created account, proposal or new support record, and grant recipient) exceeds the block capacity, naming the weight limit, instead of preparing one that admission then refused with a generic error. While the node's own miner account does not exist yet, as on a wallet-only or newly launched node, they also refuse one within 1,024 weight of capacity, the room that node's admission keeps for that account, and say so; it refused such a transaction at broadcast and never relayed it (L055). `scheduled_change` also reports a MinimumFeeRate or BlockBytes change that the next block passes when it resolves a decision; with a zero Rest that block also activates it, and no tip was ever in Rest to report it (L056).
- **`getblock` `format`.** `format: "hex"` returns `hash`, `height` and `raw`, the canonical block record, which the response limit admits for every valid block; `submitblock` accepts that object or `{raw}` back. The default JSON form is built only within the JSON page budgets (32 MiB of text, 2,000,000 values, about 2 MB of block) and paid per value; a larger block is refused with a pointer to `format: "hex"` instead of building a tree of tens of bytes per block byte, gigabytes for a large-data block (L045).
- **Development mining.** `mine` runs only on a development network that untrusted peers cannot reach, unless `--dev-rpc`.
- **Public website.** The node accounts each visitor named by the loopback proxy's `X-Real-IP` (6 sessions, a share of the budgets), keeps a quarter of the request, byte and work budgets for wallet calls, which page requests must leave too, and requires request heads within 5 seconds. Each active address is one share and a /24 or /48 counts at most four; a proxied connection whose visitor is refused returns its request unit. When all 32 sessions are in use, a newcomer from a network holding at least two fewer closes the oldest session of the network holding the most. Replies must be written within 5 seconds plus one per 64 KiB (at most 15); pages and scripts pay their bytes; replies over 64 KiB wait for slow readers within a 64 MiB allowance, of which one /24, /48 or local address holds at most a quarter, or one larger reply; explorer pages reserve their per-KiB work before they are built. Session tokens are never served over HTTP.
- **RPC work bursts** grow with governed capacity to admit one broadcast of a largest transaction (about 2 million units at 64 MiB blocks), on the private listener as well as for public visitors, so a valid large transaction is never refused, and its sender penalized, as larger than a whole budget. A public visitor's growth is for wallet-critical calls only: its explorer and governance reads stay within its ordinary burst, so one visitor cannot spend the shared pool in one burst.
- **Process health.** A poisoned lock or a panic in a long-lived task exits with status 70 for a supervised restart.
- **`peerstatus`** adds `transport_version`, `version1_peers`, `capacity_allowance` and listener accept errors; `chain_stalled` scales with the governed interval.
- **Memory limit check (L035).** At startup, every minute and whenever the validated capacity changes, the node compares its control group's memory limit (such as the unit's `MemoryMax`) with its resident memory plus what peers and public visitors can make it hold (128 MiB plus 20 times `capacity_allowance`). While the limit is lower it logs `warning: this node's memory limit ...` (repeated hourly), and `peerstatus` reports `memory` (`limit`, `resident`, `peer_fillable` in bytes and `short`), so operators raise the limit before governance raises capacity into an out-of-memory crash loop.

### Mining

- **Breaking for operators:** a non-loopback Stratum listener requires `--stratum-password-file`.
- Unauthorized connections use a separate 128-slot pool with a 10-second authorization window charged to a per-address budget; the 256 most recently authorized addresses, and `--stratum-trusted ADDRESS[/LENGTH]` prefixes, keep 32 reserved slots (persisted in `NAME.stratum-trusted.json`). Authorized workers ignore cooldowns, so a solved block is never discarded by a budget.
- Job retention retires the oldest same-parent job instead of flushing all; same-parent refreshes reach a connection at most every two seconds; rate-based vardiff; `blocks_found` counts only selected blocks.
- **Templates (L022, L071, L091).** Each template build is claimed for the tip it extends, so one parent is never built twice at once and an older build never replaces a newer one. A build that a new tip overtakes stops at its next step on every attempt. After three such builds, counting each wait for another request's build of the same parent that a new tip overtook, as during catch-up, Stratum and the development `mine` method get an empty template for the current tip, which is not stored, and Stratum asks for the full one at its next refresh. A template that cannot be finished with its whole selection logs the first transaction it left out, and later templates for that tip leave it out with its sender's later nonces; they stay pooled for the next tip.
- **Authorized worker slots (L037, L041).** Workers from outside the `--stratum-trusted` prefixes hold at most 16 authorized slots per IPv4 /24 or IPv6 /48 (refused with "per-network mining worker limit reached") and, when any prefix is trusted, at most 48 of the 64; the other 16 stay for trusted prefixes. When the slots a newly authorized worker may use are full, it replaces the competing worker that has gone longest, and at least five minutes, without a valid share since it authorized; that connection closes. A new worker from outside the trusted prefixes counts as idle from the earliest authorization among its group's workers that have sent no valid share, including those that left, until an hour after the last of them left, so reconnecting or replacing its own idle workers does not restart the five minutes. Squatting without work then costs a fresh /24 or /48 for every 16 slots every five minutes, but no slot is guaranteed except the 16 that `--stratum-trusted` reserves. A trusted worker, once authorized, no longer counts toward its address's 16 or its /24's 64 connections and pays only its own session limits, so a rental proxy behind one trusted address can connect more than 16 rigs.
- **Shared budgets (L038).** An authorized worker whose address or /24 budget other connections exhausted gets a rate error for its non-block shares instead of being disconnected, and the refusal penalizes no one; a block it finds is still submitted.
- **Trusted prefixes (L082).** `--stratum-trusted` (`STRATUM_TRUSTED`) refuses a prefix shorter than IPv4 /16 or IPv6 /32 outside loopback, private, CGNAT, link-local and unique-local networks, such as `0.0.0.0/0`; the new `--stratum-trusted-broad` (`STRATUM_TRUSTED_BROAD`) accepts one deliberately.
- **Several worker names (L085).** One connection may authorize up to 64 worker names, each with the password, and submit under any of them; proof of work is checked before the name, so a solved block is submitted whatever name it carries.
- **Vardiff (L087).** Rates are judged on samples of at least 16 share intervals over 30 seconds, and the multiplier rounds down to keep about one share per second or more. A stream above eight shares per second is raised sooner, measured over at least two seconds and by at most eight times at once, so a batch of shares from a proxy or after a stall cannot raise difficulty 64 times. Raised difficulty halves again while shares average fewer than one per two seconds over two minutes.
- **Extranonces (L042)** start at a random value in each process, so nodes paying one key do not hand out identical first jobs.

### Command line and genesis

- `init`: `--preset slow` requires `--hashrate` or `--uncalibrated`; `--hashrate` caps the easiest target at 256 times the calibrated one; `--genesis-time`; warnings for an easy limit (naming the minimum rate, 73.4G at 15-second blocks), a future genesis and unsafe but valid genesis values.
- `run`: refuses a non-loopback `--p2p` or `--peer-discovery` on an easy proof-of-work limit unless `--allow-easy-target`; `--preflight` makes every pre-database check and exits; refuses a peer identity equal to a wallet key, an empty or malformed Stratum password file, and warns when `--public-web` serves plain HTTP on a non-loopback address.
- RPC client: plain HTTP only to loopback unless `--insecure-http`, no proxies or redirects, bounded replies; `send`, `transfer` and `prepare` cap automatic fees (`--max-fee`), accept `--nonce` and `--anchor-url`, require a network pin for a non-loopback `--url`, verify remote nonce claims and print a review before signing.

### Deployment

- `deploy/linux/install.sh` pins 0.43.0, stages every input in a private directory before hashing and installing it, runs the service's own `run --preflight` in `--check`, and never replaces existing files. The unit adds system-call, namespace, `/proc` and core-dump confinement, restart back-off (`RestartSteps=8`, `RestartMaxDelaySec=2min`) and an out-of-memory message.
- `node.env` gains `ALLOW_EASY_TARGET`, `STRATUM_TRUSTED` and `STRATUM_TRUSTED_BROAD`; the launcher refuses a `STRATUM_TRUSTED` prefix shorter than IPv4 /16 or IPv6 /32 outside local networks. The nginx template overwrites `X-Real-IP`, limits each client to 2 JSON-RPC requests per second (burst 20) and 6 connections, caps its connections to the node at 32 with an `upstream` block's `max_conns` (503 with `Retry-After` when all are in use, but a plain 502 when the node closed a connection that had reached it, since that request may have run) instead of a connection limit shared by all clients, which a few slow clients could fill, keeps request and reply buffering on, and needs nginx 1.15.7 or later. The unit and README give the memory headroom that peers can fill at a governed capacity: at least 128 MiB plus 20 times the greatest validated block capacity above the measured peak; the node warns, and `peerstatus` reports, while its limit is lower.
- `scripts/release.sh` builds the release binaries reproducibly (`--locked`, pinned toolchain, remapped paths, no `test-fixtures`) and writes `SHA256SUMS` and `BUILDINFO`; `--verify` rebuilds and compares.
- `scripts/launch-kit.sh` generates a public network's per-server files from the seeds' public IPv4 addresses, the web host and the calibration hashrate: discovery `node.env` files (each seed advertises itself and seeds from the others, optionally pinned), Stratum settings, ufw rules, the nginx site with the faucet routes, the faucet configuration and the new confined `deploy/linux/hashstash-faucet.service`, an archive script for earlier installations and a numbered `INSTALL.md` per server. With the release binary it creates the genesis once and fills in every hash. It validates its inputs strictly, never embeds a secret and never overwrites. Stratum runs on every seed except the web host unless `--stratum-hosts` says otherwise; the faucet is funded by a transfer prepared on the web host, signed offline with `hashstash-cold` and broadcast, so the payout key never comes online; each kit is copied into a new directory of its own on the servers; and staged peer identities and Stratum passwords stay in `/root/hashstash-keys` until the announcement, so a reinstall reuses them. `scripts/test-launch-kit.sh` covers it and, with a real build, runs each server's rendered install steps up to the installer's check (also run by `tests/operator_files.rs`); `scripts/launch_rehearsal.py` rehearses a kit on one machine, including outsiders joining with the published command and through gossip; and [launch day](docs/LAUNCH-DAY.md) gives the launch sequence, with a rehearsal on the real servers two days before.

### Faucet

- Reorg-safe accounting: consumed nonces are reconciled on every refresh, reorganized receipts relocated or expired, and each nonce pays at most one claim. New operator commands `--inspect`, `--accept-spent-nonce` and `--clamp-future-claims`.
- Limits: `subnet_daily_claims` per IPv4 /24 or IPv6 /48 (default 10), exact fee and capacity checks before signing, claims deferred before a scheduled fee or capacity change, 64 connections with a 5-second head deadline, and 429/503 handling. IPv6 is grouped by /48, as network admission groups it, and a 6to4 address by the IPv4 /24 it embeds: grouped by /56, one free tunnel-broker or VPS /48 held 256 daily network shares, more than the whole daily allowance (L031).
- A reserved claim's answer waits at most two seconds for its first broadcast, and never past one second before the 15-second request deadline; a busy node's `Retry-After` and resend continue in the background, so a reserved payment is no longer answered as "still being checked" (L077). A claim the faucet could not reserve within the deadline, queued behind other claims or slow to prepare, is still answered 503, and its outcome is read from status. A reorganized receipt behind a newer pending claim is documented as left to the nodes' pool recovery (L061).

### Wallet and interface

- Nonces predicted from the whole pool, quoted weight re-derived before signing, submissions followed by sender nonce ("No longer pending", "Mined or replaced"), governed bounds checked before signing, partial grant summaries, fee-locked outcome accounts named, mail scans that resume at fork heights, and visible escapes for bidirectional and invisible characters in Chat, Mail, proposals and the Explorer.
- **Broadcasts of unknown outcome (L004).** Only the node's own 429 or 503 refusal, which carries the request's JSON-RPC ID, means a broadcast did not run ("Not sent"). The public website template's 503 for an upstream 502, which nginx also returns when the node drops a connection after the broadcast reached it, carries no ID and does not. Any other failure (a lost connection, a gateway error, or a 200 JSON-RPC error such as the public site's "public response byte budget exhausted; try again") is reported as "Result unknown" instead of the node's text: the form keeps the signed bytes, offers to send the same bytes again (which is idempotent), and signs nothing new until the snapshots settle it; only then is the node's reply shown. A pending row at its nonce counts as this transaction only when its fee, anchor, lifetime and operation match the signed bytes; another transaction there, such as one sent from another tab, releases the form as "Not pending" and keeps a mail draft. A used nonce is looked up by transaction ID ("Mined", which clears an unchanged mail draft, or "Transaction number used" when the explorer cannot tell), and two later snapshots showing the nonce free release it. The tracker keeps the network the transaction was signed for, so another tab's wallet change during the broadcast no longer drops it. Before, the natural retry signed a second transaction at the next nonce, so a payment, trade, bid, proposal or mail could be made twice. Advanced → Broadcast reads its outcomes the same way.
- **Retry-After in the web interface (L028).** A 429 or 503 pauses the periodic refresh, the Chat feed and Explorer reloads for its `Retry-After` (at most a minute); explicit refreshes and navigation are still sent. A refused Mail page is sent again from the same position after the wait instead of at the next block, and so is a page whose reply the node replaced with a 200 error asking to try again (reply allowance or byte budget spent, explorer index updating), after 1.5, 3, 4.5 and 6 seconds. On a public website the Mail scan sends at most 8 pages at once, then one every 1.5 seconds, counting every further 4,160 KiB of envelopes as another page.
- **Browser key protection (L072, L074, L075, L076).** Changing or removing the browser wallet passphrase needs the current passphrase; **Lock now** locks every open page of the site that holds the network's passphrase open. The 30-second clipboard clear of a copied private key no longer erases what was copied after it: it clears unasked only while the page kept focus and nothing was copied or cut in it since, and otherwise asks (**Clear clipboard**, **Keep**); leaving the page before the clear asks first, and the backup dialog warns that closing the page leaves the key on the clipboard. The guide describes the optional passphrase, its idle lock and what it does not cover.

- Continuous integration (`.github/workflows/ci.yml`): formatting, Clippy in both configurations, Linux and Windows suites, frontend and Python checks, a test pass with debug assertions, the byte-for-byte rebuild of the browser cryptography bundle with the pnpm that `package.json` pins, the Stratum worker, cross-process discovery and production-issuance programs, every PowerShell launcher test under Windows PowerShell 5.1, network suites, and fuzzing. Every action is pinned to a commit and every toolchain and tool to an exact version (Rust 1.97.1, Node.js 22.22.1 with its corepack, Python 3.12.15, nightly-2026-10-10 and cargo-fuzz 0.13.2), and each check is its own step, so a later passing command cannot hide a failing one. A push of a `v*` tag or a `release/*` branch runs the full gate, per-target fuzzing and network suites included, on exactly that commit.
- **Chaos soak on 0.43.0 (S001 follow-up).** `scripts/soak.py` signed in 0.42.0's network-independent domain, so a 0.43.0 node refused every soak transaction ("invalid transaction signature for this network"), no world ever opened and no trade was cleared, while the run reported only unrelated failures. It now signs `tagged_hash("Hashstash/chain-bound-transaction", chain_id || body)` for the chain ID its binary reports; its startup self-test, `scripts/test_soak.py` and the new `tests/transaction_signing_vector.rs` all check one shared vector (`tests/data/transaction-signing.json`), and a new `signature_accepted` check fails the soak if a node refuses any harness signature. Two invariants still encoded 0.42.0 rules and now follow this release: `grant_capacity` is revenue plus half the reserve rounded down (it was revenue plus reserve less one), and `mempool_capacity` allows the next-block selection plus a backlog of at most one block's bytes (it allowed one block). The report counts tips on which trades cleared on a bent curve (`governance.bent_curve_tips`).
- **Release requirement:** the launch commit needs a green full-gate run, recorded in [the release gate](docs/VALIDATION.md#release-gate). The workflow had not yet run on GitHub when 0.43.0 was prepared.
- Sixteen coverage-guided fuzz targets: every parser of hostile input; `peer_sync`, which synchronizes a fixture node from a scripted hostile peer through header replies, the held-header store and block validation; and `peer_serve`, which connects to a fixture node's peer port as a hostile host and sends header requests with hostile locators, versions and declared capacities, a locator request and its push, and address requests, checking each reply against protocol order, the declared capacity and the active chain. After either session the node's tip, a replay of its active chain and its held-header bounds are checked. A stable seeded runner in the test suite runs them all, with kept regression inputs.

### Specification

No rule changes: these entries document the rules exactly as the node applies them, and known-answer vectors computed by independent models written from the documents (`scripts/clearing_model.py`, `scripts/consensus_model.py`, checked by `scripts/test_consensus_models.py`) pin them against the node.

- **Batch clearing is specified step for step (L016, L067).** The [reference clearing algorithm](docs/SPECIFICATION.md#reference-clearing-algorithm) is normative pseudocode with every constant: the 2^(2b+32) price grid, the bracket (a two-sided net buy's D/B cap never binds, since the closing-price bound is always lower, so implementations may omit it), the Newton step, the directed logarithms, the small-ratio rule, the order of neighbour probes and the budget search's gap, Illinois weights and stop rule. Comparisons decided by integer checks stay decided after the 1,024 curve evaluations are spent, and the limit counts curve evaluations only, not all clearing work. Vectors in `tests/data/clearing-vectors.json` pin fills, closing curves and evaluation counts for flat, curved, dust, bound- and range-limited, full-redemption and exhausted clearings (`tests/clearing_vectors.rs`).
- **Auction transitions (L015, L063, L066).** A new [auction evaluation](docs/CONSENSUS.md#auction-evaluation) section gives every committed value an auction writes: opening fields, round numbering, refund heights, `lead_since` after a cancellation, and exactly when entries leave the committed `displaced` list. Entries of cancelled proposals leave it lazily and are part of the state root. A leader chosen in a block can always open in that block, so the documented cancellation of a mature leader, with the next leader chosen a block later, cannot happen; that unreachable branch is now a debug assertion. State-root vectors for a scripted 43-block chain pin each transition (`auction_transition_vectors` in `src/consensus.rs`).
- **Miner-account weight (L064).** Grant settlement that creates the miner's account charges its 1,024 weight to the block even when the block pays the miner nothing; a zero reward creates no account.
- **ASERT (L083)** is written out as exact integer pseudocode, with vectors for its rounding, cutoffs, floor and clamp. Its compact rounding is written out too: it keeps three significant bytes, or two when the leading one is 0x80 or more.
- **Records (L068).** A Refund removes its support record, which cannot be created again; proposal and round records are never pruned.
- **Fork choice and restart (L034, L083).** [Specification](docs/SPECIFICATION.md#12-records-storage-and-networking) sections 1 and 12 state the held-header bounds (65,536 counted or admitted headers, plus 32,768 presync headers) and their operational consequence: a heavier branch that needs more than 65,536 headers past a node's stored fork point before it claims more work than the node's tip is not followed automatically. After a partition longer than about 11 days of evenly split 15-second blocks, and longer when the split is uneven, operators on the lighter side must resynchronize their nodes: an empty database in pinned mode, with the node's existing `--peer-key-file` and a `--peer` and `--peer-pin` for each heavier-side endpoint, without `--peer-discovery`, until the node reaches their tip. Explicit peers without a key file cannot do it, since every pinned or discovery node refuses unauthenticated transport. Section 12 and the [launch runbook](docs/LAUNCH.md#14-incident-response) give the steps. It also states that startup deletes losing-branch blocks that fell out of competition.
- **Library API (L065).** `tree::Map::proof` and `tree::Proof` are test-only: nothing served them, and they prove inclusion only, without naming their map.

### Accepted limitations

These are documented design limits that this release does not remove; tell users about them. See [the launch runbook](docs/LAUNCH.md#15-limitations-users-must-be-told).

- Stash orders have no limit price or minimum output; orders sharing a block, which a miner can arrange, move each other's price within the per-block bound.
- The default PASS margin is 0 basis points. On flat or nearly flat curves integer rounding alone can move a price, and at the genesis exchange rate nothing moves, so a revenue-funded grant or setting change on that baseline resolves FAIL.
- A bidder with liquidity can delay another proposal's opening until the auction timeout at the cost of fees.
- Each block issues whole atoms of one petahash of expected work; the remainder is discarded, which loses a large share of issuance on a small network.
- A node follows a heavier branch by itself only if that branch needs at most 65,536 headers past the node's stored fork point before it claims more work than its tip. After a partition of more than about 11 days of evenly split 15-second blocks, nodes on the lighter side stay there until their operators resynchronize them by hand.
- Peer transport is authenticated but not encrypted, and Stratum V1 is plain TCP.
- Mail has no forward secrecy: a compromised account key exposes past mail.
