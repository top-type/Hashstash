# Network resource controls

Hashstash bounds local resources used by untrusted peer, RPC, and mining traffic. These are node policies: exceeding a traffic budget does not make a block invalid.

## Isolation and admission

RPC requires a loopback listener, including on nodes without an enabled wallet. RPC, peer traffic, and Stratum use separate session and worker capacity. Per-IP counters are scoped to each service; a peer cooldown cannot also disable wallet access from that IP. IPv4-mapped IPv6 addresses share the IPv4 counter, and a global-unicast IPv6 source shares one counter with its whole /64, because one host normally controls that prefix. Connections this node opens use records separate from inbound traffic from the same address, so inbound abuse or a cooldown caused by another host behind a shared address cannot block this node's own synchronization with it.

Admission checks run before large reads and expensive work. Request, byte, and work budgets refill over time. Accounting is bounded to 1,024 address/service/direction entries, and active entries cannot be evicted; when the table is full, an inactive entry whose cooldown has ended is replaced before one still cooling down. Temporary cooldowns increase from 250 milliseconds up to 16 seconds. They apply to malformed frames or payloads and explicit resource violations; ordinary stale transactions and competing branches are not grounds for a permanent ban. A failed authenticated handshake closes without a cooldown, because nothing has been proved and the source address may be shared; connection-rate limits still apply. Exhausting the budget for a reply this node chose to send fails that reply without penalizing the recipient. Configured-peer retries back off with jitter rather than reconnecting at a fixed rate after every failure. Stratum requires authorization within 10 seconds; an expired attempt or a failed password closes the connection and starts a cooldown for that address. Connections awaiting authorization have their own pool and leave it once authorized, so unauthenticated sockets cannot occupy authorized worker slots. A non-loopback Stratum listener requires a password. Authorized solo miners can remain connected while waiting to find a block.

Inbound peer sessions use 16 general slots. At most two concurrent sessions may come from one public network group (IPv4 /16, IPv6 /32); loopback and private sources keep per-address limits only. When the general slots are full, configured peers, pinned peers and discovery peers this node synchronized with during the last hour can use four reserved slots. Each inbound session has an absolute deadline of twice the peer read allowance, and its handshake and first message share one read allowance. An outbound synchronization, including its wait for one of the two outbound slots, has an overall deadline of five read allowances. Accept errors never stop a listener or abort its live sessions: a reset or aborted connection is skipped, other errors back off from 10 milliseconds to one second, and counts and the last error appear in `peerstatus.listeners`. Stratum extranonces are allocated only for mining sessions and skip values held by connected sessions, so no listener depends on a lifetime connection count. Only peer synchronization failures enter the `peers` diagnostic ring; web and mining clients cannot push them out.

| Local policy | RPC | Peers | Stratum |
| --- | ---: | ---: | ---: |
| Concurrent sessions per node | 8 | 16 incoming plus 4 reserved, 2 outgoing | 64 authorized, 128 awaiting authorization |
| Concurrent sessions per IP | 8 | 4 | 16 |
| Request units per second / burst | 512 / 1,024 | 32 / 64 | 32 / 64 |
| MiB per second / burst | 32 / 66 | 8 / 66 | 1 / 2 |
| Work units per second / burst | 131,072 / 1,048,576 | 16,384 / 65,536 | 1,024 / 8,192 |

The table gives baseline byte bursts. The private node's RPC and peer byte bursts grow with the highest validated block capacity. They cover the greater of the 66 MiB baseline, the peer frame allowance, or twice that capacity plus 128 KiB for a hexadecimal JSON envelope and 16 KiB for HTTP headers, within the host's allocation representation. A published capacity increase refreshes the allowance immediately; refill rates and other quotas do not change. Public-web uses a separate guard with a 66 MiB byte burst. Connection admission also consumes a request unit. Each Stratum session has a further limit of 8 requests per second with a burst of 16. Peer byte and work budgets cover replies as well as incoming traffic, preventing small locator requests from generating unlimited large responses. A message costs one work unit per loose transaction and per block plus its transactions; a receiver also charges its current mempool size when loose transactions arrive. One reply's block work is limited to 16,384 minus 256 loose transactions and the 4,096-entry mempool, so a complete reply fits one second of peer work refill; the first block is always sent. The peer work burst grows, if needed, to admit one block at the genesis signature limit with a full loose batch and mempool. Buffered inbound peer frame bytes across all sessions are limited to the greater of 64 MiB and twice the largest validated frame allowance; a frame beyond that budget closes without a cooldown. Work units are operation-cost estimates, not hashes or wall-clock CPU measurements. There are two parser workers per service, four RPC read workers, two RPC mutation workers, two peer workers, and two mining workers. Worker permits remain held until the work finishes even if a connection closes.

The configured Stratum reporting difficulty defaults to 65,536. Choose it for the expected hash rate and traffic budget; a connection whose accepted reporting shares reach 16 within eight seconds has its difficulty doubled for new jobs. Each job's reporting difficulty is capped at network difficulty so every block solution is reported. BIP310 minimum-difficulty negotiation must remain compatible with the fixed genesis target limit, including when timestamp ASERT makes mining easier. An extremely easy chain therefore needs an appropriate starting target before ASIC-scale mining. Valid non-block shares are acknowledged without executing the block. Each job caches its coinbase fragments and retains its assigned reporting target. A connection keeps its eight most recent jobs; a parent change discards previous jobs, while a same-parent refresh retires only the oldest. Same-parent template refreshes reach a connection at most once every two seconds. A solved block waits for a mining worker without a deadline, and its work charge cannot discard it. Duplicate header tracking spans job IDs on the same parent. Worker records are removed on disconnect, and hashrate samples use a bounded rolling window. Reporting shares never create issuance or alter fork choice. See [mining setup](MINING.md).

Wallet status, account, governance, quote and transaction-preparation reads use one immutable published view. They can return the latest completed state while another worker validates incoming history. State-changing requests and historical block reads can still wait for chain access. The view is published after accepted changes, including accepted blocks preceding a later rejected block in the same peer exchange. Tasks on the asynchronous runtime never wait for chain access: peer frame limits and exchange deadlines use the published configuration and the greatest validated capacity, Stratum stale-job checks compare with the published tip, and server-wallet reads run on blocking workers. A hot-wallet submission copies its key and releases the wallet store before waiting for chain access.

A panic while chain, snapshot or wallet state is held may leave that state partially updated. The next access ends the process with exit status 70 rather than leaving a running node that cannot validate, mine or accept changes; restart revalidates history from disk. The [Linux service](../deploy/linux/hashstash.service) restarts failed exits without a start limit.

Read work that depends on operands or state size is charged once it is known and before it runs. On a curved Stash (reserve below curve mass), each exact curve evaluation costs 512 work units: account valuation one, `stash_quote` three plus its trade, and a single-order trade estimate two when the order cannot move the price by half the per-block limit, otherwise up to one per input bit for the executable-budget search. A curved `quote` deposit is also limited to the world's total account cash. Governance projections pay one unit per inline grant payment. Proposal and mempool pages pay one unit per row and per grant payment, plus one per 32 data bytes for full JSON mempool rows or one per 512 bytes for hexadecimal rows. The state root, governance projection and a by-round proposal index are built at most once per published tip. Public-web responses are also charged to the byte budget, like peer replies; an exhausted budget returns a short error instead of the result. The HTTP response limit is the greater of 193 MiB and the hexadecimal envelope of the largest valid transaction at the current capacity. Public-web errors from local storage, such as an unopenable explorer index, are reported generically and logged locally.

## Parsing and validation

Frame lengths are checked before reading their payloads. Binary peer messages receive a structural preflight before deserialization: counts, record lengths, transaction-data lengths, amount encodings and compact integers must fit their field and network limits. An amount's byte length is bounded by its containing record and network allowance; monetary and share ranges are enforced by validation after decoding. Canonical record decoding then rejects malformed values and trailing bytes. Parsing and expensive mining/peer work run on bounded worker pools.

Governed capacity bounds canonical block bytes and transaction execution weight. A complete signed transaction must fit the block’s remaining byte and weight capacity. Peer record admission is the greatest validated governed capacity plus 1 KiB of record framing. That capacity is the greatest in the active chain's history, so history can be relayed after a reduction, together with that of losing branches that remain competitive: within six next-block works of the tip, with a leaf block carrying at least a quarter of that work. A branch about to overtake can therefore deliver its larger blocks, while a cheap or abandoned branch cannot raise the allowance. The value is recomputed after every accepted block, falls again when such a branch is left behind, and is rebuilt the same way on restart. At the 16 KiB preset capacity a whole peer frame is at most about 3 MiB. The four-byte peer length field still permits at most `u32::MAX` payload bytes, including message framing. A valid record beyond that representation cannot be sent by this peer format; this is a transport error, not a consensus-invalid block.

Incoming batches allow at most 32 blocks, 256 loose transactions and 128 locator hashes. One synchronization frame carries at most 2 MiB of block records, or a single block when one block of the validated capacity is larger. A connection's first message must be a locator request or an address request: its read is bounded by the locator overhead plus the loose-transaction allowance, and a first message carrying blocks is rejected with a cooldown. A locator is matched through the header index; answering it never decodes a matched block body or reconstructs historical state. The recipient validated the common ancestor, so its allowance covers the genesis capacity and the ancestor's post-state capacity, which must also cover the next block's body; the reply uses that lower bound, or the current capacity when the ancestor is the tip. During catch-up, outgoing batches therefore stop before a block requiring a newly increased capacity so the receiver can validate that increase first. Loose transactions can accompany catch-up blocks if they fit that allowance and the frame's remaining capacity. Larger transactions are postponed while the relay cursor advances so smaller records can still be sent. The normal 512 KiB transaction budget expands to admit a single larger transaction within the peer allowance. Every frame must still fit the wire representation and local byte/work budgets. A received block must meet its own compact target within the genesis target limit before it is copied or its full record is hashed under the node lock. Blocks already stored on the active chain are skipped and never become download cursors, so resending known history cannot displace competing-branch downloads.

RPC and Stratum use JSON. Their preflight bounds nesting depth, encoded string length, container size and total value count before deserialization creates a tree. The maximum nesting depth is 64. General strings are limited to 1,024 decoded bytes and 6,144 encoded bytes, arrays to 100,000 entries, and objects to 128 members. Designated raw-transaction and transaction-data hex fields are bounded by the actual request body; completed transactions must still fit current governed capacity. Other fields retain the general bounds. RPC/mining trees have a two-million-value budget. Transaction RPC request bodies are checked before allocation against twice the current governed block capacity plus 128 KiB of JSON framing, with checked allocation arithmetic. HTTP responses retain a 193 MiB service limit. Collection pages normally target 32 MiB; a single larger record can be returned by itself subject to the remaining response and JSON-value limits. Wallet management requests, HTTP headers and mining messages retain smaller limits. Peer response serialization also runs on bounded workers.

HTTP parsing is strict: the request line has exactly three tokens separated by single spaces, `Content-Length` contains only decimal digits, and chunked bodies and duplicate headers are rejected. A POST is routed, and a wallet request authorized, before any body byte is read; an unknown path returns 404. Bodies are read as bytes arrive, so a claimed length allocates nothing in advance. After an early error the node ends its write side and discards up to 256 KiB of remaining input for at most one second, so the error response is delivered rather than reset. Each connection serves one request.

The command-line RPC client bounds replies from the endpoint it calls. It counts JSON values before building a tree. Fixed-shape replies such as `status`, `account` and broadcast results are limited to 1 MiB and 65,536 values. Preparation replies are limited in proportion to their request. Pending-nonce discovery may read at most 386 MiB of mempool pages and take at most five minutes in total, however the endpoint paginates. The generic `rpc` command keeps only the 193 MiB response frame. The client follows no redirects and no environment proxies. It sends plain HTTP only to loopback IP addresses unless `--insecure-http` is passed.

The generic HTTP `submitblock` endpoint retains the RPC request and value budgets, so it cannot accept every large block that the binary peer interface can relay. A large template returned by RPC is not guaranteed to fit a later HTTP submission. Built-in Stratum submits solved jobs directly and does not have this HTTP limitation.

Transaction selection reuses one prepared state for candidate transactions. It authenticates each unique candidate at most once per selection and applies each attempted operation atomically. A selection accepts at most 8,192 input candidates. Only opening funds can be committed, so a candidate whose fee and inputs the sender's opening balance cannot cover is dropped before ranking, whatever fee it declares. The rest wait in per-sender nonce queues; only each sender's next nonce is ranked. A failed operation is retried after later acceptances, but each sender has its own budget of four attempts per candidate it submitted, so failing candidates cannot exhaust the attempts of other senders. Creating an account reprices only payments to that account. Reverse nonce order and state-dependent failures cannot trigger repeated validation of ever-growing block prefixes or rescans of the whole candidate list. If the accepted set cannot be finished as a block, selection keeps the longest finishing prefix it finds, down to an empty block.

The pool is the next-block selection, at most 4,096 transactions, plus a backlog of at most 256 previously pooled or recovered transactions that lost only to block capacity, within one block's bytes. A backlog entry competes again in every later selection until it is included, outbid at its nonce, or expires; when an unsaturated selection leaves byte and weight room that an entry would fit, the entry was refused for validity and is dropped with its sender's later nonces. A new transaction that does not win a place in the next block is refused rather than queued. There is no separate count gate: a better fee rate displaces the weakest entry. Relayed transactions are authenticated before the node lock is taken. Selection runs only when an unseen entry also passes size, anchor, lifetime, funded-sender and unused-nonce checks, and the published pool and cached template change only when the selection does. Up to 4,096 refused relay identities are remembered: forged or malformed records permanently, other refusals until the tip changes. Preparation reads the published pool and does not reselect it.

Reorg recovery walks header metadata to the fork point and loads each detached body once, oldest first so nonce predecessors precede successors. Anchor and nonce checks drop stale entries before any signature check, at most 16,384 detached blocks and transactions are examined, and one selection rebuilds the pool. Detached transactions beyond that bound are not recovered locally; peers can relay them again. An accepted block stays accepted when recovery fails: the earlier entries are kept and revalidated by the next selection.

Transactions directly encode one of six operations and a raw data vector. Decoding rejects unknown tags, malformed and noncanonical encodings; operations cannot nest. Signing commits the exact fee and every data byte within block capacity. The weighted capacity rule additionally counts 1,024 units for a new payment or mining account and for each proposed grant recipient. Mandatory grant settlement is exempt from the settlement block’s weight because the proposal prepaid its capacity. These consensus rules complement the local traffic budgets.

A cache holds up to 128 permanently invalid block messages for up to 60 seconds. Its key covers the entire canonical block message: an invalid body cannot poison a later correct body carrying the same header. Unknown parents, future timestamps, local storage errors, deferred history reconstruction and side blocks declined by the admission policy below are not permanently cached as invalid.

A block that would not become the tip is fully validated and stored only while its branch is competitive. It must carry at least 1/64 of the work of the active chain's next block, and its branch must be able to overtake the tip within 4,096 further blocks of its own work. The check uses proof of work verified first and runs before any ancestry walk, state reconstruction or storage, so cheap blocks from old forks, whose timestamp error lets ASERT reach the easy target limit, cost no validation or disk. This is local policy, not consensus: extending the tip and switching to a heavier branch are never refused, and a declined block can be offered again when its branch becomes competitive. A heavier branch whose early blocks are more than 64 times cheaper than the active chain's, or that forked more than 4,096 of its blocks' work behind, is not followed automatically. Work can only price side blocks where blocks carry real work: on a network whose target is already at its easy limit, as on the presets, every block costs about two hashes and siblings near the tip remain cheap to store. Use a calibrated starting target for public networks.

Historical parent-state reconstruction replays from the nearest retained state: the tip, one of 128 recent states (least recently used are evicted first), or an active-chain checkpoint. Checkpoints keep every state within 32 blocks of the tip and two per doubling of depth beyond it, so an ancestor costs about its depth below the tip to rebuild, never the chain height, and side-branch traffic or other reconstructions cannot evict them. The ancestor walk on a side branch is charged against the replay budget too, one step per 16 entries. Deferred reconstruction keeps its progress outside the recent cache and resumes on retry; a change of the active chain beneath it restarts the work. It does not impose a maximum reorganization depth. Accepted history is still retained and independently checked. Peer locator requests never trigger reconstruction.

Accepted header/branch metadata uses a 256-entry memory cache backed by a derived SQLite index. Each entry carries a skip link, so anchor ancestry on a side branch is resolved with a logarithmic number of index reads rather than a walk over the branch. Canonical heights also live in SQLite rather than an ever-growing memory vector. Deep replay paths use a disk-backed temporary table; canonical reorganization walks disk metadata without constructing a whole branch in memory. SQLite's main page cache is limited to 8 MiB. Every startup rebuilds these derived indexes from fully validated saved block bodies, including losing branches. The rebuild commits in batches of 4,096 blocks, so the write-ahead log stays bounded (a 64 MiB journal limit applies after checkpoints) and is truncated once startup completes; an interrupted rebuild is simply repeated. A stored losing-branch block that fails current validation, and its descendants, move to a `rejected_blocks` table with a log line; a failing block that the persisted tip depends on, or one claiming more work than it, still stops startup. A stale tip hint is replaced by the replayed best tip. Cache eviction neither deletes blocks nor rejects a valid higher-work branch. This bounds the header-index and traversal components, not the live account state, all allocator overhead, or total process memory. Disk history and startup replay time still grow.

## Binary peer transport

Each payload begins with the eight ASCII bytes `HSP2PBIN`, followed by a one-byte message tag: `0` for synchronization, `1` for acknowledgment, `2` for an address request, or `3` for an address response. An acknowledgment has no further fields. A synchronization payload contains the 32-byte chain ID, then locator hashes, block records and loose transaction records, in that order. Each collection starts with a canonical compact count. Locator hashes are fixed 32-byte values; each block or transaction has a compact byte length followed by its unchanged canonical binary record.

Address exchanges use a separate short authenticated connection after a successful synchronization. Requests contain chain ID, a random per-process 32-byte node identifier, a one-byte presence flag and optionally one endpoint. Responses contain chain ID, node identifier, a one-byte count, then at most 32 fixed 18-byte endpoints (16-byte IP, IPv4 represented as mapped IPv6, then two-byte big-endian port). Zero ports, invalid flags, oversized counts, truncated records and trailing bytes are rejected. The exact count times record size is checked before allocating the address vector. Discovery replies have a separate 650-byte payload ceiling. Both directions verify chain identity; transport identities and discovery identifiers reject self connections. Discovery messages are never accepted in the middle of a synchronization exchange. Peers that do not implement discovery can still use unchanged configured synchronization with a compatible authenticated policy.

Unpinned frames use a four-byte big-endian payload length followed by the payload. Pinned frames use the authenticated 76-byte frame header described below, followed directly by the same binary payload. They do not add a second length prefix. No newline or JSON representation is used on either peer path.

Both peer paths require this binary envelope and a matching chain identity. Transport authentication is separate from economic consensus. RPC and Stratum use JSON interfaces.

## Pinned peer authentication

For a fixed operator-managed network, give each node its own dedicated transport identity and pin the other nodes. Run key generation as the service account in its private data directory:

```sh
hashstash peer-keygen --out /var/lib/hashstash/peer-identity.json
```

The command prints only the public key, creates the file without overwriting anything, and uses a distinct file format that wallet-key loading does not accept. On Unix the file is owner-only. On Windows it inherits its directory's access control, so keep it in a private directory such as the service profile. Never reuse mining, faucet, activity or visitor wallet keys. Peer identity loading rejects symbolic links and reads through one handle that must still be the regular file it inspected; on Unix it also rejects group/world-readable files. Protect the key directory as well. Exchange only the printed public keys over an independently trusted channel.

`hashstash peer-keycheck --key-file PATH --miner PAYOUT_PUBLIC_KEY --peer-pin IP:PORT=PUBLIC_KEY` validates a dedicated identity and one or more pins without starting any listener. It prints only the transport public key and rejects reusing the configured payout identity. The Linux installer uses this preflight before installing the key owner-only for its service account.

For every existing `--peer IP:PORT`, add `--peer-pin IP:PORT=PUBLIC_KEY`, plus `--peer-key-file /var/lib/hashstash/peer-identity.json`. All configured peers must be pinned, with no duplicates. In pinned mode, an incoming source IP must belong to a configured peer, and its proved public key must match a pin for that IP. This assumes stable, directly reachable peer addresses; account for the actual source IP when using NAT. Pinned mode never retries without authentication. Nodes started without identity/pin options use unauthenticated transport; authentication requires explicit configuration.

The `HSP2PAUT` handshake uses fresh 32-byte OS-random challenges, both pinned BIP340 keys, the chain ID, format marker and explicit client/server roles. Both peers prove possession under a peer-only signature domain before exchanging block data. Every subsequent payload, including the final acknowledgment, carries a session-bound signature over its direction, sequence, length and payload digest. Its frame header contains a four-byte big-endian payload length, an eight-byte big-endian sequence number and a 64-byte signature, in that order. Changed, reflected, reordered and replayed frames fail authentication. Signature/hash work on large frames remains in bounded workers; frame and traffic budgets still apply. Connections, outgoing handshakes and discovery-only reads have a 15-second timeout. Other peer reads allow 15 seconds plus one second per whole MiB of the highest validated block capacity, with that capacity clamped to the u32 wire maximum for this calculation. Writes allow 15 seconds plus one second per whole MiB of the frame. Each outbound synchronization attempt has an overall limit of five times that read allowance, and each inbound session twice it. A signed session never reverts to unsigned frames: if its channel is lost, every later read or write fails. This transport provides authentication and integrity, **not confidentiality**.

The private read-only `peerstatus` RPC reports configured-peer reachability, last successful exchange, consecutive failures, transport mode, listener accept errors, and seconds without a new local chain tip. A peer becomes stalled after 90 seconds without a successful exchange; the chain indicator uses 180 seconds without a new tip. No-miner periods can trigger the chain indicator normally. Neither indicator proves an attack. Discovery mode additionally reports its enabled state, advertised endpoint, seeds, known/verified counts, bounded peer entries, and persistence errors. Independent configured-peer retry loops remain active in closed mode; public discovery uses a bounded scheduler with jitter/backoff and reserved outgoing capacity.

`hashstash run --no-stratum` starts a validating/relaying node without binding its solo-mining listener. RPC and peer synchronization continue. It does not start or stop external mining hardware, and it is not a replacement for access restrictions on development RPC methods.

## Public authenticated discovery

`--peer-discovery` explicitly enables public participation using the same signed handshake and frames. New nodes prove possession of a valid dedicated transport key; previously configured endpoint pins remain mandatory. Incoming traffic from a pinned IP must prove a pinned key for that IP, and an outgoing connection to another port on a pinned IP must also prove one of that IP's pinned keys. An unrecognized key at another IP may join, but it never bypasses block validation. Closed pinned mode continues to reject discovery and unconfigured peers. Neither mode falls back to unsigned traffic. See [joining a network](RUNNING.md#joining-a-public-network) for seeds and inbound port setup.

Bootstrap accepts at most 16 numeric/DNS seeds, at most eight DNS results per seed, five-second resolution deadlines, and ten-minute refresh intervals. DNS replies cannot nominate private addresses in public mode. A numeric seed or configured peer is an explicit operator choice; it is still subject to handshake and chain validation. Discovery gossip accepts only conservative global-unicast addresses, rejecting private, loopback, link-local, unspecified, multicast, documentation, benchmarking and transition ranges. IPv4-mapped addresses normalize to IPv4 before filtering. An inbound advertisement must match the connection's observed source IP. Advertised addresses are not forwarded until a successful chain synchronization, except the operator's own explicitly advertised endpoint.

The book has at most 256 entries, with at most 32 from one source network, 16 learned destinations in one network (IPv4 /16, IPv6 /32) and two learned endpoints per IP address. A full book replaces entries instead of refusing new ones: configured peers and numeric seeds displace any learned entry, so persisted entries can never crowd them out, while a learned address displaces only an unverified entry, failed ones first and otherwise in an unpredictable per-process order. A learned address that never answered is dropped after three consecutive failures. Duplicate announcements do not refresh lifetime or clear failure backoff. Entries expire after seven days without successful contact; only verified entries persist. A single unknown probe is permitted while a recent healthy peer exists, reserving capacity for established synchronization. Healthy peers cannot be queued behind a flooded unverified book. Entries with equal attempt times, including never-tried entries, are tried in the unpredictable per-process order rather than numeric address order. Prefix diversity prevents one network group occupying both public outbound slots; private-network fixtures explicitly relax this scheduling rule. Discovery runs at most once per successful endpoint per minute, separately from ordinary synchronization. Address responses never include operator-configured peers, and every requester receives the same sample until the set of eligible recent peers changes, so repeated requests cannot enumerate them.

The chain-scoped sidecar is limited to 128 KiB before parsing and 256 entries before admission; saved chain/version, endpoint filters, source quotas and timestamps are rechecked on load. A wrong-chain, malformed, oversized or symbolic-link sidecar is renamed to `NAME.invalid` without following a link; startup continues with configured peers and seeds and reports the reason in `peerstatus.discovery.load_error`. Saved verified rows dated after the current clock, as after booting without a real-time clock, remain on disk and load once the clock reaches them. Rows that look expired at startup also remain on disk until this run verifies a peer, so a clock running fast cannot erase them either. Saved future retry times are clamped to one minute. The book is rewritten only when its persisted form changes, and the write and its fsync run without holding the discovery lock. Temporary files use unpredictable names and exclusive creation, and leftovers from an interrupted save are removed at startup; books are never written through a symbolic link. Replacement is an atomic rename on Unix and Windows. Persistence errors appear in `peerstatus.discovery.last_error`.

## Remaining limits

These controls reduce resource abuse; they are not distributed denial-of-service protection. Many source addresses can evade per-IP limits: IPv6 accounting groups a /64 but does not aggregate larger prefixes, so a holder of a /48 or of many networks can still multiply rate budgets. Inbound sessions are not evicted; sources in enough distinct network groups can still occupy the general inbound slots for their session deadlines, leaving only the reserved slots to configured and recently verified peers. A compromised pinned peer can still misbehave. Discovery enforces network-prefix/source quotas rather than claiming provider or operator independence. Authentication prevents impersonating an explicitly pinned key and binds other peers to the keys they prove; an unknown discovered key is not a trusted identity. It cannot guarantee reachability, prevent a routing partition, or make compromised peers honest. A three-node deployment on one provider is not eclipse-proof. Transport is unencrypted, and a node's transport key persists across restarts and address changes, so observers can link its sessions. Accepted block bodies and disk indexes still grow, and no pruning policy is implemented. Valid live account/proposal state can grow too. A valid large block or deep reorg still consumes work; budgets bound specific stages, not total wall-clock latency or exact process memory.

## Validation

The maintained [hostile-network suite](../tests/network_hostile.rs) covers malformed and oversized frames, parser boundaries, per-IP and per-service accounting, slow connections, invalid blocks followed by honest synchronization, unauthorized mining, and coherent wallet reads under load. The [transport suite](../tests/node_transport.rs) covers relay, synchronization, and Stratum. The [reorganization suite](../tests/reorg_stress.rs) checks governance rollback, pending transaction recovery, competing histories, and database restart.

The peer-authentication unit tests cover wrong pins/chains, role and challenge binding, modified payloads, reflection, replay, cross-session substitution, oversized lengths, sequence violations and dedicated key-file handling. The [authenticated transport suite](../tests/peer_transport_authenticated.rs) runs independent localhost nodes, verifies real synchronization and recovery after hostile unauthenticated clients, checks fail-closed configuration, and verifies observer startup without a Stratum listener. Chain cache tests retain hundreds of valid siblings, exercise a deeper-than-cache higher-work fork with bounded replay, and verify reopening after corrupting only the rebuildable indexes. The [state replay suite](../tests/poc_state_replay.rs) checks depth-bounded reconstruction, fork-point retention and resumable deferral under cache churn, and side-branch admission; the [selection suite](../tests/poc_mempool_truncate.rs) checks that unpayable or repeatedly failing candidates cannot crowd out other senders; and the [capacity suite](../tests/side_branch_capacity.rs) checks that only competitive losing branches raise the peer allowance.

See the [validation record](VALIDATION.md) for completed checks. Reproduce the automated checks with `cargo test --all-targets --locked`; use the [testnet guide](TESTNET.md#repeat-isolated-checks) for a separate live network. Tests use finite traffic against isolated local listeners. The seeded parser corpus is regression testing, not continuous coverage-guided fuzzing.
