# Wallets

## Wallet setup in the app

The network phase is visible beside the Hashstash name on every page. Click Rest, Auction or Governance to open its details. **Explorer → Network → Phase timing** shows the current schedule. Decisions last a fixed number of blocks, and each block counts once. Auction lead and rest use scheduled seconds, advanced by each block’s target interval. Wall-clock estimates depend on mining; a stopped chain does not advance.

A new browser profile, site, or network starts with no saved wallets or selected account. You can browse the network without creating a wallet. Open **Wallet** in the main navigation. The three actions are:

- **Create wallet** generates a random private key in the browser and selects the new hot wallet.
- **Import private key** accepts a 64-character hexadecimal key or a backup file, saves it in the browser, then selects that hot wallet.
- **Watch account** accepts a checksummed address or exported watch-only file. Its forms prepare unsigned transactions for signing elsewhere.

The menu at the top identifies each wallet by its address and shows its hash and stash balances. Hot and watch-only labels distinguish the signing mode. Governance begins with full holdings in each possible outcome. If PASS and If FAIL show those separate positions; only the winner survives. For payments shows the smaller cash balance before fees, already included in both outcome rows. These values are never added together. Selecting an entry switches accounts immediately. Importing a private key for an existing watch entry upgrades it to a hot wallet; adding a watched address never removes a saved key. Adding a wallet does not create an on-chain account. Its first funded payment or mining reward does that. Mining configuration belongs to node operators; normal wallet pages do not initiate mining or change its payout account.

Hash amounts in the browser wallet and cold signer use **hash**: one displayed hash is 1,000 raw hash atoms. Amount fields accept a decimal hash amount, optionally followed by `hash`, with up to three decimal places. One raw atom is `0.001 hash`. Stash quantities use **stash**: one displayed stash is 1,000 share atoms. Stash fields accept a decimal, optionally followed by `stash`, with up to three decimal places. Prices show hash per stash. Both display denominations preserve the underlying balances and signed amounts. Mining work uses EH and hash rate uses EH/s, including small decimal values.

Use **Stash** to buy or sell during Rest and Auction. During an active decision, that page links to **Governance**, where the same controls trade the selected PASS or FAIL outcome. The curve graph stays on Stash with its own PASS/FAIL selector, independent of the trade form. It plots marginal price against stash supply, shows the current point on a funded curve, and shows the flat opening rate for an empty reserve. After the decision, the trade controls return to Stash. Wallet management, sending, and Explorer remain available throughout.

The Wallet page displays the selected address. **Copy address** is sufficient to add it through **Watch account** on another node: the address already encodes the public key and a network fingerprint. Send, grant proposals, and typed watch-account entry require a valid address for the current network. **Back up private key** opens the selected hot wallet's private key, with separate copy and download buttons. Import accepts that backup format as well as `{"secret":"…","public":"…"}` key files. Watch-only entries contain no private key and do not offer a private-key backup. Watch-only descriptor files can be imported explicitly.

Wallets and selection are stored in the browser profile's local storage, separately for each origin (scheme, host, and port) and chain ID. Other visitors and browser profiles have independent wallets. Tabs at the same origin share wallets and selection; switching accounts cancels a pending transaction for the previous selection. Node restarts do not affect these saved browser wallets. Changing sites or ports does not transfer them: import a backup or watch the address there.

Keys are saved in the browser, unencrypted unless you set a passphrase (see [Key protection](#key-protection)), and never sent to the node. Back up each private key before clearing site data or changing browsers. Browser wallets require HTTPS or localhost, secure randomness, and Web Locks support. The browser checks the export’s network context and verifies every prepared transaction byte against the intended sender, nonce, block reference, lifetime, operation, fees, and data before signing. Only signed transaction bytes are broadcast. As with any web wallet, use a trusted site: code served by that origin can access its saved wallets. Watch-only mode keeps spending keys on the separate signer.

Treat a browser hot wallet as a spending balance, not storage. Without a passphrase, any script running on the same origin, a browser extension with access to the site, malware on the computer, or anyone who can read the browser profile can take the saved keys. A passphrase protects the saved profile, for example a copied disk, backup or profile folder, but not the running page: same-origin code or an extension can capture the passphrase as it is typed or use the wallet while it is unlocked. Serve the wallet from its own origin (scheme, host and port), not beside other web applications. **Copy** in the private-key backup puts the key on the system clipboard, where clipboard history and other applications can read it. The page clears the clipboard 30 seconds later, unless it can see (with clipboard-read permission already granted) that the clipboard now holds something else; a page without focus cannot write the clipboard and clears it when it regains focus, and clipboard history may keep its own copy. Prefer **Download**, and store the file offline. The download is built from bytes the page wipes once the browser holds the file; the key's text in the page cannot be wiped. Keep larger balances in a watch-only account signed by the cold signer.

### Key protection

**Wallet → Key protection → Set passphrase** encrypts every private key this browser saves for the selected network. This is the migration from unencrypted storage: existing keys are sealed in one storage update, and keys created or imported later are saved only sealed. The passphrase needs at least 8 characters and cannot be recovered, so keep each key's backup. Unicode text is compared in its NFC form.

A page holds the opened passphrase key in memory only. Every new page or reload starts locked; **Unlock** asks for the passphrase, and signing, a key backup, adding a private key or reading mail with a locked wallet ask for it first. The page locks again after five minutes without signing, a backup or adding a key, or with **Lock now**. Background mail scanning does not count as use: a locked wallet stops the scan without advancing or clearing its saved checkpoint. Selecting accounts, watching addresses and preparing watch-only transactions need no passphrase. Changing the passphrase needs the current one unlocked; other tabs then lock. **Remove passphrase** returns the keys to unencrypted storage after a second confirming click.

The format is `hashstash-browser-lock-v1`. PBKDF2-HMAC-SHA256 with 600,000 iterations and a random 16-byte salt stretches the UTF-8 passphrase into a 256-bit AES-GCM key, which the page cannot export. Storage gains a `lock` object `{format, kdf:"PBKDF2-HMAC-SHA256", iterations:600000, salt, check}`, and each sealed wallet a `sealed_key` `{iv, data}` with `private_key` null. Every value is lowercase hexadecimal. Each seal uses a fresh 12-byte IV and a 128-bit tag. A sealed key's 48 bytes are the 32-byte secret and its tag; its authenticated data is the UTF-8 text `Hashstash/browser-wallet-key/v1`, a zero byte, the 32-byte chain ID and the account's 32-byte public key, so a sealed key cannot be moved to another account or network. `check` seals an empty value under the text `Hashstash/browser-wallet-lock/v1`, a zero byte, the chain ID and the salt, and identifies a wrong passphrase before any key is opened. An opened key must still match its address. Stores without a passphrase keep the original layout, and earlier pages refuse an encrypted store without changing it. A key found unencrypted beside the lock, for example written by other software, is sealed at the next unlock.

Optional node wallets use a separate local database. They are not exposed by the public listener or automatically copied into browser storage. See the node-wallet tools below.

## Sending HASH

**Amount** is exactly what the recipient receives. The wallet quotes the required minimum automatically, including account creation when needed, and signs the exact total fee. Optional extra defaults to zero and is added when constructing that quote. Sending 1 hash with a total fee of 0.001 hash costs exactly 1.001 hash. If the signed fee is below the required minimum when included, the whole transaction is rejected; a higher signed fee is paid in full.

The entire actual fee—mandatory minimum plus optional extra—follows the governed miner/revenue split, initially 50% each. The miner receives the whole-atom floor of its percentage and the revenue receives the remainder. Governance can select any whole percentage from 0% to 100%; an approved change becomes active after rest and both outcomes use the same active split.

The cold signer shows the exact recipient amount, exact fee and total debit. It cannot verify the current minimum rate or fee allocation without a node; the signed fee itself is fixed and paid in full.

Revenue is a hash buffer governed through proposals. The non-miner part of fees and winning proposal bids supply it. Grants use waiting revenue first and then reserve; a winning bid cannot fund its own grant. Outside a decision, revenue replenishes a nonflat reserve while preserving stash supply and marginal price. See [Reserve and revenue](RESERVE.md).

**Chat** reads public text attached to transactions, including ordinary payments, Stash trades and proposal support. Add text to the transaction's Message field and use its normal signing flow. Pending messages can expire or be displaced by a reorganization; mute settings affect only this browser. See [message format and feed](CHAT.md).

## Transaction data

Transaction forms offer an optional **Message** field. Enter public text, encoded as UTF-8, or choose advanced hexadecimal input for exact bytes such as `00ff80`. Leaving it empty attaches no data. The bytes are public, signed, and stored with the transaction. Proposal description is its single text attachment, with a matching signed SHA256 commitment. Mail has its own encrypted payload and never places its subject or body in this public field.

Data contributes to the transaction size and mandatory fee. The complete signed transaction, including operation, signature and data, must fit the block’s byte and weight capacity. Editing data refreshes the fee quote. Hot signing and watch-only preparation carry the same bytes; the cold signer displays the exact hex and byte count for review.

## Grant proposals

A grant can pay multiple recipients in one decision. Enter a positive amount for each distinct recipient and review both the individual payments and their combined total. The wallet puts the list in canonical key order; the signed list fixes who receives each amount.

Proposal text is published as the rationale only when it is plain UTF-8 text whose SHA256 equals the signed description hash. Plain means at most 2,048 bytes, with no leading or trailing whitespace and no control characters other than line breaks and tabs. The cold signer applies the same rule: its **Rationale** field reports whether the attached text matches, and text that is not the rationale is labelled as attached data, with a warning that names the reason: a different hash, or a matching hash on text that is not publishable plain text.

The Governance page looks each listed proposal's rationale up through the Explorer, the current decision's first, and starts at most four lookups per refresh. A verified rationale is kept for the visit. Anyone can register proposals whose text is never published, so a proposal without a verified rationale is looked up again only after 30 seconds, then after twice as long each time up to 10 minutes, or as soon as its description hash becomes known.

The proposal fee includes 1,024 execution weight per payout, even for an existing account, and another 1,024 for the proposal's permanent record. A Support also pays 1,024 when it is your first support for that proposal. This fee is paid when the proposal is included and is not refunded if it loses. It is separate from the auction bid, whose refund rules still apply. The complete signed proposal must fit the block’s remaining byte and weight capacity. There is no separate recipient-count or transaction-size setting. Maintained presets start with 16 KiB of block capacity; prepaid payout weight also uses it. Governance sets the capacity directly. Actual transactions still need room for their bytes and execution weight, and each interface has its own resource limits.

If the proposal reaches a decision, PASS escrows the combined amount. If PASS wins, all recipients receive their exact listed amounts together, without a settlement fee or a manual claim. If FAIL wins, nobody receives the grant. The full list is also shown by the offline signer.

A grant can use all waiting revenue but at most half of the reserve; the **Grant capacity** figure and the node's grant quote apply that limit. The capacity falls when holders sell Stash, so a grant sized close to it can become unfundable and be cancelled for a refund before its decision opens. While a grant that draws on the reserve is decided, both outcomes trade on the steeper drawn curve. That includes FAIL: selling FAIL pays less than the same sale would at the original ratio, and if FAIL wins, part of what the reserve set aside can stay as waiting revenue, leaving the remaining FAIL holders a lower price than without the sale.

The highest bid wins the auction once it has led for the lead period, or when it leads at the auction timeout. A proposal that outbids the leader late therefore wins at the timeout and pays its bid.

## Governance settings

Choose a setting and enter its exact new value. **Target block interval** uses positive whole seconds, at most the difficulty half-life (900 seconds in the presets), at least a quarter of the genesis interval (3 seconds in the presets), and at most half or twice the current interval. **Decision length** uses a whole number of blocks, at least 3. **Auction lead** and **Rest** use whole seconds and allow zero. The lead is at most half of the auction timeout less one block interval (232 seconds on testnet). Rest is at most 4,194,304 seconds (about 48.5 days), and a decision also lasts at most that long. A longer target interval must keep both the current lead and the current decision length within these limits; lower them first if needed. **Block capacity** uses weight, from 4,096 (room for any proposal without data beside a new mining account) through 64 MiB, and at most half or twice the current capacity. **Minimum fee rate** uses whole raw hash atoms per 1,024 weight and must stay positive; one proposal can at most double it, or raise it from zero to one, and never beyond 2^16 times the genesis rate. **Miner fee share** is a whole percentage from 0 through 100. **PASS margin** and **Price change per block** accept percentages in exact 0.01% steps. The price-change limit must be positive and below 100%, since 100% or more permits full redemption. The PASS margin must stay below the price movement that half of a decision's blocks can produce, so that a later PASS remains possible. The initial price-change limit is 10% per block.

These limits exist because only another decision can undo a passed value. Values must fit unsigned 64-bit integers. Clocks, heights and future phase boundaries must remain representable for the chain's whole height range. See the [parameter rules](CONSENSUS.md#transactions-and-parameters).

The active decision and rest period keep their frozen settings; approved changes affect the following cycle. Changing the target interval changes approximate wall time, not the number of blocks in an active decision. Minimum fee rate starts at one in the presets; block usage does not adjust it. A change takes effect from the block after its activation block, and the pending value is visible during rest. A transaction prepared just before a minimum-fee increase or a capacity decrease may therefore have only the activation block left to be included; if it misses it, prepare it again. Fee quotes then include `scheduled_change` with the new minimum fee and the first block it applies to. The wallet shows a warning beside the fee, and the CLI adds one to its review; an optional extra that covers the new minimum keeps the whole lifetime. The faucet defers claims until the change is active.

The browser preserves every digit of the entered integer or margin percentage when quoting, exporting and signing. Offline review shows the exact old and proposed values. Signing verifies the canonical bytes; the node checks the proposal against the current settings, phase and schedule before accepting it.

## Buying and selling Stash

Choose **Buy** and enter the hashes to spend, or **Sell** and enter the stash to sell. The form shows the estimated receipt and fee. **More options** contains the optional extra fee, order expiry and message. Buying deposits hashes into the reserve and creates stash; selling removes stash and returns hashes from the reserve. During Rest and Auction, orders use the shared reserve. During Governance, each order selects PASS or FAIL. A deposit into an empty reserve opens a flat curve at the configured share scale.

Orders included in the same block clear together at one execution price per world. The batch respects the governed price-change limit, initially 10% from the previous closing price. Excess input on a constrained side fills proportionally. An order can fill fully, partly, or not at all; unused input stays in your balance. Included orders do not remain open for another block. The preview is an estimate, and other orders in the same batch can change it. If the preview predicts a partial fill, the form shows the estimated unused amount. A zero fill still pays the fee if included.

Fees require hashes already available before the block begins, in both outcomes during a decision. Withdrawal proceeds and incoming transfers in that block cannot fund an order or its fee. Signing fixes the input, fee, block reference and lifetime; it does not guarantee an output. Explorer shows the actual fill and returned input.

## Cold signing

An address encodes the same public key with a network fingerprint and a Bech32m checksum. Changing address presentation does not create a different account or alter balances. See [address format](ADDRESSES.md) for the encoding and command-line tools. A public-key-only watch descriptor can be imported explicitly; the app derives its address for the selected network.

On the signing computer, run:

```powershell
.\Start-ColdWallet.ps1
```

This opens the separate `bin/hashstash-cold.exe` tool at `http://127.0.0.1:19580/`. It serves its own embedded interface and makes no node or peer connections. For offline signing, run it on a disconnected computer. No browser extensions or downloaded assets are needed. The signer never releases a loaded private key over HTTP; a newly generated key's backup leaves it once, in the response to the page that generated it.

Loopback is shared by every account and service on the computer, so the signer never serves its session token over HTTP. Every request that opens a key, reviews or signs must carry that token. The signer prints a launch address ending in `#token=…`. The launcher chooses the token itself, passes it to the signer through its own environment (`HASHSTASH_COLD_TOKEN`, which other accounts cannot read), and opens that address. The browser never sends the fragment. The page keeps the token for reloads of the same tab and removes it from the address bar. A page opened without it can show status but cannot use a key; open the printed address again. With `-NoBrowser`, copy the printed address yourself. An open wallet locks itself after five minutes without an authorized request (`hashstash-cold --idle-lock-seconds N` changes this), even if no request arrives, and a pending review is discarded with it. Lock the wallet after signing anyway. Another program running under your own account can still read the token, the key and the signer's memory, so keep the signing computer free of untrusted software.

The signer also bounds the connections other local programs can hold: it serves at most 16 at once, more than a browser opens. A connection must send each request head within five seconds of opening or of its previous response, so a partial request or an idle keep-alive connection is closed. At the limit, a new connection takes the place of the one that has waited longest for its next request, which is closed; only when all 16 are handling requests is the new one closed unread. A request without the session token is refused before its body is read, and its connection then closes. Holding connections open, idle or with partial requests, therefore never keeps the browser out. A program that keeps every connection busy with requests, without pause, can still crowd it out, at the cost of continuous work for itself and the signer; that is a local denial of service, and the signer cannot tell such a program from the browser.

The launcher uses the latest local network configuration when available; `-Config PATH` or `-ChainId HEX` selects it explicitly. On a disconnected computer, set the network by importing the small file exported from **Explorer → Network → Identity → Export network**, or paste its full chain ID into the signer's Network field. The signer reviews transactions only for a network selected this way: an export's own network context is checked against that selection and never adopted, so an export alone cannot choose which network the review displays. A known network is also required to copy an address or export its watch-only file. Changing networks clears a pending transaction review. An export with different network context is rejected.

Every transaction signature commits to the chain ID of the network it was signed for, and the review shows that chain ID as **Network · signed**. The chain ID is not part of the transaction bytes; each node verifies signatures against its own chain ID. A hostile preparer who pairs the selected network's label with a body anchored on another network therefore gains nothing: the signature is bound to the selected network, where the anchor is unknown, and the other network rejects it. The same key can safely hold funds on several networks. For a different network, export its identity and a new watch-only descriptor. A private key can represent an account on either network, but its address and balances are specific to the selected chain. Creating a fresh testnet does not move funds from a saved network.

**Open with** offers four modes:

- **Private key** (the default) restores an account from its 64-character hexadecimal key or backup file, including `{"secret","public"}` files written by `hashstash keygen`. It restores the same public key; the address additionally depends on the selected network.
- **New random key** creates an account from the operating system's secure randomness and offers its `hashstash-private-v1` backup file once, in the response that created it. The signer never serves that key again, so whoever later obtains the session token still cannot read it. Until **I saved the backup** is chosen, the signer reports no address or watch-only export and refuses to review transactions, and the page hides the public key, so an unsaved account is not funded by mistake. Reloading the page before confirming discards the key; generate a new one. **Lock** also discards an unsaved key.
- **Passphrase · this network** uses `hashstash-passphrase-v2`. It needs the network to be selected first, because the chain ID salts the derivation: the same phrase opens a different account on every network, and selecting another network locks the account. Phrases need at least 16 characters of printable ASCII (letters, digits, punctuation and spaces). Other characters are refused because a visible phrase such as `café` can be stored either composed or decomposed, depending on the keyboard, input method or system, and the two would open different accounts. Each guess costs an attacker a 128 MiB scrypt run, but a short or well-known phrase can still be guessed; a random key is stronger than any memorable phrase.
- **Legacy v1 passphrase · restore only** uses `hashstash-passphrase-v1`, a single unsalted SHA256 that is the same on every network, so anyone can test guesses against all public accounts at once. It requires confirming that an existing v1 account is being restored. Move such funds to a new random key.

Entering a private key as a passphrase derives a different account. Spaces and capitalization are significant in both passphrase schemes, and legacy v1 also uses Unicode exactly as stored.

Choose **Export watch-only account** to save the watch-only descriptor. Copy only that file to the online computer. The passphrase and private key stay in the running signer; they are not saved by the tool. **Lock** clears the loaded key and pending review. Closing the browser does not stop the signer process. The launcher prints its process ID; ending that process closes the tool. The signer wipes the buffers it controls, but request copies inside the HTTP and JSON libraries, the browser page and the secp256k1 library are not guaranteed to be erased: treat the signer computer's memory, swap and crash dumps as holding the key while it runs. On Linux the service file sets `LimitCORE=0`. On Windows, Windows Error Reporting can save a crash dump of the signer: on the signing computer, add a DWORD value named `hashstash-cold.exe` with data 1 under `HKEY_CURRENT_USER\Software\Microsoft\Windows\Windows Error Reporting\ExcludedApplications`, do not configure `LocalDumps` for it, and turn off hibernation (`powercfg /hibernate off`).

## Prepare, sign, broadcast

1. In the watch-only interface, use Payments, Stash, or Governance forms. **Prepare transaction** opens an unsigned export. Copy it or download its file.
2. Bring the export to the cold computer. Import or paste it, then choose **Review**. The tool decodes the transaction itself and displays every signed field. Hash amounts and fees use exact hash decimals with every signed raw hash atom preserved; Stash quantities use exact stash decimals with every share atom preserved. Raw share atoms remain in the collapsed technical details.
3. Choose **Sign transaction**, then copy or export the signed result.
4. On the online computer, open **Payments → Advanced → Broadcast signed transaction**, paste or import the signed result, and choose **Broadcast**.

The signer checks the transaction format and matching sender. It cannot check live balances, governance state, or whether its block reference, nonce or lifetime is still usable; the online node validates those when broadcasting and including the transaction. Editing or replacing the unsigned input clears its previous review. Signing consumes that review.

A lifetime above 1,000 blocks gets a **Lifetime warning** in the review, and the signer refuses to sign it until **I accept that this signature stays valid for … blocks** is ticked. Until such a transaction expires or its nonce is used, whoever holds the signed result can broadcast it at a moment of their choosing; an amount-only Stash order then fills at that later block's price. Prefer the shortest lifetime that covers the offline round trip.

Both hot and watch-only wallets offer this broadcast control. Every transaction defaults to a two-block lifetime. Trades expose this under **More options → Order expiry**; other transactions use **Payments → Advanced → Transaction expiry**. Preparation signs the current block hash. For example, an anchor at block 100 with a lifetime of 2 permits inclusion in blocks 101 or 102. An expired transaction must be prepared and signed again. If a reorganization removes its anchor, the transaction is invalid on that branch. The node drops such a transaction without a record. The form that submitted it follows it by sender nonce: once the pending list is complete and has twice lacked it while its nonce is unused, the form reports **No longer pending** and asks for a new preparation. A used nonce reports **Mined or replaced**. The broadcast control follows a signed transaction the same way when its sender is the selected account; for another account it reports only the broadcast ID. Expiry governs how long an order can wait for inclusion; the price limit applies separately to each block, so it can compound while an order waits.

## Advanced startup options

The testnet launcher's separate `miner.key` files back up the configured mining recipients and can be imported explicitly through the Wallet page. `Start-Testnet.ps1 -Fresh -SeedWallets` preloads the optional server wallet database for automated functional tests, not browser storage. The manifest records that choice. `Start-Devnet.ps1` uses the same opt-in seeding.

For direct startup, optional `run --wallet-key miner.key` or `run --watch-key <address>` seeds the optional server wallet database. The watch option also accepts a raw public key for command-line use. These flags cannot be combined. Without either flag, a fresh server wallet database has no entries. A database that holds no wallets is seeded by the flags, including one left empty by an earlier start that failed or ran without them (wallets are never deleted, so an empty database holds no choice to preserve). A database that holds wallets keeps its saved selection; the flags are then not applied, and the node prints a warning naming the saved selection unless it already is the requested wallet. Import or select the account through the private wallet tools instead. These options do not change a visitor's browser wallets or selection.

`Start-WatchOnly.ps1 -WatchFile .\hashstash-watch.json` remains available when a separate node is wanted. It creates its own database, seeds a watch entry, and joins the latest testnet on ports 20080–20082. Use `-Address '<address>'` instead of `-WatchFile` to enter an address directly. Use `-ManifestPath PATH` to select a saved testnet or `-Config PATH -Peer HOST:PORT` for another configured network; `-BasePort` selects unused listener ports. Its browser Wallet page has its own create/import/watch controls; add the watch address there explicitly. Normal wallet switching does not require this launcher. `Stop-WatchOnly.ps1` stops that separate node and preserves its files.

## Preparing and broadcasting from PowerShell

Use the online interface's ordinary action forms to prepare transactions in watch-only mode. The CLI supports the same operations through JSON files. CLI amount and fee arguments, RPC amount strings, configuration values, and transaction bytes retain integer hash atoms; the displayed hash conversion is a UI presentation rule. This example sends one raw atom (`0.001 hash`). Replace `RECIPIENT_ADDRESS` with the intended recipient’s address on the same chain:

```powershell
'{"TransferExact":{"recipient":"RECIPIENT_ADDRESS","amount":"1"}}' | Set-Content -Encoding ascii .\operation.json
.\bin\hashstash.exe prepare --url http://127.0.0.1:19480/rpc --sender '<address>' --operation-file .\operation.json --extra-fee 0 --expiry-blocks 2 --out .\unsigned.json
```

For a manual offline round trip, choose an explicit longer `--expiry-blocks` value if two blocks will not leave enough time. Move `unsigned.json` to the cold tool, review and sign it, then bring its signed transaction hex back to the online machine. Paste that hex into Broadcast in the online interface, or save it as `signed.txt` and run:

```powershell
.\bin\hashstash.exe broadcast --url http://127.0.0.1:19480/rpc --raw-file .\signed.txt
```

Preparation fills the next available nonce, exact total fee, operation, data, current block reference and lifetime. It places the selected chain ID in separate export metadata for address formatting and network checks; the signer then signs for its own selected network, which must match. Add `--data-hex 00ff80` to `prepare`, `send`, or `transfer` to attach exact bytes; omit it for empty data. Use `--extra-fee` to add an amount to the quoted minimum, or `--fee` to choose the exact total instead; these options are mutually exclusive. The entire signed fee follows the governed split. The optional extra is not independently encoded in the signed record. Preparation includes transactions already pending at that node when choosing the nonce. Preparing does not reserve a nonce or send a transaction. Two unbroadcast preparations may therefore use the same nonce; only one can be executed. Prepare again if the account changes or the signed transaction expires.

The CLI `send`, `transfer` and `prepare` commands check every prepared field against their request and print a review to stderr before signing or saving; stdout stays machine-readable. The endpoint still reports the fee rate, account nonce, anchor and network, so the CLI limits what it accepts:

- An automatic fee may exceed the requested extra by at most 1,000 atoms (1 hash). `--max-fee` sets a different ceiling for the total; an exact `--fee` needs none.
- Without `--nonce`, the CLI takes a loopback endpoint's reported `pending_nonce` at its word, so it downloads no raw pending records; the review marks that pending nonce as unverified. A remote endpoint's `pending_nonce` is accepted unchecked only when it equals the account nonce. A remote endpoint that reports a higher one, or any endpoint that reports none, is scanned instead: the CLI starts from its account nonce and raises it past the sender's signature-checked pending transactions while their nonces are consecutive, and refuses a reported pending nonce those transactions do not reach. Either way the CLI requires the node to use that nonce, and the review shows the chosen nonce and the reported account nonce, which only another node can confirm.
- A remote endpoint never chooses the nonce of a transaction whose lifetime exceeds the default: `send` and `prepare` then require `--nonce`. Check the account's next nonce on a node you trust first.
- Plain `http://` is accepted only for loopback IP addresses. Use `https://` for a remote endpoint, or pass `--insecure-http` to accept replies that anyone on the path can forge. Environment proxies and redirects are never followed.
- A non-loopback `--url` also requires `--config` or `--chain-id`, and the endpoint must report that network. That catches an honest endpoint on the wrong network, not a dishonest one: it can report the pinned chain ID with another network's tip as the anchor. The signature commits to the pinned chain ID, so the transaction is not valid on that other network either, but it is never accepted where it was meant to go. `--anchor-url URL` catches such an anchor with a second endpoint, ideally run by someone else: before signing or saving, it must report the pinned network and hold the anchor block at its height on its canonical chain (through `explorer_block`; a block it has not indexed yet is retried for about ten seconds). That endpoint is trusted for this fact, and it follows the same transport rules as `--url`. Without it, anchor ancestry is established only by validating nodes. For a remote endpoint the review then prints a one-line warning to add `--anchor-url` or to prepare through a loopback node. This is accepted by design: a single dishonest endpoint can withhold the broadcast just as well, with the same result, and the chain-bound signature already keeps the funds from moving on another network.

`send` and `transfer` broadcast the canonical signed hex through `broadcasttransaction`, so they also work with a public-web endpoint, and they require the reported transaction ID to match the locally computed one. A reported ID does not prove the endpoint relayed the transaction. A signed transaction that never confirms remains valid until its lifetime ends, and a transaction with a nonce above the account's next nonce becomes valid once the lower nonces are used. To cancel one early, submit a different transaction with the same nonce N through a node you trust, for example a 1-atom transfer to your own address with `--nonce N`, and give it a higher fee for its weight: nodes keep the better-paying of two transactions with one nonce, so the withheld one can still win against a cheaper cancellation. If N is above the account's next nonce on that node, the cancellation cannot enter its pool alone, and using a lower nonce first makes the withheld transaction valid. Submit those lower-nonce transactions and the cancellation together, or wait for the lifetime to end. Prefer short lifetimes when preparing through an endpoint you do not operate; the CLI warns when a remote endpoint is combined with a longer lifetime than the default.

`hashstash sign` is a low-level automation signer. It accepts a `TransactionBody` JSON document or the unsigned export and requires `--config` or `--chain-id` for the network the signature is bound to; an unsigned export prepared for another network is refused, and the export's own context is never used instead. It prints the same review, including that network, to stderr without asking for confirmation. Use the cold signer for interactive review.

`preparetransaction` accepts `{sender, operation, fee?, extra_fee?, anchor?, expiry_blocks?, nonce?, data_hex?}` with a direct operation. Specify either the exact `fee` or quote-builder `extra_fee`, never both. Omitted extra is zero, so an omitted fee quotes the required minimum. `expiry_blocks` defaults to 2 for every operation. If supplied, `anchor` must match the preparation snapshot’s tip hash; omission selects that tip. Browser forms supply the exact reviewed tip, nonce and lifetime, then verify them before signing. Absolute `expiry_height` input is rejected. Fee quotes expose `anchor`, `anchor_height`, `expiry_blocks` and the derived inclusive `expiry_height` for display; only the anchor and lifetime are signed. The response contains the unsigned export plus `fee_quote`; save `format`, `chain_id` and `body` for the strict offline export, as the CLI and browser do. The quote reports `fee`, `minimum_fee`, `account_creation_fee`, `grant_recipient_fee`, `record_fee`, `extra_fee`, `weight`, `minimum_fee_rate`, `miner_fee`, `revenue_fee` and `miner_fee_percent`, plus operation identity and exact lowercase `data_hex`/`data_bytes`. `extra_fee` describes the difference between the exact fee and the quoted minimum. When a pending MinimumFeeRate or BlockBytes change takes effect within the lifetime, the quote also has `scheduled_change`: `parameter`, `value`, `activation_height`, `effective_height` (the first block under the new value), `minimum_fee` there, and `valid_after`, which is false when the signed fee or size would no longer be accepted from that block. `broadcasttransaction` accepts `{raw}` and returns `transaction_id`. Normal consensus validation applies before acceptance.

The browser manager does not call server-wallet endpoints. It serializes local storage updates with Web Locks and checks a wallet revision before importing, selecting, exporting, signing or decrypting mail. Only public account details, quote/preparation requests, encrypted mail and signed transaction bytes go to the node. Normal wallet pages do not submit mining work or configure a mining recipient.

## Optional node-wallet tools

Opt-in node wallets store keys and selection beside the chain database: `chain.sqlite` uses `chain.wallets.sqlite`. These keys are separate from browser wallets. The file cannot be rebuilt from the chain, so a damaged or foreign one stops startup; the node checks it before replaying history, and the error appears at once. Move it aside only if it holds no keys you need. Import a key file or an explicitly exported private-key backup through Wallet to use that account in the browser.

Hot keys in this database are not encrypted (unlike browser wallets, the node has no passphrase option), so the node makes it and its rollback journal (kept in place between writes, so it never reverts to the folder's defaults) owner-only every time it opens them. On Unix that is mode 0600, and an existing, more permissive file is tightened. On Windows the node replaces the files' access lists with one that grants only the account running it, using the system's `icacls`; the same applies to key files written by `keygen` and `peer-keygen`, the auto-generated peer identity and the session token. A volume without access lists, such as FAT or exFAT, cannot protect them: the node prints a warning, and the files are then readable by every account on the computer. The database records the last network that opened it, and the node prints a warning when another network opens it, because saved keys are then shared by both networks. The record changes only once the chain database has accepted the network, so a launch refused for a mismatched network leaves it unchanged.

Files beside a chain database are named from its full file name, so no two chain databases share one. A chain database named `NAME.sqlite` keeps the names shown here (`NAME.wallets.sqlite`, `NAME.explorer.sqlite`, `NAME.peer-key.json`, `NAME.session-token`, `NAME.peers-CHAIN_ID.json`). Any other file name `F` gets `F-wallets.sqlite`, `F-explorer.sqlite`, `F-peer-key.json`, `F-session-token` and `F-peers-CHAIN_ID.json`. Earlier releases used the name without its last extension, so `net.db` and `net.sqlite` shared `net.wallets.sqlite`. On upgrade, a chain database that has no wallet storage or peer identity of its own gets a copy of the old file, and the node prints its location; the original stays for any other chain database that still uses it, so remove it once none does. The Explorer index, session token and peer book are rebuilt under the new name.

The private loopback listener exposes session-authorized wallet tools: `GET /api/session` with the local session token in `X-Hashstash-Token` lists the server wallets (IDs, names, modes and addresses), the selected account and the current revision; `POST /api/wallet/manage` with `action:"export"`, its `id`, and that `revision` returns a backup when authorized with the same token. Without a valid token `GET /api/session` returns only `chain_id`, `address_hrp`, `browser_wallet`, `public_web` and `miner`, as the public listener does, so another local process cannot link the operator's accounts. The node writes that backup's JSON into one buffer, sized for it in advance, and wipes it after sending; no other string holds the key, though the kernel's socket buffers and the client's copy are outside its control. Export only the intended key and keep the private listener private. These routes and the `/api/wallet` signer are unavailable on the public-web listener. Normal browser use never calls them.

Loopback TCP is not an access-control boundary: every local account and service, and anyone using an SSH forward of the port, can reach it. The node therefore never serves the session token over HTTP. Each server start writes a new random token to the session token file beside the chain database (`chain.sqlite` uses `chain.session-token`). It is created fresh and owner-only (see above for Windows access lists). Local tools running as the node's account read the token from that file. A token from an earlier start is rejected. Wallet requests with a missing or wrong token, or to an unknown path, are rejected before their body is read.

## Recovery and transaction formats

`hashstash-passphrase-v2` derives a secp256k1 signing key as follows. Take the exact passphrase bytes with no trimming; only printable ASCII (bytes 0x20 through 0x7E) is accepted, so no Unicode normalization question arises, and at least 16 and at most 4,096 bytes. Compute `stretched = scrypt(passphrase, salt, N = 2^17, r = 8, p = 1, 32 bytes)` (RFC 7914), where `salt` is the UTF-8 text `Hashstash/Passphrase/v2` followed by the selected network's 32-byte chain ID. Let `tag` be SHA-256 of `Hashstash/Passphrase/v2`. The candidate key is SHA-256 of `tag || tag || stretched || counter`, with a four-byte little-endian counter starting at zero, incremented until the result is a valid secp256k1 secret scalar. Restoring a v2 account needs the same chain ID. The cold signer and the browser module (`derivePrivateV2`, `importPassphrase(passphrase, scheme)`) implement it identically.

`hashstash-passphrase-v1` is the legacy, restore-only scheme. Take the exact UTF-8 passphrase bytes with no trimming or Unicode normalization. Append a four-byte little-endian counter, initially zero. Let `tag` be SHA-256 of the UTF-8 text `Hashstash/Passphrase/v1`. The candidate key is SHA-256 of `tag || tag || passphrase || counter`. If the result is not a valid secp256k1 secret scalar, increment the counter and retry. There is no salt or stretching and the result is independent of network identity, so one dictionary run tests a guess against every v1 account on every network; create new accounts with a random key or v2 instead. Empty input is rejected and the input resource limit is 4,096 UTF-8 bytes. Public keys of both schemes use the existing BIP340 x-only representation; transactions themselves sign the chain ID and an anchor block whose ancestry the node validates.

Watch-only exports with a selected network use `{"format":"hashstash-watch-v2","address":"<address>","public_key":"<64 hex>","chain_id":"<64 hex>"}`. The full chain ID, decoded address, and public key must agree. A `hashstash-watch-v1` descriptor contains only `public_key` and can be imported for the selected network. Neither format contains a signing key. Independent recovery vectors, including significant whitespace and composed/decomposed Unicode, are in `tests/data/passphrase-v1.json` and `tests/data/passphrase-v2.json`; the v2 vectors also record the scrypt output and two networks for one phrase, the browser tests rederive them with Node's own scrypt, and its `rejected` list holds Unicode and control-character phrases that v2 refuses. Their secrets are public test fixtures.

These names identify wallet file formats. Transaction signatures bind the chain ID and the anchor block; the node validates the anchor's ancestry and expiry.

An unsigned export is `{"format":"hashstash-unsigned-anchor","chain_id":"<64 lowercase hex>","body":"<hex>"}`. Its body is the canonical binary `TransactionBody`; no separate human-readable summary is trusted. The signer rejects unknown export fields, unsupported formats, invalid keys, mismatched outcome context, and noncanonical or trailing bytes. The body directly contains one operation, its exact `fee`, and a raw `data` vector, including an empty vector when no bytes are attached. No fee cap, separate extra or fee envelope is serialized. The export’s chain ID is network context, used to format addresses and check the selected network. It is absent from the transaction body; the signing message prefixes the signer's selected chain ID instead. The node checks live proposal eligibility, balances, nonce, anchor ancestry, lifetime and the required minimum fee. An offline signer displays the signed anchor and lifetime but cannot establish the anchor’s membership in a network from this export alone. Reviewed values remain strings so large integers are displayed exactly. The cold signer accepts unsigned exports of up to 64 MiB (about 32 MiB of transaction bytes) by default and refuses larger files before reading them, and larger pasted text before sending it; start `hashstash-cold --max-review-bytes N` for a network whose governed block capacity needs more. Bytes do not bound a grant review on their own, because each payment is key-checked and listed as two fields, so the signer also refuses a grant with more than 4,096 payments before checking them. Every payment needs 1,024 block weight, so that covers a block capacity of 4 MiB; start `hashstash-cold --max-review-payments N` to review larger grants.

Signed exports are canonical `Transaction` bytes in hexadecimal, with surrounding whitespace permitted. Compact integer/length encoding and the fixed 64-byte signature follow [CONSENSUS.md](CONSENSUS.md). A transaction ID is SHA256d of those signed bytes. The format helper bounds lengths by the actual supplied record and checks canonical encoding. Each node enforces the current block-byte and block-weight capacity and amount limits. Browser memory, HTTP response limits and peer frame representation remain practical interface constraints. The wallet container is `hashstash-unsigned-anchor`; older unsigned containers and signed transaction layouts are unsupported. Raw signed bytes contain no network context, so inspection without a selected network shows public keys rather than network-formatted addresses; their signature still verifies only for the chain ID it was made for. Transactions signed for or anchored to an unrelated chain are rejected by the node. Forks sharing the anchor can both accept the same transaction before expiry if its other checks pass.

## Mail and outcome balances

Mail encrypts subject and message locally for the sender and recipient using their existing account keys. See [encrypted mail](MAIL.md) for the format, visibility and recovery limits. Chat remains public. Never paste a private key into a recipient field.

Every account takes part in both governance outcomes automatically. Each outcome has its own cash and stash. Deposit or withdraw directly in PASS or FAIL. Only the winning outcome survives. Ordinary payments debit both cash balances, so the payment ceiling is their minimum, before fees. Every fee needs hashes already available in both outcomes before the block begins. Withdrawal proceeds cannot pay that fee. Use max for a buy keeps the exact quoted fee and one more minimum fee in the traded outcome, checks both cash balances, and warns when the other outcome would keep less than one more fee. Spending the last cash in either outcome therefore blocks every later transaction from the account, including selling the Stash just bought and spending the other outcome's cash, until the account receives a credit. Resolution clears this only if the drained outcome loses. Home and Governance then say so, name the locked address, and give the transfer from any other account that unlocks it: the fee for 1,024 weight less the cash left, one atom at a minimum fee rate of one atom per 1,024 weight. A form whose fee one outcome cannot pay gives the exact shortfall. Keep enough cash in each outcome for the follow-up transactions you plan. Outcome totals are alternatives, never a sum. Governance keeps personal holdings separate from public prices and reserves.

Outcome trading binds the transaction to the active decision and selected PASS or FAIL state.

Mining configuration and CPU testing are operator functions, outside the normal wallet interface; Explorer retains read-only node-work statistics.

Offline review accepts only the six current direct operations and their signed data. Unknown operation tags and malformed byte encodings are rejected before approval; the unsigned-size limit reserves space for the full signature so a reviewed transaction remains broadcastable.
